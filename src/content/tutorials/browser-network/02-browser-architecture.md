# 第二章：浏览器架构

## 本章导读

在开始学习本章之前，你可能会有这些疑问：

- 浏览器到底是由哪些部分组成的？为什么有的浏览器快、有的慢？
- 为什么有时候一个标签页崩溃了，整个浏览器不会跟着崩溃？
- JavaScript 引擎和渲染引擎分别负责什么？它们之间怎么配合？
- 了解浏览器内部架构，对写前端代码有什么实际帮助？

这一章会带你深入了解浏览器的"内部构造"。搞清楚这些，你就能理解为什么某些写法会导致页面卡顿，为什么要把 JS 放在底部加载，以及怎么利用浏览器机制写出更流畅的网页。

## 1 为什么需要了解浏览器架构？

### 痛点分析

很多新手写前端代码时，经常遇到这些问题：

- 页面加载特别慢，不知道问题出在哪里
- 动画效果一多，页面就卡顿
- 点击某个按钮后，页面要等好几秒才有反应
- 面试官问"为什么 JS 要放在 body 底部"，你答不上来

这些问题的根源，都跟浏览器内部的工作方式有关。不了解浏览器架构，就像司机不懂发动机原理——车能开，但出了问题就抓瞎。

### 了解架构的价值

打个比方：你住在小区里，每天进出大门。如果你了解小区的门禁系统、电梯运行原理、水电管线走向，你就能更高效地生活——知道什么时候坐电梯最快，知道水管堵了该找谁。

了解浏览器架构，能帮你做到：

1. **写出高性能的代码**：知道什么操作会阻塞渲染，主动避开
2. **快速定位问题**：页面卡顿时，能判断是 JS 执行慢还是渲染慢
3. **面试加分**：浏览器原理是前端面试的高频考点

> 一句话总结：了解浏览器架构，不是为了造浏览器，而是为了写出更好的网页。

## 2 核心原理：浏览器的多进程架构

### 什么是多进程架构？

早期的浏览器是单进程的——所有标签页、插件、UI 都在一个进程里运行。这就像一个大办公室，所有人共用一台电脑，一个人操作失误，所有人的工作都丢了。

现代浏览器（从 Chrome 开始）采用了**多进程架构**——每个标签页都有自己独立的进程，互不干扰。这就像每个人都有自己的独立工位和电脑，一个人出了问题，其他人不受影响。

### 浏览器有哪些进程？

| 进程类型 | 职责 | 类比 |
| --- | --- | --- |
| 浏览器主进程 | 管理界面、书签、前进后退、文件下载 | 公司前台，负责接待和调度 |
| 渲染进程 | 解析 HTML/CSS、执行 JS、绘制页面 | 车间工人，负责实际干活 |
| GPU 进程 | 处理图形加速、绘制动画和视频 | 美术师，负责画面渲染 |
| 网络进程 | 处理 HTTP 请求、管理缓存 | 快递员，负责收发数据 |
| 扩展进程 | 运行浏览器插件和扩展 | 外包团队，负责额外功能 |

### 进程之间怎么协作？

打个比方：你在浏览器地址栏输入一个网址，整个过程是这样的：

1. 浏览器主进程接收到你的输入，判断这是一个网址
2. 主进程通知网络进程去请求这个网址对应的数据
3. 网络进程下载完数据后，把数据交给渲染进程
4. 渲染进程解析 HTML/CSS/JS，把页面画出来
5. 如果页面有动画或视频，渲染进程会调用 GPU 进程来加速

### 单进程 vs 多进程对比

| 对比项 | 单进程架构 | 多进程架构 |
| --- | --- | --- |
| 稳定性 | 一个崩溃全部崩溃 | 标签页崩溃不影响其他 |
| 安全性 | 进程间无隔离 | 每个沙箱独立运行 |
| 内存占用 | 较低 | 较高（每个进程有独立内存） |
| 性能 | 容易互相阻塞 | 并行处理，性能更好 |
| 代表浏览器 | 早期 IE | Chrome、新版 Edge、Firefox |

## 3 渲染进程内部结构

渲染进程是浏览器的核心"车间"，它内部有几个关键组件：

```
渲染进程内部结构
├── JavaScript 引擎     ← 负责执行 JS 代码
│   ├── V8 (Chrome/Edge)
│   ├── SpiderMonkey (Firefox)
│   └── JavaScriptCore (Safari)
├── 渲染引擎            ← 负责解析 HTML/CSS，绘制页面
│   ├── Blink (Chrome/Edge)
│   ├── Gecko (Firefox)
│   └── WebKit (Safari)
├── 布局模块            ← 计算元素的位置和大小
├── 绘制模块            ← 把元素画到屏幕上
└── 合成模块            ← 把多层画面合成最终显示
```

打个比方：渲染进程就像一个印刷厂。JavaScript 引擎是"调度员"，负责处理逻辑和指令；渲染引擎是"印刷机"，负责把内容印到纸上；布局模块负责排版，绘制模块负责上色，合成模块负责最终装订。

## 4 JavaScript 引擎详解

### JavaScript 引擎是什么？

JavaScript 引擎负责把人类写的 JS 代码翻译成计算机能执行的机器指令。它就像一位同声传译员——你说的话（JS 代码），它实时翻译成对方能听懂的语言（机器码）。

### V8 引擎的工作流程

Chrome 使用的 V8 引擎是目前最知名的 JS 引擎之一，它的工作分四步：

| 阶段 | 做什么 | 类比 |
| --- | --- | --- |
| 1. 解析（Parsing） | 把源代码拆成一个个词，生成 AST（抽象语法树） | 把一篇文章拆成词语和句子结构 |
| 2. 编译（Compilation） | 把 AST 编译成字节码 | 把中文翻译成世界语（中间语言） |
| 3. 优化（Optimization） | 用 JIT 编译器把常用代码优化成机器码 | 发现某句话经常说，直接记住它的英文 |
| 4. 执行（Execution） | 执行机器码 | 开口说话 |

### JIT（即时编译）是什么？

传统做法是先把所有代码翻译成机器码再执行，但这样太慢了。JIT 的思路是：先边翻译边执行，发现某段代码反复执行（"热点代码"），就把它优化成更高效的机器码。

打个比方：你学外语，不是先把整本词典背下来再说话，而是用到的时候再查，用得多了自然就记住了。

### 各浏览器 JS 引擎对比

| 引擎 | 使用浏览器 | 特点 |
| --- | --- | --- |
| V8 | Chrome、Edge、Opera | 执行速度极快，JIT 优化激进 |
| SpiderMonkey | Firefox | Mozilla 开发，平衡性能和内存 |
| JavaScriptCore (JSC) | Safari | Apple 开发，注重能效比 |

## 5 渲染引擎：页面是怎么画出来的

### 渲染流程六步曲

当渲染进程拿到 HTML 数据后，会经过以下六个步骤才能把页面显示出来：

| 步骤 | 名称 | 做什么 | 类比 |
| --- | --- | --- | --- |
| 1 | 解析 HTML | 把 HTML 标签变成 DOM 树 | 读文章，理解每个段落的含义 |
| 2 | 解析 CSS | 把 CSS 样式变成 CSSOM 树 | 给每个段落标注字体、颜色、大小 |
| 3 | 构建渲染树 | 把 DOM 和 CSSOM 合并成渲染树 | 把内容和样式合在一起，生成最终排版稿 |
| 4 | 布局（Layout） | 计算每个元素的精确位置和大小 | 用尺子量每个元素该放在哪里 |
| 5 | 绘制（Paint） | 把元素画成像素 | 用画笔把元素涂上颜色 |
| 6 | 合成（Composite） | 把多层画面合成最终显示 | 把多张透明纸叠在一起，拍一张最终照片 |

### DOM 树和 CSSOM 树

```html
<!-- 这段 HTML 会生成下面的 DOM 树 -->
<html>
  <head>
    <style>
      body { font-size: 16px; }
      p { color: red; }
    </style>
  </head>
  <body>
    <p>Hello</p>
  </body>
</html>
```

```
DOM 树：                    CSSOM 树：
html                        html
├── head                    ├── head
│   └── style               │   └── style
└── body                    │       └── body { font-size: 16px }
    └── p                   └── body
        └── "Hello"             └── p { color: red }
```

### 关键概念：阻塞渲染

渲染引擎有一个重要特性：**遇到 `<script>` 标签时会暂停解析 HTML**，等 JS 执行完再继续。

打个比方：你在看一本说明书（HTML），看到"请先执行以下步骤"（script），你不得不先停下来去做那些步骤，做完才能继续看说明书。

这就是为什么：
- JS 要放在 `<body>` 底部，或者加 `defer` / `async` 属性
- CSS 要放在 `<head>` 里，因为 CSS 不会阻塞 DOM 解析

## 6 浏览器存储机制

浏览器提供了多种存储数据的方式，就像不同大小的"储物柜"：

| 存储方式 | 容量 | 生命周期 | 是否随请求发送 | 适用场景 |
| --- | --- | --- | --- | --- |
| Cookie | 4KB | 可设置过期时间 | 是，每次请求自动带上 | 保存登录状态（token） |
| LocalStorage | 5-10MB | 永久，需手动清除 | 否 | 保存用户偏好设置 |
| SessionStorage | 5-10MB | 关闭标签页就清除 | 否 | 保存临时表单数据 |
| IndexedDB | 大容量（几百MB） | 永久 | 否 | 存储大量结构化数据 |
| Cache API | 大容量 | 永久 | 否 | Service Worker 缓存资源 |

### Cookie vs LocalStorage 对比

| 对比项 | Cookie | LocalStorage |
| --- | --- | --- |
| 容量 | 4KB | 5-10MB |
| 是否随请求发送 | 是（浪费带宽） | 否 |
| 生命周期 | 可设置过期时间 | 永久（除非手动清除） |
| 跨域限制 | 有 | 同源策略 |
| API 易用性 | 需要手动解析字符串 | 直接 get/set |
| 推荐场景 | 登录 token | 用户偏好、主题设置 |

```html
  <!-- ✅ 最佳实践：把 script 放在 body 底部 -->

    // 这段代码在 HTML 全部解析完后才执行
    // 此时 DOM 已经构建完毕，可以安全操作 DOM 元素
    console.log('页面已加载完毕');
    // 输出: "页面已加载完毕"
  </script>
</body>
</html>
```

| 知识点 | 说明 |
| --- | --- |
| 多进程架构 | 每个标签页独立进程，崩溃互不影响 |

## 9 新手常见误区

### 误区 1："JS 放在 head 和 body 底部效果一样"

**错！** 把 `<script>` 放在 `<head>` 中，浏览器解析 HTML 时会先停下来执行 JS，导致页面白屏时间变长。放在 `<body>` 底部，HTML 已经解析完了，用户能先看到内容。

正确做法：把 `<script>` 放在 `<body>` 底部，或者使用 `defer` 属性。

### 误区 2："CSS 放哪里都一样"

**错！** CSS 放在 `<head>` 里，浏览器可以先加载完样式再渲染页面，避免出现"无样式闪烁"（FOUC）。如果 CSS 放在 `<body>` 底部，用户会先看到没有样式的"裸"页面，然后突然变好看，体验很差。

正确做法：CSS 始终放在 `<head>` 中，用 `<link>` 标签引入。

### 误区 3："LocalStorage 和 Cookie 差不多，随便用"

**错！** 两者差别很大。Cookie 每次 HTTP 请求都会自动带上，如果存了太多数据会浪费带宽。而且 Cookie 只有 4KB，存不了多少东西。LocalStorage 有 5-10MB，不会随请求发送，更适合存客户端数据。

正确做法：登录 token 放 Cookie（因为需要发给服务器验证），用户偏好设置放 LocalStorage。

### 误区 4："浏览器只有一个进程在干活"

**错！** 现代浏览器是多进程架构，至少有浏览器主进程、渲染进程、GPU 进程、网络进程等多个进程协同工作。一个标签页崩溃不会影响其他标签页，这就是多进程的好处。

正确做法：理解多进程架构后，你就能明白为什么 Chrome 吃内存——每个标签页都是一个独立进程。

### 误区 5："async 和 defer 效果一样"

**错！** 两者虽然都不阻塞 HTML 解析，但有关键区别：

- `defer`：等 HTML 全部解析完后再按顺序执行，多个 defer 脚本的执行顺序是确定的
- `async`：下载完就立即执行，不管 HTML 解析到哪了，多个 async 脚本的执行顺序不确定

正确做法：有依赖关系的脚本用 `defer`，独立的第三方脚本（如统计代码）用 `async`。

**预期观察结果**：

1. 每个标签页至少对应 1 个渲染进程。复杂的页面可能有多个渲染进程（进程拆分）
2. 除了标签页进程，你还会看到：
   - 浏览器进程（Browser）：管理界面和调度
   - GPU 进程：负责图形加速

### 练习 3（挑战）：存储方式选择

场景：你正在开发一个电商网站，需要存储以下数据。请为每种数据选择最合适的存储方式（Cookie / LocalStorage / SessionStorage），并说明理由。

1. 用户的登录 token
2. 用户选择的主题颜色（深色/浅色）
3. 购物车中的临时商品信息（关闭页面后清除）
4. 用户的收货地址列表（长期保存）

<details>
<summary>点击查看答案</summary>

| 数据 | 推荐存储方式 | 理由 |
| --- | --- | --- |
| 登录 token | Cookie | 需要每次请求自动带给服务器验证身份 |
| 主题颜色 | LocalStorage | 长期保存，不需要发给服务器，容量小足够 |
| 购物车临时信息 | SessionStorage | 关闭页面后自动清除，符合"临时"需求 |
| 收货地址列表 | LocalStorage | 需要长期保存，数据量适中，不需要发给服务器 |

**选择原则**：
- 需要发给服务器的 → Cookie
- 需要长期保存的 → LocalStorage
- 只需要当前会话的 → SessionStorage
- 数据量特别大的 → IndexedDB

</details>
