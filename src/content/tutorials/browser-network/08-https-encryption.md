# 第八章：HTTPS 与加密

## 本章导读

在学这一章之前，你可能会有这些疑问：

- HTTP 传输的数据为什么是不安全的？谁在偷看我的数据？
- HTTPS 是怎么加密数据的？为什么说是"安全"的？
- 对称加密和非对称加密有什么区别？为什么 HTTPS 两种都要用？
- 数字证书是什么？怎么防止中间人攻击？
- TLS 握手过程是怎样的？为什么 HTTPS 比 HTTP 慢一点？

这一章就是为了解答这些问题。我们会从 HTTP 的安全问题讲起，理解加密的基本原理，搞清楚 HTTPS 是怎么工作的，最后学会如何配置和使用 HTTPS。学完这章，你就能理解为什么现代网站都必须用 HTTPS 了。

---

## 8.1 为什么需要 HTTPS？

### HTTP 的安全问题

HTTP 协议传输的数据是**明文**的，就像寄明信片一样，任何人都可以看到内容。这会带来三个严重的安全问题：

**问题一：窃听风险（Confidentiality）**

想象一下，你在网上购物，输入了信用卡号。如果用 HTTP 传输，这些数据就像明信片一样在网络中传输。网络中的任何设备（路由器、交换机、WiFi 热点）都可以看到你的信用卡号。

```
你的电脑 → 路由器 → 交换机 → 服务器
   ↓          ↓          ↓
  信用卡号   信用卡号   信用卡号
（任何人都能看到）
```

**问题二：篡改风险（Integrity）**

不仅能看到数据，还能修改数据。假设你在下载一个软件，攻击者可以在传输过程中替换文件，让你下载恶意软件。

```
原始请求：下载 正版软件.exe
   ↓（被攻击者篡改）
实际收到：下载 病毒软件.exe
```

**问题三：身份冒充风险（Authentication）**

你以为是访问银行官网，实际上访问的是钓鱼网站。HTTP 无法验证服务器的真实身份。

```
你以为访问的是：www.bank.com（真银行）
实际访问的是：www.bank-login.com（钓鱼网站）
```

### HTTPS 解决了什么问题

HTTPS（HTTP Secure）通过加密技术解决了 HTTP 的三个安全问题：

| 安全问题 | HTTPS 的解决方案 | 生活类比 |
| --- | --- | --- |
| 窃听风险 | 加密传输，数据变成密文 | 寄密封信，只有收件人能拆开看 |
| 篡改风险 | 数据完整性校验，被篡改会被发现 | 信封上有防拆封标签，拆过就知道 |
| 身份冒充 | 数字证书验证服务器身份 | 身份证验证，确认对方是真人 |

打个比方：

> HTTP 就像寄明信片：
> - 内容谁都能看到（窃听）
> - 内容可以被修改（篡改）
> - 不知道寄件人是谁（冒充）
>
> HTTPS 就像寄密封挂号信：
> - 内容只有收件人能看（加密）
> - 被拆过就知道（完整性）
> - 有寄件人身份证（证书验证）

## 8.2 核心原理

### 8.2.1 加密的基本概念

加密就是把**明文**（能看懂的数据）变成**密文**（看不懂的数据），解密就是把密文变回明文。

```
明文 + 密钥 → 加密算法 → 密文
密文 + 密钥 → 解密算法 → 明文
```

| 概念 | 说明 | 生活类比 |
| --- | --- | --- |
| 明文 | 原始数据，能看懂 | 写在纸上的话 |
| 密文 | 加密后的数据，看不懂 | 密码写的暗号 |
| 密钥 | 加密和解密的关键 | 保险箱的钥匙 |
| 加密算法 | 加密的规则 | 加密的方法（如替换字母） |

### 8.2.2 对称加密

**对称加密**就是加密和解密使用**同一把钥匙**。

```
发送方：明文 + 密钥 → 加密 → 密文
接收方：密文 + 同一把密钥 → 解密 → 明文
```

**常见的对称加密算法：**

| 算法 | 密钥长度 | 安全性 | 速度 | 使用场景 |
| --- | --- | --- | --- | --- |
| AES-128 | 128 位 | 安全 | 快 | 目前最常用 |
| AES-256 | 256 位 | 更安全 | 快 | 高安全需求 |
| DES | 56 位 | 不安全 | 快 | 已淘汰 |
| 3DES | 168 位 | 一般 | 慢 | 逐渐淘汰 |

**对称加密的优点和缺点：**

| 优点 | 缺点 |
| --- | --- |
| 速度快，适合加密大量数据 | 密钥分发困难：怎么把钥匙安全地交给对方？ |
| 算法简单，计算量小 | 如果钥匙被偷，所有数据都不安全 |

打个比方：

> 对称加密就像用同一把钥匙锁门和开门：
> - 你和朋友各有一把相同的钥匙
> - 你用钥匙锁门（加密），朋友用同一把钥匙开门（解密）
> - 问题：怎么把钥匙安全地交给朋友？如果钥匙在寄送过程中被复制，就完了

### 8.2.3 非对称加密

**非对称加密**有两把钥匙：**公钥**（公开的）和**私钥**（私密的）。

```
公钥加密 → 只有私钥能解密
私钥加密（签名） → 只有公钥能验证
```

**工作原理：**

```
发送方：明文 + 接收方的公钥 → 加密 → 密文
接收方：密文 + 自己的私钥 → 解密 → 明文
```

**常见的非对称加密算法：**

| 算法 | 密钥长度 | 安全性 | 速度 | 使用场景 |
| --- | --- | --- | --- | --- |
| RSA | 2048/4096 位 | 安全 | 慢 | 最常用 |
| ECC | 256 位 | 安全 | 较快 | 移动端常用 |
| DSA | 1024 位 | 一般 | 慢 | 数字签名 |

**非对称加密的优点和缺点：**

| 优点 | 缺点 |
| --- | --- |
| 密钥分发安全：公钥可以公开，私钥自己保存 | 速度慢，不适合加密大量数据 |
| 支持数字签名：可以验证身份 | 计算量大，消耗资源多 |

打个比方：

> 非对称加密就像信箱：
> - 公钥 = 信箱的投信口（任何人都可以投信）
> - 私钥 = 信箱的钥匙（只有你有，只有你能取信）
> - 你把公钥（投信口）告诉别人，别人用公钥加密信息投进去
> - 只有你有私钥（钥匙），只有你能解密取出信息

### 8.2.4 HTTPS 的加密过程

HTTPS 结合了对称加密和非对称加密的优点：

1. **TLS 握手阶段**：使用**非对称加密**安全地协商出一个**对称密钥**
2. **数据传输阶段**：使用**对称密钥**加密所有数据

```
TLS 握手（非对称加密）：
客户端 ←→ 服务器
- 协商加密算法
- 验证服务器证书
- 安全地生成对称密钥

数据传输（对称加密）：
客户端 → 服务器
- 所有数据都用对称密钥加密
- 速度快，安全
```

**为什么要这样设计？**

- 对称加密速度快，但密钥分发困难
- 非对称加密安全，但速度慢
- HTTPS 先用非对称加密安全地交换对称密钥，然后用对称加密传输数据
- 完美结合了两者的优点

打个比方：

> HTTPS 的加密过程就像见面：
> 1. 第一次见面（TLS 握手）：
>    - 你们用安全的方式（非对称加密）交换了一个暗号（对称密钥）
>    - 这个过程虽然慢，但很安全
> 2. 以后的交流（数据传输）：
>    - 你们都用这个暗号（对称加密）交流
>    - 速度快，而且只有你们俩懂

### 8.2.5 TLS 握手过程

TLS 握手是 HTTPS 的核心，它完成了三个任务：
1. 协商加密算法
2. 验证服务器身份
3. 生成对称密钥

**TLS 1.2 握手过程：**

```
客户端                         服务器
  |                              |
  |--- ClientHello ------------->|  第1步：客户端打招呼
  |   (支持的加密算法,            |  - 告诉服务器我支持哪些加密算法
  |    随机数1)                   |  - 发送一个随机数
  |                              |
  |<--- ServerHello -------------|  第2步：服务器回应
  |    (选择的加密算法,           |  - 选择一个加密算法
  |     随机数2)                  |  - 发送一个随机数
  |                              |
  |<--- Certificate -------------|  第3步：服务器发送证书
  |    (服务器证书)               |  - 包含服务器的公钥
  |                              |
  |<--- ServerKeyExchange -------|  第4步：服务器发送密钥参数（可选）
  |    (密钥交换参数)             |
  |                              |
  |<--- ServerHelloDone ---------|  第5步：服务器说完啦
  |                              |
  |--- ClientKeyExchange ------->|  第6步：客户端发送密钥参数
  |   (预主密钥)                  |  - 用服务器公钥加密的预主密钥
  |                              |
  |--- ChangeCipherSpec -------->|  第7步：客户端切换加密模式
  |                              |
  |--- Finished ---------------->|  第8步：客户端完成
  |   (握手验证)                  |
  |                              |
  |<--- ChangeCipherSpec --------|  第9步：服务器切换加密模式
  |                              |
  |<--- Finished ----------------|  第10步：服务器完成
  |   (握手验证)                  |
  |                              |
  |===== 加密通信开始 ============|  第11步：开始加密传输
  |                              |
```

**握手过程详解：**

**第1步：客户端打招呼（ClientHello）**
- 客户端告诉服务器：我支持哪些加密算法
- 发送一个随机数（Random1）
- 就像说："你好，我会说中文和英文，你呢？"

**第2步：服务器回应（ServerHello）**
- 服务器选择一个加密算法
- 发送一个随机数（Random2）
- 就像说："那我们用中文吧！"

**第3步：服务器发送证书（Certificate）**
- 服务器发送数字证书
- 证书里包含服务器的公钥
- 就像说："这是我的身份证（证书），上面有我的公开信息（公钥）"

**第4-5步：服务器发送密钥参数和完成**
- 如果需要，发送密钥交换参数
- 告诉客户端：我说完了

**第6步：客户端发送密钥参数（ClientKeyExchange）**
- 客户端生成一个**预主密钥**（Pre-Master Secret）
- 用服务器的公钥加密这个预主密钥
- 发送给服务器
- 只有服务器的私钥能解密

**第7-8步：客户端切换加密模式并完成**
- 客户端用三个随机数（Random1 + Random2 + Pre-Master Secret）计算出**对称密钥**
- 告诉服务器：我切换到加密模式了
- 发送 Finished 消息，用对称密钥加密

**第9-10步：服务器切换加密模式并完成**
- 服务器用自己的私钥解密得到预主密钥
- 用同样的三个随机数计算出**对称密钥**
- 告诉客户端：我也切换到加密模式了
- 发送 Finished 消息，用对称密钥加密

**第11步：开始加密传输**
- 双方都有了相同的对称密钥
- 后续所有数据都用这个对称密钥加密

**为什么需要三个随机数？**

```
对称密钥 = f(Random1, Random2, Pre-Master Secret)
```

- Random1 和 Random2 是明文的，可以被窃听
- Pre-Master Secret 是加密传输的，只有服务器能解密
- 即使攻击者知道了 Random1 和 Random2，没有 Pre-Master Secret 也算出对称密钥

### 8.2.6 数字证书

**数字证书**就像服务器的身份证，证明服务器的身份。

**证书包含的内容：**

| 内容 | 说明 | 类比 |
| --- | --- | --- |
| 域名 | 证书属于哪个域名 | 身份证上的姓名 |
| 公钥 | 服务器的公钥 | 身份证上的公开信息 |
| 颁发机构 | 谁颁发的证书（CA） | 发证机关（公安局） |
| 有效期 | 证书的有效时间 | 身份证的有效期 |
| 数字签名 | 颁发机构的签名 | 公章 |
| 其他信息 | 组织名称、地址等 | 民族、地址等 |

**证书链：**

```
根证书（Root CA）
  ↓（签发）
中间证书（Intermediate CA）
  ↓（签发）
服务器证书（Server Certificate）
```

- **根证书**：最顶层的证书，浏览器内置了可信的根证书
- **中间证书**：由根证书签发，可以签发服务器证书
- **服务器证书**：最终给网站使用的证书

**证书验证过程：**

```
1. 浏览器收到服务器证书
2. 检查证书是否过期
3. 检查证书是否被吊销
4. 验证证书链：
   - 服务器证书 ← 中间证书 ← 根证书
   - 每一级都用上一级的公钥验证签名
5. 验证域名是否匹配
6. 验证通过，信任服务器的公钥
```

打个比方：

> 证书验证就像验证身份证：
> 1. 检查身份证是否过期（有效期）
> 2. 检查身份证是否被挂失（吊销检查）
> 3. 验证身份证上的公章是真的（证书链验证）
> 4. 检查身份证上的名字是否和本人一致（域名匹配）
> 5. 验证通过，相信身份证上的信息

### 8.2.7 中间人攻击

**中间人攻击（Man-in-the-Middle Attack）** 是 HTTPS 要防范的主要攻击方式。

**攻击过程：**

```
客户端 ←→ 攻击者 ←→ 服务器
         （冒充服务器）
```

1. 客户端请求连接服务器
2. 攻击者拦截请求，冒充服务器
3. 攻击者生成假证书，发给客户端
4. 客户端以为是服务器，发送数据
5. 攻击者解密数据，再加密转发给服务器
6. 服务器以为是攻击者，返回数据
7. 攻击者解密数据，再加密转发给客户端

**HTTPS 如何防范中间人攻击？**

- 服务器发送真实的数字证书
- 浏览器验证证书链，确认证书是真的
- 如果证书是假的，浏览器会警告用户
- 攻击者无法伪造可信的证书（因为没有私钥）

## 8.3 基础用法 + 逐行注释

### 8.3.1 在浏览器中查看证书信息

```javascript
// 在浏览器中查看 HTTPS 证书信息

// 方法1：点击浏览器地址栏的锁图标
// - Chrome/Edge：点击地址栏左边的锁图标
// - Firefox：点击地址栏左边的锁图标
// - Safari：点击地址栏左边的锁图标

// 方法2：使用 JavaScript 获取证书信息
// 注意：出于安全考虑，JavaScript 无法直接获取证书详情
// 但可以通过 Performance API 查看 TLS 握手时间

// 获取页面加载的性能数据
const timing = performance.getEntriesByType('navigation')[0]

// 检查是否使用了 HTTPS
// secureConnectionStart > 0 表示使用了 HTTPS
if (timing.secureConnectionStart > 0) {
  console.log('✅ 当前页面使用了 HTTPS')
  
  // 查看 TLS 握手耗时
  const tlsTime = timing.connectEnd - timing.secureConnectionStart
  console.log(`TLS 握手耗时: ${tlsTime} 毫秒`)
} else {
  console.log('❌ 当前页面没有使用 HTTPS')
}

// 查看完整的加载时间线
console.log('--- 页面加载时间线 ---')
console.log(`DNS 查询: ${timing.domainLookupEnd - timing.domainLookupStart} 毫秒`)
console.log(`TCP 连接: ${timing.connectEnd - timing.connectStart} 毫秒`)
console.log(`TLS 握手: ${timing.connectEnd - timing.secureConnectionStart} 毫秒`)
console.log(`请求响应: ${timing.responseEnd - timing.requestStart} 毫秒`)
console.log(`总耗时: ${timing.loadEventEnd - timing.startTime} 毫秒`)
```

### 8.3.2 使用 Node.js 创建 HTTPS 服务器

```javascript
// Node.js 创建 HTTPS 服务器需要证书文件

// 引入必要的模块
const https = require('https')
const fs = require('fs')

// 读取证书文件
// cert.pem：服务器证书文件
// key.pem：服务器私钥文件
const options = {
  cert: fs.readFileSync('./cert.pem'),  // 读取证书
  key: fs.readFileSync('./key.pem')     // 读取私钥
}

// 创建 HTTPS 服务器
const server = https.createServer(options, (req, res) => {
  // req：请求对象
  // res：响应对象
  
  // 设置响应头
  res.writeHead(200, {
    'Content-Type': 'text/html; charset=utf-8'
  })
  
  // 发送响应内容
  res.end('<h1>你好，这是 HTTPS 服务器！</h1>')
})

// 监听 443 端口（HTTPS 默认端口）
server.listen(443, () => {
  console.log('✅ HTTPS 服务器启动成功')
  console.log('📍 访问地址: https://localhost')
})
```

```bash
# Let's Encrypt 提供免费的 SSL 证书

~/.acme.sh/acme.sh --installcert -d example.com -d www.example.com \

  --fullchain-file /etc/nginx/ssl/cert.pem \
  --reloadcmd "systemctl reload nginx"
```

### 8.3.4 Nginx 配置 HTTPS

```nginx
# Nginx 配置 HTTPS

# HTTP 重定向到 HTTPS
server {
    listen 80;                          # 监听 80 端口（HTTP）
    server_name example.com;            # 域名
    
    # 所有 HTTP 请求重定向到 HTTPS
    return 301 https://$server_name$request_uri;
}

# HTTPS 服务器
server {
    listen 443 ssl;                     # 监听 443 端口（HTTPS）
    server_name example.com;            # 域名
    
    # SSL 证书配置
    ssl_certificate /etc/nginx/ssl/cert.pem;        # 证书文件
    ssl_certificate_key /etc/nginx/ssl/key.pem;     # 私钥文件
    
    # SSL 协议配置（只允许安全的版本）
    ssl_protocols TLSv1.2 TLSv1.3;                  # 禁用旧版本
    
    # SSL 加密套件配置
    ssl_ciphers HIGH:!aNULL:!MD5;                   # 使用高强度加密
    
    # SSL 会话缓存（提高性能）
    ssl_session_cache shared:SSL:10m;               # 10MB 缓存
    ssl_session_timeout 10m;                        # 10 分钟超时
    
    # HSTS（HTTP Strict Transport Security）
    # 告诉浏览器只能用 HTTPS 访问
    add_header Strict-Transport-Security "max-age=31536000" always;
    
    # 网站根目录
    root /var/www/html;
    index index.html;
    
    # 默认路由
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### 8.3.5 在代码中强制使用 HTTPS

```javascript
// 确保应用只通过 HTTPS 访问

// 方法1：Express 中间件强制 HTTPS
const express = require('express')
const app = express()

// 检查是否使用 HTTPS
app.use((req, res, next) => {
  // 检查请求是否通过 HTTPS
  // req.secure 是 Express 提供的属性
  // 或者检查 X-Forwarded-Proto 头（反向代理场景）
  if (req.secure || req.headers['x-forwarded-proto'] === 'https') {
    // 已经是 HTTPS，继续处理
    next()
  } else {
    // 不是 HTTPS，重定向到 HTTPS
    res.redirect(`https://${req.headers.host}${req.url}`)
  }
})

// 方法2：设置安全响应头
app.use((req, res, next) => {
  // HSTS：告诉浏览器只能用 HTTPS 访问
  res.setHeader('Strict-Transport-Security', 'max-age=31536000; includeSubDomains')
  
  // 禁止被 iframe 嵌套（防止点击劫持）
  res.setHeader('X-Frame-Options', 'DENY')
  
  // 禁止浏览器猜测 MIME 类型
  res.setHeader('X-Content-Type-Options', 'nosniff')
  
  // 启用 XSS 过滤
  res.setHeader('X-XSS-Protection', '1; mode=block')
  
  next()
})

// 方法3：在 Vue/React 等前端项目中
// 确保所有 API 请求都使用 HTTPS
const API_BASE_URL = process.env.NODE_ENV === 'production'
  ? 'https://api.example.com'   // 生产环境用 HTTPS
  : 'http://localhost:3000'     // 开发环境用 HTTP

// 发起请求
fetch(`${API_BASE_URL}/users`, {
  method: 'GET',
  headers: {
    'Content-Type': 'application/json'
  }
})
```

## 8.4 对比表格

### 对称加密 vs 非对称加密

| 对比项 | 对称加密 | 非对称加密 |
| --- | --- | --- |
| 密钥数量 | 1 个（双方共享） | 2 个（公钥 + 私钥） |
| 加密速度 | 快 | 慢 |
| 安全性 | 密钥分发困难 | 密钥分发安全 |
| 适用场景 | 大量数据加密 | 密钥交换、数字签名 |
| 典型算法 | AES、DES、3DES | RSA、ECC、DSA |
| 在 HTTPS 中的作用 | 加密传输数据 | TLS 握手时交换密钥 |

### HTTP vs HTTPS

| 对比项 | HTTP | HTTPS |
| --- | --- | --- |
| 端口 | 80 | 443 |
| 加密 | 无（明文传输） | 有（SSL/TLS 加密） |
| 证书 | 不需要 | 需要（数字证书） |
| 安全性 | 不安全（可被窃听、篡改） | 安全（加密、完整性、身份验证） |
| 性能 | 快（无加密开销） | 稍慢（有握手和加密开销） |
| SEO | 一般 | 优先（搜索引擎 favor） |
| 浏览器标识 | 显示"不安全" | 显示锁图标 |
| 使用场景 | 内部网络、开发环境 | 生产环境、公网传输 |

### TLS 1.2 vs TLS 1.3

| 对比项 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 发布时间 | 2008 年 | 2018 年 |
| 握手时间 | 2-RTT（两次往返） | 1-RTT（一次往返）或 0-RTT |
| 安全性 | 安全 | 更安全（移除不安全算法） |
| 性能 | 一般 | 更快（握手更快） |
| 支持的算法 | 多（包括一些不安全的） | 少（只保留安全的） |
| 兼容性 | 好（所有现代浏览器） | 较好（新浏览器支持） |
| 推荐程度 | 可用 | 强烈推荐 |

## 8.5 新手常见误区

### 误区 1："HTTPS 是绝对安全的"

**不对。** HTTPS 不是绝对安全的，它只能保护传输过程中的数据安全。如果服务器本身被攻破、用户设备中了病毒、或者用户自己泄露了密码，HTTPS 也保护不了。HTTPS 只能防止数据在传输过程中被窃听和篡改。

```javascript
// 错误理解：
// ❌ 用了 HTTPS 就绝对安全了，不用管其他安全措施

// 正确理解：
// ✅ HTTPS 只保护传输安全
// ✅ 还需要：强密码、防火墙、定期更新、安全编码等
```

### 误区 2："HTTPS 比 HTTP 慢很多，影响性能"

**不对。** HTTPS 确实比 HTTP 慢一点（因为 TLS 握手），但现代优化技术已经大大减少了这个差距：

- TLS 1.3 的握手只需要 1 次往返（TLS 1.2 需要 2 次）
- 会话复用可以避免重复握手
- HTTP/2 和 HTTP/3 只在 HTTPS 下工作，性能更好
- 现代硬件加速了加密计算

实际测试中，HTTPS 的性能损失通常在 1% 以内，完全可以接受。

```javascript
// 错误理解：
// ❌ HTTPS 太慢了，还是用 HTTP 吧

// 正确理解：
// ✅ HTTPS 的性能损失很小（通常 < 1%）
// ✅ 现代优化技术（TLS 1.3、会话复用）大大减少了开销
// ✅ HTTP/2、HTTP/3 只在 HTTPS 下工作，性能更好
```

### 误区 3："自签名证书可以用在生产环境"

**不对。** 自签名证书没有被可信的 CA 机构验证，浏览器会显示安全警告。用户看到警告后通常会离开网站。自签名证书只适合开发测试环境，生产环境必须使用可信 CA 签发的证书。

```javascript
// 错误做法：
// ❌ 生产环境使用自签名证书
// ❌ 让用户忽略浏览器警告

// 正确做法：
// ✅ 开发环境可以用自签名证书
// ✅ 生产环境使用 Let's Encrypt（免费）或商业 CA 的证书
```

### 误区 4："只要用了 HTTPS，所有数据都安全"

**不完全对。** HTTPS 只保护传输过程中的数据，以下情况 HTTPS 保护不了：

- 服务器端的数据存储（数据库泄露）
- 用户设备的安全（中了病毒、键盘记录器）
- 用户自己泄露密码（钓鱼网站、社会工程学）
- 日志文件中记录的敏感信息
- 浏览器缓存中的数据

```javascript
// 错误理解：
// ❌ 用了 HTTPS，数据库可以存明文密码了

// 正确做法：
// ✅ HTTPS 保护传输安全
// ✅ 数据库存储要加密或哈希（如 bcrypt）
// ✅ 敏感信息不要记录在日志中
// ✅ 用户密码不要明文存储
```

### 误区 5："证书有效期越长越好"

**不对。** 证书有效期越长，风险越大：

- 私钥泄露后，攻击者可以使用更长时间
- 证书算法被破解后，影响范围更大
- 现代安全实践推荐短有效期 + 自动续期

Let's Encrypt 的证书有效期只有 90 天，但提供自动续期工具，既安全又方便。

```javascript
// 错误理解：
// ❌ 证书有效期越长越好，省得经常续期

// 正确理解：
// ✅ 短有效期更安全（减少风险窗口）
// ✅ 使用自动续期工具（如 certbot）
// ✅ Let's Encrypt 90 天有效期 + 自动续期是最佳实践
```

3. 数字签名验证身份
4. 加密数据库中的用户密码
5. HTTPS 数据传输阶段

<details>
<summary>点击查看答案</summary>

```
1. 加密一个 1GB 的视频文件
   答案：对称加密
   理由：视频文件数据量大，对称加密速度快，适合加密大量数据。
   推荐算法：AES-256

2. 在 TLS 握手中交换密钥
   答案：非对称加密
   理由：需要安全地交换对称密钥，非对称加密的公钥可以公开，私钥自己保存，密钥分发安全。
   推荐算法：RSA 或 ECC

3. 数字签名验证身份
   答案：非对称加密
   理由：数字签名需要用私钥签名，公钥验证，只有非对称加密支持这种机制。
   推荐算法：RSA 或 ECDSA

4. 加密数据库中的用户密码
   答案：不应该用加密，应该用哈希
   理由：密码不需要解密，应该用单向哈希（如 bcrypt、argon2）存储。
   如果必须加密（如需要解密），使用对称加密（AES-256）

5. HTTPS 数据传输阶段
   答案：对称加密
   理由：数据传输量大，需要快速加密解密，对称加密速度快。
   TLS 握手后双方已经有了相同的对称密钥。
   推荐算法：AES-128 或 AES-256
```

场景：用户在咖啡厅连接免费 WiFi，然后访问银行网站

请画出攻击过程，并说明 HTTPS 如何防范。

<details>
<summary>点击查看答案</summary>

```
场景分析：用户在咖啡厅连接免费 WiFi，访问银行网站

可能的攻击：

1. WiFi 热点本身是恶意的
   - 攻击者搭建了名为"Coffee_Shop_Free_WiFi"的假热点
   - 用户连接后，所有流量都经过攻击者

2. DNS 劫持
   - 攻击者篡改 DNS 解析
   - 用户访问 www.bank.com 被解析到攻击者的服务器

3. 中间人攻击过程：
   ```
   用户 ←→ 攻击者（假WiFi） ←→ 真实银行服务器
   ```
   - 用户请求连接银行服务器
   - 攻击者拦截请求
   - 攻击者冒充银行服务器，发送假证书
   - 用户浏览器验证证书失败，显示警告
   - 如果用户忽略警告继续访问，攻击成功

HTTPS 如何防范：

1. 证书验证
   - 银行服务器发送真实的数字证书
   - 攻击者无法伪造可信的证书（没有银行的私钥）
   - 浏览器验证证书失败，显示醒目的警告

2. HSTS（HTTP Strict Transport Security）
   - 银行网站设置了 HSTS 头
   - 浏览器记住只能用 HTTPS 访问
   - 即使用户输入 http://，也会自动跳转到 https://

3. 证书固定（Certificate Pinning）
   - 银行 App 可以内置银行证书的指纹
   - 即使系统信任了假证书，App 也会拒绝连接

用户应该如何防范：

1. 不要连接不明 WiFi
   - 使用手机流量更安全
   - 如果必须用 WiFi，向店员确认正确的热点名称

2. 不要忽略浏览器警告
   - 看到证书警告立即停止访问
   - 不要点击"继续访问"按钮

3. 检查地址栏
   - 确认域名正确（www.bank.com 而不是 www.bank-login.com）
   - 确认有锁图标
   - 点击锁图标查看证书信息

4. 使用银行官方 App
   - App 通常有证书固定，更安全
   - 不要在公共 WiFi 下进行敏感操作
```
