# 第十章：HTTP/2 与 HTTP/3

## 本章导读

在学这一章之前，你可能会有这些疑问：

- HTTP/1.1 有什么问题，为什么需要 HTTP/2？
- HTTP/2 的多路复用是怎么工作的？
- HTTP/3 又改进了什么？为什么基于 UDP？
- 我的网站需要升级到 HTTP/2 或 HTTP/3 吗？

这一章就是为了解答这些问题。我们会从 HTTP/1.1 的痛点开始，逐步学习 HTTP/2 和 HTTP/3 的核心特性。学完之后，你就能理解现代 Web 协议的优势，并知道如何升级你的网站。

---

## 10.1 为什么需要 HTTP/2 和 HTTP/3？

### 痛点分析：HTTP/1.1 的问题

想象一下这个场景：你打开一个网页，浏览器需要加载 50 个文件（HTML、CSS、JS、图片等）。在 HTTP/1.1 下，这些文件只能排队一个一个下载，就像超市只有一个收银台，所有顾客都要排队结账。

**HTTP/1.1 的主要问题：**

- 队头阻塞：同一连接同时只能处理一个请求，前面的请求没完成，后面的请求只能等着
- 头部冗余：每次请求都携带完整的头部，浪费带宽
- 文本传输：数据未压缩，传输效率低
- 无服务器推送：服务器不能主动推送资源，只能等客户端请求

**HTTP/1.1 时代的优化方案：**

为了缓解这些问题，开发者想出了很多办法：

- 精灵图（CSS Sprites）：把多张小图合成一张大图，减少请求数量
- 域名分片：使用多个域名，每个域名可以建立更多连接
- 长连接（Keep-Alive）：复用 TCP 连接，避免重复建立连接
- 管道化（Pipelining）：允许在前一个响应返回前发送下一个请求（但有队头阻塞问题）

这些方案都是治标不治本，直到 HTTP/2 出现。

打个比方：

> HTTP/1.1 就像单车道公路，一次只能过一辆车。HTTP/2 变成了多车道高速公路，可以多辆车并行。HTTP/3 更进一步，变成了高铁，不仅快，还能在行驶中切换轨道。

## 10.2 核心原理：HTTP/2 的四大特性

### 10.2.1 二进制分帧

HTTP/2 把 HTTP 消息分解成更小的二进制帧，就像把一封信拆分成多个信封和信纸：

```
HTTP/2 消息结构：

原始 HTTP/1.1 请求：
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html

HTTP/2 分帧后：
┌─────────────────┐
│ 帧 1：头部帧     │  ← 包含 Host、Accept 等头部
├─────────────────┤
│ 帧 2：数据帧     │  ← 包含请求体数据
├─────────────────┤
│ 帧 3：数据帧     │  ← 继续包含数据
├─────────────────┤
│ 帧 4：结束帧     │  ← 标记消息结束
└─────────────────┘
```

**优势：**

- 帧可以交错传输，不会互相阻塞
- 二进制格式更高效，易于解析
- 可以更精细地控制传输

### 10.2.2 多路复用

这是 HTTP/2 最重要的特性。一个 TCP 连接可以同时传输多个请求和响应，就像多车道高速公路：

| 特性 | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 请求方式 | 串行请求，排队等待 | 并行请求，同时传输 |
| 连接数量 | 需要多个连接（6-8 个） | 单个连接即可 |
| 队头阻塞 | 有，前面请求阻塞后面 | 无，各请求独立传输 |
| 性能 | 请求越多越慢 | 请求越多优势越明显 |

**工作原理：**

```
HTTP/1.1 串行传输：
连接 1：请求 A → 响应 A → 请求 B → 响应 B → 请求 C → 响应 C
（排队等待，慢）

HTTP/2 并行传输：
连接 1：请求 A → 请求 B → 请求 C
        响应 A → 响应 B → 响应 C
（同时传输，快）
```

### 10.2.3 头部压缩

HTTP/2 使用 HPACK 算法压缩头部，就像把重复的信息压缩成简短的代码：

**HPACK 的三个机制：**

1. 静态字典：预定义了常用的头部（如 `Content-Type`、`Accept`）
2. 动态字典：记录已经传输过的头部，下次只传输索引
3. 哈夫曼编码：对字符串进行压缩编码

**压缩效果：**

```
原始头部（HTTP/1.1）：
Content-Type: text/html
Accept: text/html
User-Agent: Mozilla/5.0
（约 200 字节）

压缩后（HTTP/2）：
索引 62，索引 15，索引 91
（约 20 字节，压缩率 90%）
```

### 10.2.4 服务器推送

HTTP/2 允许服务器主动推送资源，不用等客户端请求。就像餐厅在你点菜后，主动把餐具和纸巾一起送上来：

```http
# 服务器响应 HTML 时，主动推送 CSS 和 JS
HTTP/2 200 OK
Content-Type: text/html
Link: </style.css>; rel=preload; as=style
Link: </app.js>; rel=preload; as=script

# 客户端收到 HTML 后，CSS 和 JS 已经在缓存中了
```

**使用场景：**

- 推送 HTML 页面需要的 CSS 和 JS
- 推送首屏关键资源
- 推送预测用户可能需要的资源

### 10.2.5 请求优先级

客户端可以为请求设置优先级，让重要的资源先传输：

| 优先级 | 资源类型 | 说明 |
| --- | --- | --- |
| 最高 | HTML 文档 | 页面主体 |
| 高 | CSS、字体 | 影响页面渲染 |
| 中 | JavaScript | 交互逻辑 |
| 低 | 图片、视频 | 非关键资源 |

## 10.3 基础用法：配置和使用 HTTP/2

### 10.3.1 Nginx 配置 HTTP/2

```nginx
# 启用 HTTP/2 需要 HTTPS
server {
    # 监听 443 端口，启用 SSL 和 HTTP/2
    listen 443 ssl http2;
    
    # 域名
    server_name example.com;
    
    # SSL 证书路径
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    
    # SSL 配置
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
}

# HTTP 重定向到 HTTPS
server {
    listen 80;
    server_name example.com;
    return 301 https://$server_name$request_uri;
}
```

### 10.3.2 检测是否支持 HTTP/2

```javascript
// 方法 1：检查响应头
// 打开浏览器开发者工具，查看 Network 面板
// 如果协议显示为 h2，说明支持 HTTP/2

// 方法 2：使用 JavaScript 检测
async function checkHTTP2() {
  // 发送请求
  const response = await fetch('/');
  
  // 检查 alt-svc 头部（HTTP/3 升级提示）
  const altSvc = response.headers.get('alt-svc');
  console.log('Alt-Svc:', altSvc);
  
  // 注意：浏览器 API 无法直接获取 HTTP 版本
  // 需要通过开发者工具或服务器日志确认
}

checkHTTP2();
```

### 10.3.3 使用服务器推送

```javascript
// 服务器端（Node.js + Express）
const http2 = require('http2');
const fs = require('fs');

// 创建 HTTP/2 服务器
const server = http2.createSecureServer({
  key: fs.readFileSync('key.pem'),
  cert: fs.readFileSync('cert.pem')
});

// 处理请求
server.on('stream', (stream, headers) => {
  // 推送 CSS 文件
  const pushStream = stream.pushStream({ ':path': '/style.css' });
  
  // 读取并发送 CSS
  pushStream.respond({ ':status': 200 });
  pushStream.end(fs.readFileSync('style.css'));
  
  // 发送 HTML 响应
  stream.respond({
    ':status': 200,
    'content-type': 'text/html'
  });
  stream.end('<html>...</html>');
});

server.listen(443);
```

## 10.4 核心原理：HTTP/3 的革命性改进

### 10.4.1 基于 QUIC 协议

HTTP/3 最大的改变是底层传输协议从 TCP 变成了 QUIC（Quick UDP Internet Connections）。QUIC 基于 UDP，但实现了 TCP 的可靠性：

| 特性 | TCP | QUIC（HTTP/3） |
| --- | --- | --- |
| 传输层协议 | TCP | UDP |
| 握手时间 | 3 次握手（1.5 RTT） | 0-1 次握手（0-1 RTT） |
| 队头阻塞 | 有（TCP 层） | 无（独立流） |
| 连接迁移 | 不支持（基于 IP+端口） | 支持（基于 Connection ID） |
| 拥塞控制 | 操作系统内核实现 | 用户空间实现，可快速迭代 |
| 加密 | 可选（TLS） | 强制加密 |

**为什么基于 UDP？**

- TCP 在内核中实现，升级困难
- UDP 在用户空间实现，可以快速迭代
- UDP 更灵活，可以自定义传输逻辑

### 10.4.2 0-RTT 连接建立

HTTP/3 支持 0-RTT（零往返时间）连接建立，第一次请求就能立即发送数据：

```
HTTP/1.1 连接建立（慢）：
客户端                    服务器
  |                         |
  |--- SYN ---------------->|  第 1 次握手
  |<--- SYN-ACK ------------|
  |--- ACK ---------------->|  第 2 次握手（连接建立）
  |--- GET /index.html ---->|  第 3 次（发送请求）
  |<--- 200 OK -------------|  第 4 次（收到响应）
  |                         |
  总共需要 3 个 RTT

HTTP/2 连接建立（稍快）：
客户端                    服务器
  |                         |
  |--- TCP SYN + TLS ------>|  TCP + TLS 握手
  |<--- TCP SYN-ACK + TLS --|  （1.5 RTT）
  |--- ACK + GET ---------->|  发送请求（0.5 RTT）
  |<--- 200 OK -------------|  收到响应
  |                         |
  总共需要 2 个 RTT

HTTP/3 连接建立（最快）：
客户端                    服务器
  |                         |
  |--- Initial + Data ----->|  第一次请求（0 RTT）
  |<--- Initial + Data ------|  响应
  |                         |
  总共需要 1 个 RTT（首次连接）
  后续连接需要 0 个 RTT
```

**0-RTT 原理：**

- 首次连接后，服务器会发送配置信息
- 客户端缓存这些信息
- 后续连接时，客户端直接使用缓存的配置，无需等待服务器确认

### 10.4.3 连接迁移

HTTP/3 使用 Connection ID 标识连接，而不是 IP+端口。这意味着：

- WiFi 切换到 4G 时，连接不会断开
- 手机锁屏后再打开，连接可以恢复
- 不需要重新建立连接

**工作原理：**

```
传统 TCP 连接（基于 IP+端口）：
连接标识 = 客户端 IP + 客户端端口 + 服务器 IP + 服务器端口
WiFi 环境下：192.168.1.100:50000 + 服务器 IP:443
切换到 4G 后：10.0.0.100:60000 + 服务器 IP:443
→ IP 和端口都变了，连接断开

HTTP/3 连接（基于 Connection ID）：
连接标识 = Connection ID（如 "abc123"）
WiFi 环境下：Connection ID = "abc123"
切换到 4G 后：Connection ID = "abc123"
→ Connection ID 不变，连接继续
```

### 10.4.4 改进的拥塞控制

HTTP/3 的拥塞控制在用户空间实现，可以快速迭代和优化：

- 更精确的 RTT（往返时间）测量
- 更好的丢包恢复机制
- 可以根据网络状况快速调整

## 10.6 新手常见误区

### 误区 1："HTTP/2 完全解决了队头阻塞"

**错！** HTTP/2 只解决了 HTTP 层的队头阻塞，但 TCP 层仍有队头阻塞。如果 TCP 包丢失，整个连接都会阻塞。HTTP/3 基于 QUIC，才真正解决了队头阻塞。

### 误区 2："HTTP/2 不需要优化了"

**错！** HTTP/2 虽然快，但仍需要优化：

- 仍然需要减少请求数量
- 仍然需要压缩资源
- 仍然需要合理使用缓存

### 误区 3："HTTP/3 可以立即使用"

**不完全对！** HTTP/3 虽然已经标准化，但：

- 需要服务器支持（Nginx、Apache 等）
- 需要 CDN 支持
- 部分老旧浏览器不支持
- 防火墙可能拦截 UDP

建议：优先使用 HTTP/2，HTTP/3 作为补充。

### 误区 4："多路复用意味着不需要合并文件"

**错！** 虽然 HTTP/2 支持多路复用，但：

- 每个请求仍有开销
- 浏览器对并发连接数有限制
- 合并文件仍然能减少请求数量

建议：适度合并，不要过度拆分。

### 误区 5："HTTP/2 服务器推送一定好"

**不一定！** 服务器推送有缺点：

- 推送的资源可能已经在缓存中
- 推送会占用带宽
- 浏览器可能拒绝推送

建议：谨慎使用，只推送关键资源。

### 练习 3（挑战）：综合练习

请解释以下场景为什么 HTTP/3 比 HTTP/2 更适合：

```
场景：用户在地铁里使用手机浏览网页
- 地铁经过隧道时信号变弱
- 手机在 WiFi 和 4G 之间切换
- 网络延迟较高，丢包率较高
```

<details>
<summary>点击查看答案</summary>

```
HTTP/3 的优势：

1. 连接迁移
   - WiFi 切换到 4G 时，HTTP/2 连接会断开
   - HTTP/3 使用 Connection ID，连接不会断开

2. 0-RTT 连接建立
   - 信号恢复后，HTTP/2 需要重新握手（1.5 RTT）
   - HTTP/3 可以 0-RTT 恢复连接，立即发送请求

3. 无 TCP 队头阻塞
   - 丢包率高时，HTTP/2 的 TCP 层会阻塞整个连接
   - HTTP/3 的 QUIC 流独立，一个流丢包不影响其他流

4. 更好的拥塞控制
   - HTTP/3 的拥塞控制在用户空间，可以快速调整
   - 适合高延迟、高丢包的网络环境

结论：移动网络环境下，HTTP/3 能提供更好的用户体验。
```

</details>
