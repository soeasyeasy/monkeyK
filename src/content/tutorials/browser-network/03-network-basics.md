# 第三章：网络基础概念

## 本章导读

在开始学习网络知识之前，你可能会有这些疑问：

- 浏览器是怎么从服务器获取数据的？网络通信到底是怎么回事？
- 什么是 IP 地址、端口、协议？这些概念跟我写代码有什么关系？
- 为什么网络要分层？OSI 七层模型和 TCP/IP 四层模型是什么？
- 数据从我的电脑发到服务器，中间经历了什么过程？

这一章会带你搞懂网络通信的基础原理。我们会从最经典的"客户端-服务器模型"讲起，了解网络协议为什么要分层，数据是怎么一层层"打包"发送出去的。理解了这些，你才能明白 HTTP 协议为什么这样设计，也能更好地调试网络问题。

---

## 3.1 为什么需要了解网络基础？

### 痛点分析

很多前端开发者会遇到这些问题：

- 接口请求失败了，报了一个"网络错误"，但不知道问题出在哪里
- 面试官问"TCP 三次握手是什么"，你完全懵了
- 看到 HTTP 状态码 404、500，只知道是"出错了"，不知道具体原因
- 调试跨域问题时，对"同源策略"一知半解

这些问题的根源，都在于对网络基础知识不了解。不懂网络，就像快递员不知道物流流程——包裹丢了，完全不知道去哪找。

### 了解网络的价值

打个比方：你每天用手机点外卖，从下单到收到餐，中间经历了什么？

1. 你在 APP 上下单（客户端发起请求）
2. 订单传到商家（网络传输）
3. 商家接单做菜（服务器处理）
4. 骑手取餐送餐（网络传输）
5. 你收到外卖（客户端接收响应）

网络通信也是一样的道理。浏览器是"你"，服务器是"商家"，网络是"骑手"。了解这个过程，你就能在"外卖丢了"的时候，知道该找谁——是下单时出了问题，还是骑手送错了，还是商家根本没做。

> 一句话总结：了解网络基础，不是为了当网络工程师，而是为了在出问题时知道问题出在哪一层。

## 3.2 核心原理：客户端-服务器模型

### 什么是客户端-服务器模型？

网络通信的基础是**客户端-服务器模型**（Client-Server Model）。这个模型很简单：

- **客户端**：发起请求的一方，比如你的浏览器
- **服务器**：接收请求并返回响应的一方，比如网站的后台程序

打个比方：你去餐厅吃饭，你是"客户端"，服务员是"服务器"。你点菜（发请求），服务员把菜端给你（返回响应）。

### 请求-响应流程

一次完整的网络通信，要经过以下步骤：

| 步骤 | 谁在做 | 做什么 | 类比 |
| --- | --- | --- | --- |
| 1 | 客户端 | 建立连接 | 打电话给餐厅 |
| 2 | 客户端 | 发送请求 | 告诉服务员要吃什么菜 |
| 3 | 服务器 | 接收请求 | 服务员记下你的订单 |
| 4 | 服务器 | 处理请求 | 厨师做菜 |
| 5 | 服务器 | 返回响应 | 服务员把菜端给你 |
| 6 | 客户端 | 接收响应 | 你收到菜，开始吃 |
| 7 | 双方 | 关闭连接 | 吃完饭，挂电话 |

### 客户端和服务器的角色对比

| 对比项 | 客户端 | 服务器 |
| --- | --- | --- |
| 角色 | 请求方 | 响应方 |
| 主动性 | 主动发起请求 | 被动等待请求 |
| 典型代表 | 浏览器、手机 APP | Web 服务器、API 服务器 |
| 数量 | 可以有很多个 | 通常集中部署 |
| 运行环境 | 用户设备上 | 数据中心/云服务器 |

## 3.3 网络协议分层：为什么要分层？

### 痛点：如果网络不分层会怎样？

想象一下，如果网络通信不分层，你要写一个网页聊天程序，需要自己处理所有事情：

- 怎么把数据变成电信号发出去？
- 怎么保证数据不丢包、不乱序？
- 怎么找到对方的电脑？
- 怎么把文字显示在屏幕上？

这就像让你一个人同时当厨师、服务员、清洁工、收银员——累死了还容易出错。

### 解决方案：分层设计

网络协议采用**分层设计**，每一层只负责一件事，层与层之间通过接口协作。这样每一层都可以独立开发、独立升级，互不影响。

打个比方：物流公司分层工作：

- 前台：接待客户，接单（应用层）
- 调度：规划路线，分配车辆（传输层）
- 司机：开车送货（网络层）
- 修路工：维护道路（数据链路层）
- 道路本身：物理基础设施（物理层）

每一层只关心自己的事，前台不需要知道路怎么修，司机不需要知道客户是谁。

### OSI 七层模型

OSI（Open System Interconnection）是一个理论上的七层模型，帮助我们理解网络通信的每个环节：

| 层次 | 名称 | 职责 | 生活类比 | 协议示例 |
| --- | --- | --- | --- | --- |
| 7 | 应用层 | 提供用户接口，处理具体应用 | 你在 APP 上点外卖 | HTTP、FTP、SMTP |
| 6 | 表示层 | 数据格式转换、加密解密 | 把中文翻译成英文 | SSL/TLS |
| 5 | 会话层 | 管理会话，保持连接 | 记住你是哪个用户 | NetBIOS |
| 4 | 传输层 | 端到端通信，保证可靠性 | 快递员保证包裹送达 | TCP、UDP |
| 3 | 网络层 | 路由选择，找到目标地址 | 导航系统规划路线 | IP、ICMP |
| 2 | 数据链路层 | 帧传输，错误检测 | 公路上的车辆行驶 | Ethernet、Wi-Fi |
| 1 | 物理层 | 比特流传输，物理介质 | 公路、光纤本身 | 光纤、电缆 |

### TCP/IP 四层模型

OSI 七层太复杂了，实际应用中用的是简化的**TCP/IP 四层模型**：

```
应用层      ← HTTP、FTP、DNS（对应 OSI 的应用层+表示层+会话层）
传输层      ← TCP、UDP（对应 OSI 的传输层）
网络层      ← IP、ICMP（对应 OSI 的网络层）
网络接口层  ← Ethernet、Wi-Fi（对应 OSI 的数据链路层+物理层）
```

### OSI 七层 vs TCP/IP 四层对比

| 对比项 | OSI 七层模型 | TCP/IP 四层模型 |
| --- | --- | --- |
| 层数 | 7 层 | 4 层 |
| 复杂度 | 理论完善，但复杂 | 简化实用，广泛使用 |
| 实际应用 | 教学参考 | 实际标准 |
| 应用层 | 应用层+表示层+会话层 | 合并为一个应用层 |
| 网络接口层 | 数据链路层+物理层 | 合并为一个网络接口层 |

> 实际开发中，我们主要关注**应用层**（HTTP）和**传输层**（TCP/UDP），其他层由操作系统和网络设备处理。

## 3.4 数据封装：数据是怎么发送出去的？

### 什么是数据封装？

当你在浏览器里输入一个网址，数据不是一次性发出去的，而是**每一层都会加上自己的"包装"**，这个过程叫数据封装。

打个比方：你要寄一封信给朋友：

1. 你写好信的内容（应用层数据）
2. 装进信封，写上收件人名字（传输层加头部）
3. 信封外再套一个快递袋，写上地址（网络层加头部）
4. 快递袋贴上条形码，交给快递公司（数据链路层加头部）
5. 快递公司把包裹放上货车运走（物理层传输）

### 封装过程详解

```
应用层数据： "Hello, Server!"
    ↓
添加传输层头部（TCP/UDP）→ 段（Segment）
    [TCP 头部: 源端口 12345, 目标端口 80, 序列号...]
    + "Hello, Server!"
    ↓
添加网络层头部（IP）→ 包（Packet）
    [IP 头部: 源 IP 192.168.1.100, 目标 IP 8.8.8.8...]
    + [TCP 头部] + "Hello, Server!"
    ↓
添加数据链路层头部 → 帧（Frame）
    [MAC 头部: 源 MAC aa:bb:cc, 目标 MAC dd:ee:ff...]
    + [IP 头部] + [TCP 头部] + "Hello, Server!"
    ↓
转换为比特流传输 → 0101010111010101...
```

### 解封装过程

接收端收到数据后，按相反顺序"拆包装"：

| 步骤 | 哪一层 | 做什么 | 类比 |
| --- | --- | --- | --- |
| 1 | 物理层 | 接收比特流，转换成电信号 | 收到快递包裹 |
| 2 | 数据链路层 | 去除帧头部，检查错误 | 拆掉快递袋，检查有没有破损 |
| 3 | 网络层 | 去除 IP 头部，确认目标地址 | 拆掉信封，确认是寄给自己的 |
| 4 | 传输层 | 去除 TCP/UDP 头部，重组数据 | 打开信封，取出信纸 |
| 5 | 应用层 | 获取原始数据，交给应用程序 | 读信的内容 |

### 每一层的数据单位

| 层次 | 数据单位 | 说明 |
| --- | --- | --- |
| 应用层 | 消息（Message） | 原始数据 |
| 传输层 | 段（Segment） | TCP 叫段，UDP 叫数据报 |
| 网络层 | 包（Packet） | IP 数据包 |
| 数据链路层 | 帧（Frame） | 以太网帧 |
| 物理层 | 比特（Bit） | 0 和 1 |

## 3.5 网络地址：IP 地址和端口号

### IP 地址是什么？

IP 地址是网络中设备的"门牌号"，用于唯一标识一台设备。就像你家的地址是"XX 省 XX 市 XX 路 XX 号"，IP 地址告诉网络"数据该发给谁"。

### IPv4 vs IPv6 对比

| 对比项 | IPv4 | IPv6 |
| --- | --- | --- |
| 地址长度 | 32 位 | 128 位 |
| 格式 | 点分十进制 | 冒号十六进制 |
| 示例 | 192.168.1.1 | 2001:0db8:85a3::8a2e:0370:7334 |
| 地址数量 | 约 43 亿个 | 几乎无限 |
| 现状 | 即将耗尽 | 正在推广 |

### 端口号是什么？

一台电脑可以同时运行多个服务（Web 服务器、数据库、邮件服务器等），端口号用于区分这些服务。就像一栋大楼有很多房间，IP 地址是大楼的地址，端口号是房间号。

### 端口号分类

| 端口范围 | 用途 | 示例 |
| --- | --- | --- |
| 0-1023 | 知名端口（系统保留） | HTTP:80, HTTPS:443, SSH:22 |
| 1024-49151 | 注册端口（应用程序使用） | MySQL:3306, Redis:6379 |
| 49152-65535 | 动态端口（临时分配） | 客户端随机使用 |

### 常见服务端口速查表

| 服务 | 端口 | 协议 | 说明 |
| --- | --- | --- | --- |
| HTTP | 80 | TCP | 网页浏览（未加密） |
| HTTPS | 443 | TCP | 网页浏览（加密） |
| FTP | 21 | TCP | 文件传输 |
| SSH | 22 | TCP | 远程登录 |
| SMTP | 25 | TCP | 发送邮件 |
| DNS | 53 | UDP/TCP | 域名解析 |

## 3.6 基础用法：用代码验证网络概念

### 查看本机 IP 地址

```javascript
// 在浏览器控制台执行以下代码

// 方法 1：使用 RTCPeerConnection 获取本地 IP
// 这是一种常用的技术手段，通过 WebRTC 获取本机 IP
const pc = new RTCPeerConnection({
  // 配置 ICE 服务器，用于获取网络信息
  iceServers: []
});

// 创建一个数据通道，触发 ICE 候选收集
pc.createDataChannel('');

// 监听 ICE 候选事件，从中提取 IP 地址
pc.onicecandidate = (event) => {
  // 当候选收集完成时，event.candidate 为 null
  if (!event.candidate) {
    // 输出所有找到的 IP 地址
    console.log('本机 IP 地址:', pc.localDescription);
    // 关闭连接，释放资源
    pc.close();
    return;
  }
  
  // 从候选字符串中提取 IP 地址
  // candidate 格式: "candidate:xxx 1 udp xxx xxx.local xxxxx typ host"
  const candidate = event.candidate.candidate;
  // 使用正则匹配 IP 地址部分
  const ipMatch = candidate.match(/(\d+\.\d+\.\d+\.\d+)/);
  if (ipMatch) {
    // 输出找到的 IP 地址
    console.log('找到 IP:', ipMatch[1]);
  }
};
```

### 使用 fetch 验证请求-响应流程

```javascript
// 使用 fetch API 发起一个 HTTP 请求
// 这是前端最常用的网络请求方式

// 发起 GET 请求到指定 URL
fetch('https://jsonplaceholder.typicode.com/posts/1')
  // 第一个 then：接收响应，转换为 JSON 格式
  .then(response => {
    // 检查响应状态码，200-299 表示成功
    if (!response.ok) {
      // 如果状态码不在成功范围，抛出错误
      throw new Error(`HTTP 错误! 状态码: ${response.status}`);
    }
    // 将响应体解析为 JSON 对象
    return response.json();
  })
  // 第二个 then：处理解析后的数据
  .then(data => {
    // 在控制台输出获取到的数据
    console.log('获取到的数据:', data);
    // 输出示例: { userId: 1, id: 1, title: "...", body: "..." }
  })
  // catch：捕获并处理错误
  .catch(error => {
    // 输出错误信息
    console.error('请求失败:', error);
    // 常见错误：网络断开、跨域问题、服务器错误等
  });
```

### 使用 XMLHttpRequest 查看请求细节

```javascript
// XMLHttpRequest 是更底层的请求方式，能看到更多细节

// 创建 XMLHttpRequest 对象
const xhr = new XMLHttpRequest();

// 配置请求：方法、URL、是否异步
// 第三个参数 true 表示异步请求，不会阻塞页面
xhr.open('GET', 'https://jsonplaceholder.typicode.com/posts/1', true);

// 监听请求状态变化
xhr.onreadystatechange = function() {
  // readyState 表示请求状态
  // 0: 未初始化  1: 已打开  2: 已发送  3: 接收中  4: 完成
  if (xhr.readyState === 4) {
    // 状态码 200 表示请求成功
    if (xhr.status === 200) {
      // 输出响应头信息
      console.log('响应头:', xhr.getAllResponseHeaders());
      // 输出响应体
      console.log('响应数据:', JSON.parse(xhr.responseText));
    } else {
      // 输出错误状态码
      console.error('请求失败，状态码:', xhr.status);
    }
  }
};

// 监听进度事件（可选）
xhr.onprogress = function(event) {
  // 如果知道总长度，可以计算下载进度
  if (event.lengthComputable) {
    // 计算百分比
    const percent = (event.loaded / event.total) * 100;
    // 输出进度信息
    console.log(`下载进度: ${percent.toFixed(2)}%`);
  }
};

// 发送请求
xhr.send();
```

## 3.8 新手常见误区

### 误区 1："IP 地址和 MAC 地址是一回事"

**错！** IP 地址是逻辑地址，可以改变（比如你换个 Wi-Fi，IP 就变了）。MAC 地址是物理地址，烧录在网卡上，一般不会变。

打个比方：IP 地址像你的收货地址（可以改），MAC 地址像你的身份证号（基本不变）。网络通信时，IP 地址用于找到目标网络，MAC 地址用于在局域网内找到具体设备。

正确做法：理解两者的区别，IP 用于跨网络定位，MAC 用于局域网内定位。

### 误区 2："TCP 和 UDP 差不多，随便用"

**错！** 两者差别很大：

- TCP：可靠传输，保证数据不丢包、不乱序，但速度慢（HTTP、HTTPS 用 TCP）
- UDP：不可靠传输，可能丢包，但速度快（视频直播、在线游戏用 UDP）

打个比方：TCP 像顺丰快递，保证送达但慢；UDP 像扔飞盘，快但可能扔偏。

正确做法：需要可靠传输用 TCP（文件下载、网页浏览），追求速度用 UDP（视频通话、游戏）。

### 误区 3："网络分层只是理论，实际用不到"

**错！** 网络分层跟你的开发工作密切相关：

- 应用层：你写的 HTTP 请求代码
- 传输层：TCP 三次握手影响连接建立速度
- 网络层：IP 地址、DNS 解析
- 数据链路层：MAC 地址、局域网通信

调试网络问题时，分层思维能帮你快速定位问题出在哪一层。

正确做法：遇到网络问题，从应用层开始逐层排查。

### 误区 4："端口号可以随便用"

**错！** 端口号有明确分类：

- 0-1023：系统保留，普通程序不能用（需要管理员权限）
- 1024-49151：注册端口，建议用这些（比如 3000、8080）
- 49152-65535：动态端口，系统自动分配

如果用了知名端口（比如 80），可能跟系统服务冲突。

正确做法：开发时用 3000、8080 等注册端口，避免用 0-1023 的端口。

### 练习 2（进阶）：理解数据封装

假设你要发送一条消息 "Hello" 到服务器（IP: 8.8.8.8，端口: 80），你的电脑 IP 是 192.168.1.100。请写出每一层封装后的数据格式。

<details>
<summary>点击查看答案</summary>

**封装过程**：

1. **应用层**：原始数据
```
"Hello"
```

2. **传输层**：添加 TCP 头部
```
[TCP 头部: 源端口 12345, 目标端口 80, 序列号 1, 确认号 0]
+ "Hello"
= 段（Segment）
```

3. **网络层**：添加 IP 头部
```
[IP 头部: 源 IP 192.168.1.100, 目标 IP 8.8.8.8, TTL 64]
+ [TCP 头部] + "Hello"
= 包（Packet）
```

4. **数据链路层**：添加帧头部和尾部
```
[帧头部: 源 MAC aa:bb:cc:dd:ee:ff, 目标 MAC 11:22:33:44:55:66]
+ [IP 头部] + [TCP 头部] + "Hello"
+ [帧尾部: FCS 校验码]
= 帧（Frame）
```

5. **物理层**：转换为比特流
```
010101011101010100110011...（电信号/光信号）
```

### 练习 3（挑战）：网络分层故障排查

场景：用户反馈"网页打不开"，请你用分层思维排查问题。请按照从应用层到物理层的顺序，列出可能的故障点和检查方法。

<details>
<summary>点击查看答案</summary>

**分层排查思路**：

| 层次 | 可能故障 | 检查方法 |
| --- | --- | --- |
| 应用层 | 浏览器设置错误、DNS 配置错误 | 换个浏览器试试；检查 DNS 设置 |
| 传输层 | 防火墙拦截、端口被封 | 检查防火墙规则；尝试 telnet 端口 |
| 网络层 | IP 冲突、路由错误、DNS 解析失败 | ping 目标 IP；检查路由表 |
| 数据链路层 | 网卡驱动问题、MAC 地址冲突 | 检查设备管理器；更换网卡 |
| 物理层 | 网线松动、Wi-Fi 信号弱 | 检查网线连接；靠近路由器 |

**实际排查步骤**：

1. 先 ping 127.0.0.1（测试本机 TCP/IP 协议栈）
2. 再 ping 网关 IP（测试局域网连通性）
3. 然后 ping 8.8.8.8（测试外网连通性）
4. 最后 ping www.baidu.com（测试 DNS 解析）

根据哪一步失败，就能定位问题出在哪一层。

</details>
