# 第七章：TCP/IP 协议栈

## 本章导读

在学这一章之前，你可能会有这些疑问：

- 浏览器拿到服务器 IP 之后，是怎么和服务器建立连接的？为什么叫"三次握手"？
- TCP 和 UDP 有什么区别？为什么视频通话用 UDP，而网页浏览用 TCP？
- 为什么关闭连接要"四次挥手"，不能像建立连接那样三次搞定？
- 数据在网络中传输时，怎么保证不丢包、不乱序？

这一章就是为了解答这些问题。我们会从 TCP/IP 协议栈的基本结构讲起，深入理解三次握手和四次挥手的原理，搞清楚 TCP 是怎么保证数据可靠传输的。学完这章，你就能理解网络通信的底层机制了。

---

## 1 为什么需要 TCP/IP？

### 没有 TCP/IP 的时候有多混乱

想象一下，你要寄一封重要的信件给朋友。如果没有邮政系统，你只能自己跑到朋友家把信交给他。如果朋友不在家，你就得等，或者改天再来。如果路上遇到堵车，信可能会迟到，甚至丢失。

互联网也是这样。如果没有一套规则来管理数据的传输，数据可能会丢失、重复、乱序，甚至送到错误的地方。TCP/IP 协议栈就是互联网的"邮政系统"，它规定了数据怎么打包、怎么传输、怎么确认收到、怎么处理异常。

打个比方：

> TCP/IP 就像快递系统：
> - IP 协议负责"地址"——每个包裹都要写上收发双方的地址（IP 地址）
> - TCP 协议负责"可靠"——保证包裹不丢、不乱、按顺序到达
> - 端口号就像"门牌号"——同一台服务器上不同的服务用不同的端口
> - 三次握手就像"打电话前确认"——"喂，能听到吗？""能听到，你呢？""我也能听到，那开始聊吧"

没有 TCP/IP，网络通信就像没有邮政系统的寄信，完全靠运气。

## 2 核心原理

### 7.2.1 TCP/IP 协议栈的四层结构

TCP/IP 不是一个协议，而是一组协议的集合，按照功能分成四层：

| 层次 | 做什么用 | 代表协议 | 生活类比 |
| --- | --- | --- | --- |
| 应用层 | 提供用户服务（网页、邮件、文件传输） | HTTP、HTTPS、FTP、DNS、SMTP | 写信的内容（你写的是什么） |
| 传输层 | 保证端到端的可靠传输 | TCP、UDP | 快递公司的服务（保证包裹安全到达） |
| 网络层 | 负责路由选择，找到最佳路径 | IP、ICMP、ARP | 快递的路线规划（走哪条路最快） |
| 网络接口层 | 负责物理传输（网线、Wi-Fi） | Ethernet、Wi-Fi、PPP | 快递车（实际运输工具） |

打个比方：

> 你从北京寄一个包裹到上海：
> - 应用层 = 包裹里的内容（你写了一封信）
> - 传输层 = 快递公司的服务（保证包裹不丢，按顺序送到）
> - 网络层 = 路线规划（从北京走高速到上海）
> - 网络接口层 = 快递车（实际运输工具）

### 7.2.2 TCP vs UDP

TCP 和 UDP 是传输层的两个协议，它们的特点完全不同：

| 特性 | TCP | UDP | 生活类比 |
| --- | --- | --- | --- |
| 连接方式 | 面向连接（先建立连接再传输） | 无连接（直接发送） | TCP = 打电话（先拨号接通）<br>UDP = 发广播（直接喊） |
| 可靠性 | 可靠传输（保证不丢、不乱序） | 不可靠（可能丢包、乱序） | TCP = 挂号信（有回执）<br>UDP = 平信（没回执） |
| 顺序保证 | 保证顺序（按发送顺序接收） | 不保证顺序 | TCP = 排队进场<br>UDP = 各自进场 |
| 流量控制 | 有（根据接收方能力调整速度） | 无（想发多快发多快） | TCP = 看对方消化能力<br>UDP = 不管对方能不能接住 |
| 拥塞控制 | 有（网络拥堵时减速） | 无（不管网络堵不堵） | TCP = 堵车时慢行<br>UDP = 堵车也照开 |
| 传输速度 | 较慢（有握手、确认、重传开销） | 较快（没有这些开销） | TCP = 快递（要签收）<br>UDP = 外卖（放下就走） |
| 头部开销 | 20 字节（信息多） | 8 字节（信息少） | TCP = 详细的快递单<br>UDP = 简单的标签 |
| 应用场景 | 网页浏览、文件传输、邮件 | 视频通话、在线游戏、DNS 查询 | TCP = 重要文件<br>UDP = 实时聊天 |

### 7.2.3 TCP 三次握手

建立 TCP 连接需要三次握手，这个过程就像两个人打电话前的确认：

```
客户端                    服务器
  |                         |
  |--- SYN (seq=x) -------->|  第一次握手：客户端说"我想和你聊天"
  |                         |
  |<-- SYN+ACK (seq=y,      |  第二次握手：服务器说"好的，我听到了"
  |    ack=x+1) ------------|
  |                         |
  |--- ACK (ack=y+1) ------>|  第三次握手：客户端说"我也听到你了，开始吧"
  |                         |
  |===== 连接建立 ==========|
```

**三次握手的详细过程：**

1. **第一次握手（客户端 → 服务器）**：
   - 客户端发送一个 SYN 包（SYN = Synchronize，同步序列号）
   - 包里有客户端的初始序列号 `x`
   - 客户端进入 `SYN_SENT` 状态（等待服务器响应）

2. **第二次握手（服务器 → 客户端）**：
   - 服务器收到 SYN 包，回复一个 SYN+ACK 包
   - SYN 包里有服务器的初始序列号 `y`
   - ACK 包确认收到客户端的 SYN，确认号是 `x+1`
   - 服务器进入 `SYN_RCVD` 状态（等待客户端确认）

3. **第三次握手（客户端 → 服务器）**：
   - 客户端收到 SYN+ACK 包，回复一个 ACK 包
   - ACK 包确认收到服务器的 SYN，确认号是 `y+1`
   - 客户端进入 `ESTABLISHED` 状态（连接已建立）
   - 服务器收到 ACK 后也进入 `ESTABLISHED` 状态

**为什么需要三次握手？**

- **防止历史连接**：如果网络中有一个延迟的旧 SYN 包到达服务器，服务器会误以为是一个新连接。三次握手可以让客户端确认这个连接是否真的有效。
- **双方确认能力**：三次握手确保双方都能正常发送和接收数据。客户端确认服务器能收到自己的数据，服务器确认客户端能收到自己的数据。
- **同步序列号**：双方交换初始序列号，后续的数据传输都基于这些序列号进行排序。

打个比方：

> 三次握手就像打电话：
> 1. 你："喂，能听到吗？"（SYN）
> 2. 对方："能听到，你呢？"（SYN+ACK）
> 3. 你："我也能听到，那开始聊吧"（ACK）
> 
> 如果只有两次握手：
> 1. 你："喂，能听到吗？"（SYN）
> 2. 对方："能听到"（ACK）
> 
> 问题：你不知道对方能不能听到你说话。三次握手解决了这个问题。

### 7.2.4 TCP 四次挥手

断开 TCP 连接需要四次挥手，这个过程比建立连接多一次：

```
客户端                    服务器
  |                         |
  |--- FIN (seq=u) -------->|  第一次挥手：客户端说"我说完了"
  |                         |
  |<-- ACK (ack=u+1) -------|  第二次挥手：服务器说"好的，我知道了"
  |                         |
  |===== 客户端进入 FIN-WAIT-2 =====|
  |                         |
  |<-- FIN (seq=w) ---------|  第三次挥手：服务器说"我也说完了"
  |                         |
  |--- ACK (ack=w+1) ------>|  第四次挥手：客户端说"好的，那挂了吧"
  |                         |
  |===== 连接关闭 ==========|
```

**四次挥手的详细过程：**

1. **第一次挥手（客户端 → 服务器）**：
   - 客户端发送 FIN 包（FIN = Finish，结束）
   - 表示客户端没有数据要发送了
   - 客户端进入 `FIN_WAIT_1` 状态

2. **第二次挥手（服务器 → 客户端）**：
   - 服务器收到 FIN 包，回复 ACK 包
   - 确认号是 `u+1`，表示收到客户端的 FIN
   - 服务器进入 `CLOSE_WAIT` 状态
   - 客户端收到 ACK 后进入 `FIN_WAIT_2` 状态
   - **注意**：此时服务器可能还有数据要发送，所以连接是半关闭状态

3. **第三次挥手（服务器 → 客户端）**：
   - 服务器发送完所有剩余数据后，发送 FIN 包
   - 表示服务器也没有数据要发送了
   - 服务器进入 `LAST_ACK` 状态

4. **第四次挥手（客户端 → 服务器）**：
   - 客户端收到 FIN 包，回复 ACK 包
   - 确认号是 `w+1`，表示收到服务器的 FIN
   - 客户端进入 `TIME_WAIT` 状态
   - 服务器收到 ACK 后进入 `CLOSED` 状态
   - 客户端等待 2MSL（Maximum Segment Lifetime，最大报文段生存时间）后进入 `CLOSED` 状态

**为什么需要四次挥手？**

- **全双工通信**：TCP 是全双工的，双方都可以发送和接收数据。关闭连接时，每个方向需要单独关闭。
- **服务器可能还有数据**：客户端说"我说完了"，但服务器可能还有数据要发送。所以服务器先确认收到，等数据发送完后再发送自己的 FIN。
- **确保双方都正常关闭**：四次挥手确保双方都知道对方已经关闭连接。

打个比方：

> 四次挥手就像挂电话：
> 1. 你："我说完了"（FIN）
> 2. 对方："好的，我知道了"（ACK）
> 3. 对方等一会儿，然后："我也说完了"（FIN）
> 4. 你："好的，那挂了吧"（ACK）
> 
> 为什么不能三次？因为对方可能还有话要说，不能你说完了就立刻挂断。

### 7.2.5 TCP 可靠传输机制

TCP 通过多种机制保证数据的可靠传输：

| 机制 | 做什么用 | 生活类比 |
| --- | --- | --- |
| 序列号 | 给每个数据段编号，保证顺序 | 给每页信纸编号（1、2、3...） |
| 确认号 | 确认收到数据，告诉对方下一个期望的编号 | "我收到第1页了，请发第2页" |
| 超时重传 | 超时没收到确认，重新发送 | 寄信后没收到回信，再寄一次 |
| 滑动窗口 | 控制发送速度，提高传输效率 | 根据对方消化能力调整发送速度 |
| 流量控制 | 接收方告诉发送方自己的接收能力 | "我一次只能收10封，你慢点发" |
| 拥塞控制 | 根据网络状况调整发送速度 | 堵车时慢行，路通时快行 |

**序列号和确认号的工作原理：**

```
客户端发送数据：
- 发送第1个数据段（seq=1，数据="Hello"）
- 发送第2个数据段（seq=6，数据="World"）
  （假设 "Hello" 是5个字节，所以下一个序列号是6）

服务器确认数据：
- 收到第1个数据段，回复 ACK（ack=6）
  表示"我收到第1个数据段了，请发第6个字节开始的数据"
- 收到第2个数据段，回复 ACK（ack=11）
  表示"我收到第2个数据段了，请发第11个字节开始的数据"
```

**超时重传的工作原理：**

```
客户端发送数据段（seq=1）
   ↓
启动定时器，等待服务器的 ACK
   ↓
如果在超时时间内收到 ACK → 发送下一个数据段
   ↓
如果超时没收到 ACK → 重新发送数据段（seq=1）
```

**滑动窗口的工作原理：**

```
假设窗口大小是 4：

客户端可以连续发送 4 个数据段，不用等确认：
- 发送 seq=1（窗口内第1个）
- 发送 seq=2（窗口内第2个）
- 发送 seq=3（窗口内第3个）
- 发送 seq=4（窗口内第4个）
   ↓
收到 ack=2（确认第1个）
   ↓
窗口向前滑动，可以发送第5个：
- 发送 seq=5（窗口内第5个）
```

### 7.2.6 TCP 头部结构

TCP 头部包含了很多重要信息，理解这些字段有助于深入理解 TCP 的工作原理：

| 字段 | 长度 | 做什么用 | 生活类比 |
| --- | --- | --- | --- |
| 源端口 | 16 位 | 发送方的端口号 | 发件人的门牌号 |
| 目的端口 | 16 位 | 接收方的端口号 | 收件人的门牌号 |
| 序列号 | 32 位 | 数据段的序号 | 信纸的页码 |
| 确认号 | 32 位 | 期望收到的下一个序号 | "请发第X页" |
| 数据偏移 | 4 位 | TCP 头部的长度 | 信封的大小 |
| 标志位 | 6 位 | 控制信息（SYN、ACK、FIN 等） | 信的类型（普通、紧急、结束） |
| 窗口大小 | 16 位 | 接收方的接收能力 | "我一次能收多少封" |
| 校验和 | 16 位 | 检查数据是否损坏 | 检查信封是否被拆开过 |
| 紧急指针 | 16 位 | 紧急数据的位置 | 标记哪一页是紧急的 |

**标志位的含义：**

| 标志位 | 含义 | 什么时候用 |
| --- | --- | --- |
| SYN | Synchronize，同步序列号 | 建立连接时（三次握手的前两次） |
| ACK | Acknowledgment，确认 | 确认收到数据（三次握手的第三次，以及后续所有数据） |
| FIN | Finish，结束 | 关闭连接时（四次挥手） |
| RST | Reset，重置 | 连接异常时强制关闭 |
| PSH | Push，推送 | 要求对方立即处理数据，不要缓存 |
| URG | Urgent，紧急 | 标记数据为紧急数据 |

### 7.3.1 在浏览器中查看 TCP 连接信息

```javascript
// 使用 Performance API 查看 TCP 连接耗时
// 这可以帮助你了解 TCP 握手对页面加载速度的影响

// 获取页面加载的性能数据
const timing = performance.getEntriesByType('navigation')[0]

// 查看 TCP 连接耗时（单位：毫秒）
// connectStart：TCP 连接开始时间
// connectEnd：TCP 连接完成时间
const tcpTime = timing.connectEnd - timing.connectStart
console.log(`TCP 连接耗时: ${tcpTime} 毫秒`)

// 如果使用了 HTTPS，还可以查看 TLS 握手耗时
// secureConnectionStart：TLS 握手开始时间
// 如果没有使用 HTTPS，这个值是 0
const tlsTime = timing.connectEnd - timing.secureConnectionStart
console.log(`TLS 握手耗时: ${tlsTime} 毫秒`)

// 查看完整的加载时间线
console.log(`重定向耗时: ${timing.redirectEnd - timing.redirectStart} 毫秒`)

console.log(`TCP 连接耗时: ${timing.connectEnd - timing.connectStart} 毫秒`)
console.log(`TLS 握手耗时: ${timing.connectEnd - timing.secureConnectionStart} 毫秒`)

```

### 7.3.2 在 Node.js 中创建 TCP 服务器

```javascript
// Node.js 提供了 net 模块，可以创建 TCP 服务器和客户端

// 引入 net 模块
const net = require('net')

// 创建 TCP 服务器
const server = net.createServer((socket) => {
  // socket 代表一个 TCP 连接
  
  // 当收到客户端数据时触发
  socket.on('data', (data) => {
    // data 是 Buffer 对象，需要转成字符串
    console.log(`收到客户端消息: ${data.toString()}`)
    
    // 回复客户端
    socket.write(`服务器收到: ${data.toString()}`)
  })
  
  // 当客户端关闭连接时触发
  socket.on('end', () => {
    console.log('客户端断开连接')
  })
  
  // 当发生错误时触发
  socket.on('error', (err) => {
    console.error(`连接错误: ${err.message}`)
  })
})

// 服务器监听 8080 端口
server.listen(8080, () => {
  console.log('TCP 服务器启动，监听端口 8080')
})
```

### 7.3.3 在 Node.js 中创建 TCP 客户端

```javascript
// 引入 net 模块
const net = require('net')

// 创建 TCP 客户端
const client = net.createConnection({
  host: '127.0.0.1',  // 服务器地址（本地）
  port: 8080          // 服务器端口
}, () => {
  // 连接建立成功后的回调
  console.log('已连接到服务器')
  
  // 发送数据给服务器
  client.write('你好，服务器！')
})

// 当收到服务器数据时触发
client.on('data', (data) => {
  // data 是 Buffer 对象，需要转成字符串
  console.log(`收到服务器消息: ${data.toString()}`)
  
  // 收到回复后关闭连接
  client.end()
})

// 当连接关闭时触发
client.on('end', () => {
  console.log('与服务器断开连接')
})

// 当发生错误时触发
client.on('error', (err) => {
  console.error(`连接错误: ${err.message}`)
})
```

### 7.3.4 使用 WebSocket 进行全双工通信

```javascript
// WebSocket 是基于 TCP 的全双工通信协议
// 它允许服务器主动向客户端推送数据

// ========== 浏览器端代码 ==========

// 创建 WebSocket 连接
// ws:// 表示未加密的 WebSocket
// wss:// 表示加密的 WebSocket（类似 https）
const ws = new WebSocket('ws://example.com/socket')

// 连接建立成功时触发
ws.onopen = () => {
  console.log('WebSocket 连接已建立')
  
  // 发送数据给服务器
  ws.send('你好，服务器！')
}

// 收到服务器消息时触发
ws.onmessage = (event) => {
  // event.data 是服务器发来的数据
  console.log(`收到服务器消息: ${event.data}`)
}

// 连接关闭时触发
ws.onclose = (event) => {
  // event.code 是关闭状态码
  // event.reason 是关闭原因
  console.log(`连接关闭: ${event.code} - ${event.reason}`)
}

// 发生错误时触发
ws.onerror = (error) => {
  console.error(`WebSocket 错误: ${error}`)
}

// 主动关闭连接
// ws.close()
```

```javascript
// ========== Node.js 服务器端代码（使用 ws 库） ==========

// 先安装 ws 库：npm install ws

// 引入 ws 库
const WebSocket = require('ws')

// 创建 WebSocket 服务器，监听 8080 端口
const wss = new WebSocket.Server({ port: 8080 })

// 当有客户端连接时触发
wss.on('connection', (ws) => {
  console.log('客户端已连接')
  
  // 收到客户端消息时触发
  ws.on('message', (message) => {
    console.log(`收到客户端消息: ${message}`)
    
    // 回复客户端
    ws.send(`服务器收到: ${message}`)
  })
  
  // 客户端断开连接时触发
  ws.on('close', () => {
    console.log('客户端已断开')
  })
  
  // 主动向客户端发送消息
  ws.send('欢迎连接到 WebSocket 服务器！')
})

console.log('WebSocket 服务器启动，监听端口 8080')
```

## 4 对比表格

### TCP vs UDP 详细对比

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 连接方式 | 面向连接（三次握手） | 无连接（直接发送） |
| 可靠性 | 可靠（保证不丢、不乱序） | 不可靠（可能丢包、乱序） |
| 传输速度 | 较慢（有握手、确认开销） | 较快（没有这些开销） |
| 头部开销 | 20 字节 | 8 字节 |
| 流量控制 | 有 | 无 |
| 拥塞控制 | 有 | 无 |
| 传输方式 | 字节流 | 数据报 |
| 应用场景 | 网页、文件传输、邮件 | 视频通话、在线游戏、DNS |
| 典型协议 | HTTP、HTTPS、FTP、SMTP | DNS、DHCP、TFTP、SNMP |

### 三次握手 vs 四次挥手

| 对比项 | 三次握手 | 四次挥手 |
| --- | --- | --- |
| 目的 | 建立连接 | 断开连接 |
| 次数 | 3 次 | 4 次 |
| 发起方 | 客户端 | 客户端或服务器都可以 |
| 为什么这个次数 | 双方确认收发能力，同步序列号 | 全双工通信，每个方向需要单独关闭 |
| 关键标志位 | SYN、SYN+ACK、ACK | FIN、ACK、FIN、ACK |
| 状态变化 | SYN_SENT → SYN_RCVD → ESTABLISHED | FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED |

## 5 新手常见误区

### 误区 1："TCP 三次握手可以改成两次"

**不行。** 两次握手无法防止历史连接的建立。假设网络中有一个延迟的旧 SYN 包到达服务器，服务器会误以为是一个新连接并回复 SYN+ACK。如果只有两次握手，服务器就会认为连接已建立，但客户端知道这是一个旧连接，不会使用它。这样服务器会白白等待资源。三次握手可以让客户端确认这个连接是否真的有效。

```javascript
// 错误理解：
// ❌ 两次握手就够了，第三次是多余的

// 正确理解：
// ✅ 三次握手是必要的，防止历史连接，确保双方收发能力正常
```

### 误区 2："四次挥手可以改成三次"

**不行。** TCP 是全双工通信，双方都可以发送和接收数据。当客户端发送 FIN 时，只是表示客户端没有数据要发送了，但服务器可能还有数据要发送。所以服务器先回复 ACK 确认收到，等数据发送完后再发送自己的 FIN。如果合并成三次，服务器可能还有数据没发完就被迫关闭了。

```javascript
// 错误理解：
// ❌ 四次挥手太麻烦，三次就够了

// 正确理解：
// ✅ 四次挥手是必要的，因为服务器可能还有数据要发送
// 第二次和第三次挥手不能合并，因为中间可能有数据传输
```

### 误区 3："UDP 不可靠，所以比 TCP 差"

**不对。** UDP 和 TCP 各有适用场景，没有绝对的好坏。UDP 虽然不可靠，但速度快、开销小，适合对实时性要求高、可以容忍少量丢包的场景（如视频通话、在线游戏）。TCP 虽然可靠，但速度慢、开销大，适合对可靠性要求高的场景（如网页浏览、文件传输）。

```javascript
// 错误理解：
// ❌ UDP 不可靠，所以比 TCP 差，应该全部用 TCP

// 正确理解：
// ✅ UDP 和 TCP 各有适用场景
// 视频通话用 UDP：可以容忍偶尔卡顿，但不能延迟
// 网页浏览用 TCP：必须保证数据完整，不能丢包
```

### 误区 4："TCP 连接建立后就可以一直使用"

**不对。** TCP 连接有空闲超时机制。如果连接长时间没有数据传输，服务器或中间设备（如防火墙、路由器）可能会主动关闭连接。此外，网络异常、服务器重启等情况也会导致连接断开。实际开发中，通常需要实现心跳机制来保持连接活跃。

```javascript
// 错误理解：
// ❌ TCP 连接建立后可以永久使用

// 正确理解：
// ✅ TCP 连接可能会因为各种原因断开
// 需要实现心跳机制保持连接活跃
// 需要实现重连机制处理连接断开
```

### 误区 5："端口号是随便写的"

**不对。** 端口号有明确的规范：
- 0-1023 是知名端口（Well-Known Ports），分配给常用服务（如 80 给 HTTP，443 给 HTTPS）
- 1024-49151 是注册端口（Registered Ports），分配给特定的应用程序
- 49152-65535 是动态端口（Dynamic Ports），操作系统自动分配给客户端

你不能随便使用 80 或 443 端口，因为这些端口已经被 HTTP 和 HTTPS 占用了。如果你开发的应用需要使用特定端口，应该选择 1024 以上的端口。

```javascript
// 错误做法：
// ❌ 服务器监听 80 端口（需要管理员权限，且可能和 HTTP 冲突）
// ❌ 服务器监听 443 端口（需要管理员权限，且可能和 HTTPS 冲突）

// 正确做法：
// ✅ 开发环境使用 3000、8080 等端口
// ✅ 生产环境使用 80、443（需要配置反向代理）
```

TCP 三次握手的完整过程：

第一次握手（客户端 → 服务器）：
- 客户端发送 SYN 包
- SYN 包内容：SYN=1，seq=x（客户端的初始序列号）
- 客户端状态变化：CLOSED → SYN_SENT
- 作用：客户端告诉服务器"我想建立连接"

第二次握手（服务器 → 客户端）：
- 服务器收到 SYN 包，回复 SYN+ACK 包
- SYN+ACK 包内容：SYN=1，ACK=1，seq=y（服务器的初始序列号），ack=x+1
- 服务器状态变化：LISTEN → SYN_RCVD
- 作用：服务器告诉客户端"我听到你了，我的序列号是y"

- 客户端收到 SYN+ACK 包，回复 ACK 包
- ACK 包内容：ACK=1，seq=x+1，ack=y+1
- 客户端状态变化：SYN_SENT → ESTABLISHED
- 服务器收到 ACK 后状态变化：SYN_RCVD → ESTABLISHED
- 作用：客户端告诉服务器"我也听到你了，连接建立"

为什么需要三次握手：
1. 防止历史连接：如果网络中有延迟的旧 SYN 包，三次握手可以让客户端确认连接是否有效
2. 双方确认能力：确保双方都能正常发送和接收数据
3. 同步序列号：双方交换初始序列号，后续数据传输基于这些序列号排序

### 练习 3（挑战）：TCP 状态机分析

分析以下场景，说明 TCP 连接的状态变化：

场景：客户端主动关闭连接

请画出完整的状态转换图，并说明每个状态的含义。

<details>
<summary>点击查看答案</summary>

```
客户端主动关闭连接的状态变化：

初始状态：ESTABLISHED（连接已建立，双方可以传输数据）

第一次挥手（客户端 → 服务器）：
- 客户端发送 FIN 包
- 客户端状态变化：ESTABLISHED → FIN_WAIT_1
- 含义：客户端没有数据要发送了，等待服务器确认

第二次挥手（服务器 → 客户端）：
- 服务器收到 FIN 包，回复 ACK 包
- 客户端状态变化：FIN_WAIT_1 → FIN_WAIT_2
- 含义：服务器确认收到客户端的 FIN，但服务器可能还有数据要发送
- 此时连接处于半关闭状态：客户端不能发送数据，但可以接收数据

第三次挥手（服务器 → 客户端）：
- 服务器发送完所有数据后，发送 FIN 包
- 客户端收到 FIN 包，回复 ACK 包
- 客户端状态变化：FIN_WAIT_2 → TIME_WAIT
- 含义：客户端等待 2MSL（最大报文段生存时间），确保服务器收到 ACK

第四次挥手后：
- 服务器收到 ACK 包
- 服务器状态变化：LAST_ACK → CLOSED
- 客户端等待 2MSL 后状态变化：TIME_WAIT → CLOSED
- 含义：连接完全关闭

为什么需要 TIME_WAIT 状态：
1. 确保最后一个 ACK 能到达服务器：如果 ACK 丢失，服务器会重发 FIN，客户端在 TIME_WAIT 状态可以重新发送 ACK
2. 让网络中的旧数据包消失：等待 2MSL 时间，确保网络中属于这个连接的所有数据包都消失，防止影响新连接

2MSL 的时间：
- MSL（Maximum Segment Lifetime）是报文段在网络中的最大生存时间，通常是 2 分钟
- 2MSL = 4 分钟
- 所以客户端在关闭连接后需要等待 4 分钟才能完全释放资源
```

</details>
