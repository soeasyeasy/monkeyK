# 第2章：单线程模型深度剖析

## 本章导读

在学这一章之前，你可能会有这些疑问：

- Redis 为什么坚持用单线程？多线程不是更快吗？
- 单线程怎么处理那么多并发连接？不会阻塞吗？
- IO 多路复用到底是什么？select、poll、epoll 有什么区别？
- Redis 6.0 的多线程是怎么实现的？会不会有并发问题？

这一章就是为了解答这些问题。我们会先搞清楚 **为什么单线程还能这么快**，再深入 **IO 多路复用的底层原理**，最后弄明白 **6.0 多线程的具体实现**。

---

## 1 为什么需要单线程模型？

### 痛点分析

多线程模型看起来很美好，但会带来很多问题：

```c
// 多线程模型需要处理的问题
pthread_mutex_lock(&mutex);    // 加锁
value = get(key);              // 操作
pthread_mutex_unlock(&mutex);  // 解锁

// 问题：
// 1. 锁竞争——多个线程抢锁，性能下降
// 2. 死锁——锁的顺序不对，程序卡死
// 3. 上下文切换——线程切换有开销
// 4. 并发 bug——竞态条件、内存可见性
```

### 解决方案

Redis 选择了单线程模型：

```c
// 单线程模型，简单直接
value = get(key);  // 不需要锁，直接操作
```

打个比方：

> 单线程就像一个"只有一个收银员的超市"——所有顾客排队结账，不会发生"两个人抢着扫同一个商品"的情况。虽然只有一个收银员，但因为扫码速度很快（内存操作），所以排队的人也能很快结完。

## 2 单线程为什么能处理高并发？

### 2.1 并发 vs 并行

先搞清楚两个概念：

| 概念 | 说明 | 例子 |
|------|------|------|
| 并发 | 同时处理多个任务（交替执行） | 一个收银员快速切换服务不同顾客 |
| 并行 | 同时执行多个任务（真正同时） | 多个收银员同时服务不同顾客 |

Redis 的单线程是 **并发**，不是并行：

```
// 单线程并发模型
// 一个线程快速切换处理多个连接
连接1: 读 → 处理 → 写
连接2:     读 → 处理 → 写
连接3:         读 → 处理 → 写
时间:  ─────────────────────────→
```

### 2.2 非阻塞 IO

单线程能处理高并发的关键是 **非阻塞 IO**：

```c
// 阻塞 IO（一个连接卡住，整个线程卡住）
read(fd, buffer);  // 如果没数据，一直等

// 非阻塞 IO（没数据就返回，不等待）
result = read(fd, buffer);
if (result == -1 && errno == EAGAIN) {
    // 没数据，先处理其他连接
}
```

### 2.3 IO 多路复用

非阻塞 IO + 轮询 = IO 多路复用：

```c
// 伪代码：IO 多路复用
// 一次调用，监控多个连接
events = epoll_wait([fd1, fd2, fd3, ...]);

// 只返回有事件的连接
for (fd in events) {
    if (fd.readable) {
        data = read(fd);  // 保证有数据可读
        process(data);
    }
}
```

打个比方：

> IO 多路复用就像"一个老师同时看管多个学生"——老师不需要每个学生问问题都单独辅导，而是等所有学生都做完题后，统一解答有疑问的学生。

## 3 IO 多路复用详解

### 3.1 三种实现方式

| 方式 | 原理 | 最大连接数 | 性能 |
|------|------|------------|------|
| select | 遍历所有 fd，检查是否有事件 | 1024 | 低 |
| poll | 类似 select，但没有连接数限制 | 无限制 | 低 |
| epoll | 事件驱动，只返回有事件的 fd | 无限制 | 高 |

### 3.2 select 的问题

```c
// select 的问题
fd_set fds;
FD_ZERO(&fds);
FD_SET(fd1, &fds);
FD_SET(fd2, &fds);
// ... 最多 1024 个

// 每次调用都要遍历所有 fd
select(max_fd + 1, &fds, ...);
// 即使只有 1 个 fd 有事件，也要遍历 1024 个
```

### 3.3 epoll 的优势

```c
// epoll 的优势
int epfd = epoll_create(1);

// 注册感兴趣的事件
epoll_ctl(epfd, EPOLL_CTL_ADD, fd1, &event1);
epoll_ctl(epfd, EPOLL_CTL_ADD, fd2, &event2);

// 只返回有事件的 fd
struct epoll_event events[MAX_EVENTS];
int n = epoll_wait(epfd, events, MAX_EVENTS, -1);

// n 是有事件的 fd 数量，不需要遍历所有
for (int i = 0; i < n; i++) {
    handle(events[i].data.fd);
}
```

### 3.4 epoll 的底层原理

epoll 使用 **红黑树** 和 **双向链表**：

```
// 红黑树：存储所有监控的 fd
红黑树
├── fd1 → event1
├── fd2 → event2
└── fd3 → event3

// 双向链表：存储有事件的 fd（就绪列表）
就绪链表
├── fd2 (有读事件)
└── fd3 (有写事件)

// epoll_wait 只需要遍历就绪链表，不需要遍历红黑树
```

## 4 Redis 的事件循环

### 4.1 ae 事件循环

Redis 使用自己实现的事件循环库 `ae`：

```c
// ae 事件循环的核心结构
typedef struct aeEventLoop {
    int maxfd;              // 最大文件描述符
    int nevents;            // 当前事件数量
    aeFileEvent *events;    // 文件事件数组
    aeTimeEvent *timeEvents;// 时间事件链表
    void *apidata;          // 多路复用库的私有数据
} aeEventLoop;
```

### 4.2 事件类型

Redis 的事件分为两类：

| 类型 | 说明 | 例子 |
|------|------|------|
| 文件事件 | 处理网络 IO | 客户端连接、读写数据 |
| 时间事件 | 定时任务 | 服务器定时操作、持久化 |

### 4.3 事件循环流程

```c
// 事件循环主流程
void aeMain(aeEventLoop *eventLoop) {
    while (!eventLoop->stop) {
        // 1. 处理到期的时间事件
        aeProcessTimeEvents(eventLoop);
        
        // 2. 处理文件事件（阻塞等待）
        aeProcessFileEvents(eventLoop);
    }
}
```

打个比方：

> 事件循环就像一个"值班护士"——她不断检查：有没有病人需要处理（文件事件）？有没有到时间该吃药的病人（时间事件）？一直循环，直到下班。

## 5 Redis 6.0 多线程详解

### 5.1 为什么引入多线程？

Redis 6.0 引入多线程，但 **只用于网络 IO**：

```
// 6.0 之前的瓶颈
网络速度提升（10G/25G 网卡）
    ↓
单线程网络处理成为瓶颈
    ↓
CPU 利用率低（命令执行快，网络处理慢）
```

### 5.2 多线程模型

```
┌─────────────────────────────────────────┐
│           客户端连接                      │
├─────────────────────────────────────────┤
│  线程1: 读取请求1                        │
│  线程2: 读取请求2                        │  ← 多线程读
│  线程3: 读取请求3                        │
├─────────────────────────────────────────┤
│           命令执行（单线程）               │  ← 单线程执行
├─────────────────────────────────────────┤
│  线程1: 写回响应1                        │
│  线程2: 写回响应2                        │  ← 多线程写
│  线程3: 写回响应3                        │
├─────────────────────────────────────────┤
│           客户端连接                      │
└─────────────────────────────────────────┘
```

### 5.3 实现原理

```c
// 多线程 IO 的实现
// 1. 主线程从 epoll 获取可读的客户端
// 2. 将客户端分配给 IO 线程
// 3. IO 线程并行读取请求
// 4. 主线程串行执行命令
// 5. IO 线程并行写回响应

// 分配策略（轮询）
int io_threads_assign_client(client *c) {
    // 轮询分配给 IO 线程
    int thread_id = next_thread++ % io_threads_num;
    io_threads_list[thread_id]->add(c);
    return thread_id;
}
```

### 5.4 配置与性能

```bash
# redis.conf 配置
io-threads 4              # IO 线程数（包括主线程）
io-threads-do-reads yes   # 开启读线程（默认关闭）
```

性能对比：

| 配置 | QPS | 说明 |
|------|-----|------|
| 单线程 | ~10 万 | 默认配置 |
| 4 线程 | ~15 万 | 提升 50% |
| 8 线程 | ~18 万 | 提升 80% |

## 6 Reactor 模型

### 6.1 单 Reactor 单线程

Redis 6.0 之前的模型：

```
┌─────────────────────────────────────┐
│         Reactor 线程                │
│  ┌─────────────────────────────┐    │
│  │     事件循环 (epoll)         │    │
│  │  ┌─────┐ ┌─────┐ ┌─────┐  │    │
│  │  │连接1│ │连接2│ │连接3│  │    │
│  │  └─────┘ └─────┘ └─────┘  │    │
│  └─────────────────────────────┘    │
│           ↓ 读取请求                 │
│      命令处理（同步）                 │
│           ↓ 返回响应                 │
└─────────────────────────────────────┘
```

### 6.2 单 Reactor 多线程

Redis 6.0 的模型：

```
┌─────────────────────────────────────┐
│         Reactor 主线程              │
│  ┌─────────────────────────────┐    │
│  │     事件循环 (epoll)         │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
         ↓ 分发连接
┌─────────────────────────────────────┐
│  IO 线程1    IO 线程2    IO 线程3   │
│  读取请求1   读取请求2   读取请求3   │
│  写回响应1   写回响应2   写回响应3   │
└─────────────────────────────────────┘
         ↑ 命令执行仍由主线程处理
```

### 6.3 多 Reactor 多线程

其他系统（如 Netty）的模型：

```
┌─────────────────────────────────────┐
│  MainReactor 线程（接受连接）        │
└─────────────────────────────────────┘
         ↓ 分发连接
┌─────────────────────────────────────┐
│  SubReactor1  SubReactor2  ...      │
│  处理读写      处理读写               │
└─────────────────────────────────────┘
         ↓ 业务处理
┌─────────────────────────────────────┐
│  业务线程1    业务线程2    ...        │
└─────────────────────────────────────┘
```

Redis 没有采用这种模型，因为命令执行很快，不需要单独的业务线程池。

## 7 核心知识点总结

| 知识点 | 说明 |
|--------|------|
| 单线程优势 | 无锁竞争、无上下文切换、无并发 bug、实现简单 |
| IO 多路复用 | 一个线程监控多个连接，epoll 是最佳实现 |
| epoll 原理 | 红黑树存储 fd，就绪链表返回有事件的 fd |
| 事件循环 | ae 库实现，处理文件事件和时间事件 |
| 6.0 多线程 | 只用于网络 IO，命令执行仍单线程 |
| Reactor 模型 | Redis 使用单 Reactor 多线程模型 |

## 8 新手常见误区

### 误区 1："单线程一定很慢"

**错！** 单线程的快慢取决于做什么。Redis 的命令主要是内存操作，单线程每秒能执行 10 万次以上。瓶颈在网络 IO，不在 CPU。

### 误区 2："epoll 比 select 快是因为底层不同"

**不完全对。** 它们底层都是系统调用，区别在于：

- select 每次都要遍历所有 fd
- epoll 只返回有事件的 fd，不需要遍历

fd 数量越多，epoll 优势越明显。

### 误区 3："Redis 6.0 多线程，所以会有并发问题"

**不会。** 命令执行仍然是单线程的，不会有并发问题。多线程只用于网络 IO，读写数据不会修改数据库状态。

### 误区 4："IO 线程数越多越好"

**不是的。** IO 线程数建议设置为 CPU 核数的 3/4。线程太多会导致上下文切换开销增加，反而降低性能。

## 9 动手练习

### 练习 1：基础练习

**题目**：解释 select、poll、epoll 的区别，为什么 Redis 选择 epoll？

<details>
<summary>点击查看答案</summary>

```
区别：
1. select
   - 最大连接数 1024
   - 每次遍历所有 fd
   - 性能随连接数增加而下降

2. poll
   - 无连接数限制
   - 每次遍历所有 fd
   - 性能随连接数增加而下降

3. epoll
   - 无连接数限制
   - 只返回有事件的 fd
   - 性能稳定，不随连接数增加而下降

Redis 选择 epoll 的原因：
- Linux 下性能最好
- 支持大量连接
- 事件驱动，效率高
```

</details>

### 练习 2：进阶练习

**题目**：Redis 6.0 多线程是如何避免并发问题的？

<details>
<summary>点击查看答案</summary>

```
避免并发问题的方式：

1. IO 线程只负责网络读写
   - 读取客户端请求到缓冲区
   - 写回响应到客户端
   - 不修改数据库状态

2. 命令执行由主线程串行处理
   - IO 线程读取的请求放入队列
   - 主线程从队列取出命令，串行执行
   - 执行结果放入 IO 线程的写队列

3. 同步机制
   - 主线程等待所有 IO 线程完成读取
   - 主线程执行命令
   - 主线程等待所有 IO 线程完成写回
```

</details>

### 练习 3（挑战）：综合练习

**题目**：手写一个简单的 epoll 服务器伪代码，实现同时处理多个客户端连接。

<details>
<summary>点击查看答案</summary>

```c
// 简单的 epoll 服务器伪代码

// 1. 创建监听 socket
int listen_fd = socket();
bind(listen_fd);
listen(listen_fd);

// 2. 创建 epoll 实例
int epfd = epoll_create(1);

// 3. 注册监听 socket 的可读事件
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &event);

// 4. 事件循环
while (true) {
    // 等待事件
    int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
    
    for (int i = 0; i < n; i++) {
        if (events[i].data.fd == listen_fd) {
            // 新连接
            int client_fd = accept(listen_fd);
            epoll_ctl(epfd, EPOLL_CTL_ADD, client_fd, &event);
        } else {
            // 已有连接的数据
            int client_fd = events[i].data.fd;
            read(client_fd, buffer);
            process(buffer);
            write(client_fd, response);
        }
    }
}
```

</details>
