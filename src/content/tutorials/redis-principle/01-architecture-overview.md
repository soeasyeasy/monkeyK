# 第1章：Redis 整体架构与设计哲学

## 本章导读

在学这一章之前，你可能会有这些疑问：

- Redis 为什么能这么快？真的是因为"内存数据库"吗？
- Redis 的源码结构是怎样的？我想看源码应该从哪里开始？
- Redis 的设计哲学是什么？为什么它一直坚持"简单"？
- Redis 6.0 引入多线程，是不是意味着单线程模型被淘汰了？

这一章就是为了解答这些问题。我们会先搞清楚 **Redis 的整体架构**，再理解它的 **设计哲学**，最后弄明白 **为什么 Redis 这么快**。

---

## 1 为什么需要理解 Redis 架构？

### 痛点分析

很多开发者用 Redis 很多年，但只停留在"会用"的层面：

```
// 会用，但不知道为什么
redis.set("key", "value")
redis.get("key")
```

当你遇到以下问题时，就会很痛苦：

- 线上 Redis 突然变慢，不知道怎么排查
- 面试官问"Redis 为什么快"，你只能说"因为基于内存"
- 想优化 Redis 性能，但不知道瓶颈在哪里
- 想阅读 Redis 源码，但打开文件就懵了

### 解决方案

理解 Redis 架构，就像拿到了一张"地图"：

> 有了地图，你就知道每个模块在哪里、做什么事、怎么配合。遇到问题时，你能快速定位到对应的模块，而不是盲目猜测。

打个比方：

> 用 Redis 不会架构，就像开车不会看仪表盘——油没了不知道，发动机过热也不知道，直到抛锚在路上。

## 2 Redis 整体架构

### 2.1 架构分层

Redis 的架构可以分成 **五层**：

```
┌─────────────────────────────────────────┐
│           客户端连接层                    │
│    (网络通信、RESP 协议、客户端管理)        │
├─────────────────────────────────────────┤
│           命令解析与执行层                 │
│    (命令解析、查找命令表、执行命令)          │
├─────────────────────────────────────────┤
│           数据操作层                      │
│    (数据类型实现、对象系统、编码转换)        │
├─────────────────────────────────────────┤
│           存储引擎层                      │
│    (内存管理、持久化、数据库实现)            │
├─────────────────────────────────────────┤
│           基础架构层                      │
│    (事件循环、线程模型、集群、复制)          │
└─────────────────────────────────────────┘
```

打个比方：

> 这五层就像一家餐厅：
> - 客户端连接层 = 服务员（接待客人、点菜）
> - 命令解析层 = 菜单翻译员（把客人的需求翻译成厨房能懂的指令）
> - 数据操作层 = 厨师（按指令做菜）
> - 存储引擎层 = 冰箱和仓库（存放食材）
> - 基础架构层 = 餐厅的水电、通风、安保系统

### 2.2 核心源码结构

Redis 源码非常精简，核心文件不到 10 万行 C 代码。主要文件如下：

| 文件 | 职责 | 说明 |
|------|------|------|
| `server.c/h` | 服务器核心 | 定义 `redisServer` 结构，包含所有服务器状态 |
| `networking.c/h` | 网络通信 | 处理客户端连接、RESP 协议解析 |
| `db.c/h` | 数据库实现 | 键空间管理、过期处理、SCAN 迭代 |
| `object.c/h` | 对象系统 | `redisObject` 定义、编码转换、引用计数 |
| `t_string.c` 等 | 数据类型命令 | 五种基础类型的具体命令实现 |
| `ae.c/h` | 事件循环 | 事件驱动模型的核心 |
| `rdb.c/h` | RDB 持久化 | bgsave、fork、写时复制 |
| `aof.c/h` | AOF 持久化 | AOF 追加、重写、混合持久化 |
| `replication.c/h` | 主从复制 | 全量同步、增量同步、心跳 |
| `cluster.c/h` | 集群 | 哈希槽、gossip、故障转移 |
| `ziplist.c` / `listpack.c` | 底层数据结构 | 紧凑列表实现 |
| `dict.c/h` | 哈希表 | 字典实现、rehash |

### 2.3 核心数据结构

Redis 的核心数据结构可以用一棵"树"来理解：

```
redisServer (服务器)
├── db[] (数据库数组，默认 16 个)
│   └── dict (键空间，哈希表)
│       └── redisObject (值对象)
│           ├── ptr (指向具体编码的数据结构)
│           └── encoding (编码类型)
├── clients (客户端链表)
├── aeLoop (事件循环)
│   ├── fileEvents (文件事件)
│   └── timeEvents (时间事件)
└── masterhost/slaves (复制相关)
```

## 3 Redis 的设计哲学

### 3.1 简单至上

Redis 的设计哲学可以总结为一个词：**简单**。

- 单线程模型（6.0 之前）——不用处理锁竞争
- 内存存储——不用处理磁盘 IO 的复杂性
- 命令式接口——没有复杂的查询语言
- 单进程执行——命令按顺序执行，没有并发问题

打个比方：

> Redis 的设计就像一个"极简主义者"——家里只放必要的家具，不堆杂物。东西少了，找起来就快，管理起来也简单。

### 3.2 内存优先

Redis 的所有设计都围绕"内存"展开：

- 数据存在内存中——读写都是纳秒级
- 数据结构针对内存优化——SDS、ziplist 都是紧凑布局
- 持久化是"附加功能"——RDB/AOF 都是后台异步完成
- 内存不够就淘汰——8 种淘汰策略，主动释放数据

### 3.3 单进程单线程

Redis 6.0 之前，核心命令执行始终是单线程的：

```
// 所有命令在一个线程中顺序执行
// 不需要加锁，不需要考虑并发
void call(client *c, int flags) {
    c->cmd->proc(c);  // 直接执行命令处理函数
}
```

为什么这样设计？

- CPU 不是瓶颈——Redis 的命令大多是内存操作，CPU 消耗很少
- 网络才是瓶颈——IO 多路复用已经能处理大量连接
- 单线程简单——不用处理锁、不用考虑死锁、不用考虑竞态条件

### 3.4 渐进式增强

Redis 的版本演进体现了"渐进式增强"的思想：

| 版本 | 关键特性 | 设计思想 |
|------|----------|----------|
| 2.x | 持久化、主从复制 | 基础功能完善 |
| 3.x | Cluster 集群、Lua 脚本 | 分布式能力 |
| 4.0 | 混合持久化、内存子命令 | 性能优化 |
| 5.0 | Stream、Cluster 改进 | 功能完善 |
| 6.0 | 多线程 IO、ACL、客户端缓存 | 突破网络瓶颈 |
| 7.0 | Function、多 AOF 文件 | 功能增强 |

每次大版本升级，都是在保持"简单"的基础上，解决新的瓶颈。

## 4 Redis 为什么快？

### 4.1 六大原因

Redis 快的原因可以总结为六点：

| 原因 | 说明 | 贡献度 |
|------|------|--------|
| 纯内存操作 | 数据在内存中，读写都是纳秒级 | 最大 |
| 单线程执行 | 没有锁竞争、上下文切换开销 | 很大 |
| IO 多路复用 | 一个线程处理大量连接 | 很大 |
| 高效数据结构 | SDS、跳表、压缩列表等针对内存优化 | 较大 |
| C 语言实现 | 接近硬件，执行效率高 | 较大 |
| 响应式协议 | RESP 协议简单，解析开销小 | 一般 |

### 4.2 内存 vs 磁盘

先看一个对比：

```
// 内存访问速度
内存随机访问：~100 纳秒
SSD 随机访问：~100 微秒 = 100,000 纳秒
HDD 随机访问：~10 毫秒 = 10,000,000 纳秒

// 差距
内存比 SSD 快 1000 倍
内存比 HDD 快 100,000 倍
```

打个比方：

> 内存操作就像在书桌上拿书，伸手就到；磁盘操作就像去图书馆借书，要走路、找书、排队、借出，来回折腾。

### 4.3 单线程的优势

很多人误以为"单线程 = 慢"，但在 Redis 的场景下，单线程反而是优势：

```
// 多线程模型（需要处理锁）
lock(mutex)
value = get(key)
unlock(mutex)

// 单线程模型（不需要锁）
value = get(key)  // 直接操作，没有锁开销
```

单线程的好处：

- 没有锁竞争——不需要加锁、解锁、等待
- 没有上下文切换——线程切换是有开销的
- 没有竞态条件——命令按顺序执行，结果可预测
- 实现简单——代码容易维护，bug 少

### 4.4 IO 多路复用

Redis 使用 IO 多路复用来处理大量连接：

```
// 伪代码：IO 多路复用
while (true) {
    // 一次调用，监控多个 socket
    events = epoll_wait(fds)
    
    // 哪个 socket 有事件就处理哪个
    for (event in events) {
        if (event.readable) {
            handleRead(event.fd)
        }
        if (event.writable) {
            handleWrite(event.fd)
        }
    }
}
```

打个比方：

> IO 多路复用就像一个"前台接待员"——她不需要为每个来访者单独安排一个人，而是自己一个人就能接待所有来访者，谁到了就处理谁。

## 5 Redis 6.0 多线程变革

### 5.1 为什么引入多线程？

Redis 6.0 引入了多线程，但 **只用于网络 IO**，命令执行仍然是单线程的：

```
// 6.0 之前的模型
网络读取 → 命令执行 → 网络写回 （全部在一个线程）

// 6.0 之后的模型
网络读取（多线程） → 命令执行（单线程） → 网络写回（多线程）
```

为什么？

- 网络 IO 成为瓶颈——随着网卡速度提升（10G/25G），单线程网络处理跟不上了
- 命令执行不是瓶颈——命令执行主要是内存操作，CPU 消耗很少
- 保持简单——命令执行单线程，避免了复杂的并发问题

### 5.2 多线程模型

```
┌─────────────────────────────────────────┐
│           客户端连接                      │
├─────────────────────────────────────────┤
│  线程1: 读取请求1  线程2: 读取请求2  ...   │  ← 多线程 IO
├─────────────────────────────────────────┤
│           命令执行（单线程）               │  ← 单线程执行
├─────────────────────────────────────────┤
│  线程1: 写回响应1  线程2: 写回响应2  ...   │  ← 多线程 IO
├─────────────────────────────────────────┤
│           客户端连接                      │
└─────────────────────────────────────────┘
```

### 5.3 配置与开启

```bash
# redis.conf 配置
io-threads-do-reads yes  # 开启读线程（默认关闭）
io-threads 4             # IO 线程数（包括主线程）
```

注意：

- 默认只开启主线程，即退化为单线程模式
- 需要手动开启 `io-threads-do-reads`
- 线程数建议：CPU 核数的 3/4，如 8 核设 6

## 7 新手常见误区

### 误区 1："Redis 快只是因为基于内存"

**不完全对！** 内存只是原因之一。同样基于内存的数据库，性能差距可能很大。Redis 快的核心在于：

- 单线程避免了锁竞争
- IO 多路复用高效处理连接
- 数据结构针对内存优化
- C 语言实现，执行效率高

### 误区 2："Redis 6.0 多线程，所以单线程模型被淘汰了"

**错！** Redis 6.0 的多线程只用于网络 IO，命令执行仍然是单线程的。单线程模型没有被淘汰，只是网络 IO 的瓶颈被突破了。

### 误区 3："Redis 源码很复杂，看不懂"

**不是的。** Redis 源码非常精简，核心代码不到 10 万行。而且代码风格统一，注释清晰，是学习 C 语言和系统编程的绝佳材料。建议从 `server.c` 的 `main` 函数开始，顺着启动流程看下去。

### 误区 4："Redis 只能做缓存"

**大错特错！** Redis 是一个功能丰富的数据结构服务器，除了缓存，还可以做：

- 分布式锁
- 消息队列（Stream）
- 排行榜（ZSet）
- 计数器（String）
- 会话管理
- 地理位置（Geospatial）
