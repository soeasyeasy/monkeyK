## 本章导读

在学这一章之前，你可能会有这些疑问：

## 1 为什么需要 RDB 持久化？

### 痛点分析

Redis 是内存数据库，数据存在内存中：

```
// 问题：
// 1. 服务器宕机 → 内存数据丢失
// 2. 进程崩溃 → 内存数据丢失
// 3. 硬件故障 → 内存数据丢失

// 需要一种机制，将内存数据保存到磁盘
```

### 解决方案

Redis 提供两种持久化方式：

| 方式 | 说明 | 特点 |
|------|------|------|
| RDB | 快照持久化 | 定时生成快照，恢复快 |
| AOF | 追加日志 | 记录每个写命令，数据更安全 |

## 3 bgsave 流程

### 3.1 执行流程

```
// bgsave 执行流程
1. 客户端发送 BGSAVE 命令
   ↓
2. 主进程检查是否已有子进程在执行
   ↓
3. 主进程调用 fork() 创建子进程
   ↓
4. 父子进程共享内存页（写时复制）
   ↓
5. 子进程将内存数据写入临时 RDB 文件
   ↓
6. 写入完成后，替换旧的 RDB 文件
   ↓
7. 子进程退出，发送完成信号
   ↓
8. 主进程收到信号，更新统计信息
```

### 3.2 代码实现

```c
// bgsave 的核心代码
int rdbSaveBackground(char *filename) {
    pid_t childpid;
    
    // 检查是否已有子进程
    if (server.rdb_child_pid != -1) return C_ERR;
    
    // fork 创建子进程
    childpid = fork();
    
    if (childpid == 0) {
        // 子进程
        // 1. 关闭网络监听（不需要处理客户端）
        closeListeningSockets(0);
        
        // 2. 生成 RDB 文件
        retval = rdbSave(filename);
        
        // 3. 退出
        exitFromChild(retval);
    } else {
        // 父进程
        // 记录子进程 PID
        server.rdb_child_pid = childpid;
        return C_OK;
    }
}
```

## 4 写时复制（Copy-On-Write）

### 4.1 原理

```
// 写时复制的过程

// 1. fork 后，父子进程共享同一块内存
父进程 ──→ 内存页 A ──→ 数据
子进程 ──→ 内存页 A ──→ 数据（共享）

// 2. 父进程要修改内存页 A
父进程 ──→ 内存页 A' ──→ 新数据（复制后修改）
子进程 ──→ 内存页 A ──→ 旧数据（不变）

// 3. 只有被修改的内存页才会被复制
// 未被修改的内存页仍然共享
```

打个比方：

> 写时复制就像"复印文件"——开始时两个人看同一份文件，如果其中一个人要在文件上修改，就复印一份给他修改，另一个人继续看原件。这样既节省内存，又保证数据一致性。

### 4.2 内存页管理

```
// 内存页的大小通常是 4KB
// fork 后，所有内存页都是共享的

// 内存页状态：
// - 共享页：父子进程都只读
// - 私有页：父进程修改后复制的页

// 监控写时复制的开销
INFO persistence
// rdb_last_cow_size: 写时复制的内存大小
```

### 4.3 优化策略

```bash
# 减少写时复制的开销
# 1. 避免在 bgsave 期间大量写入
# 2. 配置合理的 save 条件
# 3. 使用大页内存（Transparent Huge Pages）

# Linux 配置大页内存
echo always > /sys/kernel/mm/transparent_hugepage/enabled
```

## 5 RDB 文件格式

### 5.1 文件结构

```
// RDB 文件的整体结构
| MAGIC | VERSION | DB SELECT | KEY-VALUE | ... | EOF | CHECKSUM |
| REDIS | 0011    | 254 0     | 数据      |     | 255 | 8 字节   |

// 具体结构
1. 文件头（5 字节）
   - "REDIS"（5 字节）：魔术字符串
   - "0011"（4 字节）：RDB 版本号

2. 数据库选择
   - 254（1 字节）：DB 选择标识
   - 数据库编号（变长）

3. 键值对数据
   - 类型标识（1 字节）
   - 键（字符串）
   - 值（根据类型不同）
   - 过期时间（可选）

4. 文件尾
   - 255（1 字节）：EOF 标识
   - 校验和（8 字节）：CRC64
```

### 5.2 数据类型编码

| 类型 | 编码 | 说明 |
|------|------|------|
| String | 0 | 字符串类型 |
| List | 1 | 列表类型 |
| Set | 2 | 集合类型 |
| ZSet | 3 | 有序集合类型 |
| Hash | 4 | 哈希类型 |
| ZSet2 | 5 | 有序集合类型 V2 |
| Module | 6 | 模块类型 |
| Module2 | 7 | 模块类型 V2 |

### 5.3 字符串编码

```
// 字符串的编码方式
1. 8 位整数：00 000000 | 1 字节值
2. 16 位整数：01 000000 | 2 字节值
3. 32 位整数：10 000000 | 4 字节值
4. 压缩字符串：11 000000 | 压缩算法 | 长度 | 数据
5. 普通字符串：长度 | 数据
```

## 7 RDB 恢复流程

### 7.1 启动加载

```
// Redis 启动时的恢复流程
1. 检查是否存在 RDB 文件
   ↓
2. 验证文件头（MAGIC 和 VERSION）
   ↓
3. 验证校验和（CRC64）
   ↓
4. 逐个读取键值对
   ↓
5. 根据类型标识创建对应的数据结构
   ↓
6. 设置过期时间（如果有）
   ↓
7. 加载完成，开始接受客户端连接
```

### 7.2 代码实现

```c
// RDB 加载的核心代码
int rdbLoad(char *filename) {
    FILE *fp = fopen(filename, "r");
    
    // 1. 验证文件头
    if (rdbLoadHeader(fp) == C_ERR) return C_ERR;
    
    // 2. 逐个读取键值对
    while (1) {
        int type = rdbLoadType(fp);
        
        if (type == RDB_TYPE_EOF) break;
        
        // 3. 读取键
        key = rdbLoadString(fp);
        
        // 4. 读取值
        val = rdbLoadObject(type, fp);
        
        // 5. 插入数据库
        dbAdd(db, key, val);
        
        // 6. 设置过期时间
        if (expiretime != -1) {
            setExpire(db, key, expiretime);
        }
    }
    
    // 7. 验证校验和
    if (rdbVerifyChecksum(fp) == C_ERR) return C_ERR;
    
    fclose(fp);
    return C_OK;
}
```

## 8 RDB 优缺点

### 8.1 优点

| 优点 | 说明 |
|------|------|
| 紧凑 | RDB 是压缩的二进制文件，体积小 |
| 恢复快 | 直接加载内存，比 AOF 快很多 |
| 适合备份 | 可以定时生成 RDB，用于灾难恢复 |
| 性能影响小 | bgsave 在子进程执行，主进程不阻塞 |

### 8.2 缺点

| 缺点 | 说明 |
|------|------|
| 数据丢失 | 两次快照之间的数据可能丢失 |
| fork 开销 | 数据量大时，fork 可能阻塞主进程 |
| 写时复制 | 大量写入时，内存占用可能翻倍 |

## 9 核心知识点总结

| 知识点 | 说明 |
|--------|------|
| bgsave | 后台生成 RDB，不阻塞主线程 |
| 写时复制 | fork 后父子进程共享内存，修改时才复制 |
| RDB 格式 | 文件头 + 数据库 + 键值对 + EOF + 校验和 |
| 压缩 | LZF 压缩算法，减少文件体积 |
| 恢复 | 启动时加载 RDB，逐个读取键值对 |

## 10 新手常见误区

### 误区 1："bgsave 不会阻塞主进程"

**不完全对。** bgsave 本身在子进程执行，但 fork 操作会短暂阻塞主进程。数据量越大，fork 时间越长。

### 误区 2："RDB 是实时持久化"

**错！** RDB 是定时快照，两次快照之间的数据可能丢失。如果需要实时持久化，应该使用 AOF。

### 误区 3："写时复制不消耗内存"

**不是的。** 写时复制在修改内存页时需要复制，如果 bgsave 期间有大量写入，内存占用可能翻倍。

```
bgsave 执行流程：

- fork 后，父子进程共享同一块内存
- 父进程要修改内存页时，先复制一份再修改
- 子进程继续读取原始数据
- 只有被修改的内存页才会被复制
```

```
3. 在业务低峰期执行 bgsave
4. 使用 SSD 减少 IO 竞争
5. 监控 rdb_last_cow_size，评估写时复制开销
```
