## 1 分布式锁

### 1.1 为什么需要分布式锁？

```
// 单机锁的问题
// 在分布式环境下，多个进程/线程无法共享同一把锁

// 示例：秒杀系统
// 多个服务器同时处理秒杀请求
// 需要使用分布式锁保证只有一个请求成功
```

### 1.2 简单实现

```bash
# 使用 SETNX 实现分布式锁
SETNX lock:order:1001 1
EXPIRE lock:order:1001 10

# 问题：
# 1. SETNX 和 EXPIRE 不是原子操作
# 2. 锁超时后，其他客户端可能获取锁
# 3. 客户端崩溃，锁无法释放
```

### 1.3 改进实现

```bash
# 使用 SET 命令的原子操作
SET lock:order:1001 1 NX EX 10

# 释放锁（Lua 脚本）
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

### 1.4 Redlock 算法

```
// Redlock 算法
// 使用多个独立的 Redis 节点实现分布式锁

// 步骤
1. 获取当前时间（毫秒）
   ↓
2. 依次向所有 Redis 节点请求锁
   ↓
3. 计算获取锁的总时间
   ↓
4. 如果多数节点返回成功，且总时间小于锁超时时间，则获取锁成功
   ↓
5. 锁的实际有效时间 = 原始超时时间 - 获取锁花费的时间
   ↓
6. 如果获取锁失败，向所有节点释放锁
```

### 1.5 Redlock 实现

```c
// Redlock 的伪代码实现
int acquireLock(RedisInstance *instances, int numInstances, const char *resource, int ttl) {
    int acquired = 0;
    long startTime = mstime();
    
    // 1. 依次向所有节点请求锁
    for (int i = 0; i < numInstances; i++) {
        if (tryLock(instances[i], resource, ttl)) {
            acquired++;
        }
    }
    
    // 2. 计算花费时间
    long elapsed = mstime() - startTime;
    
    // 3. 检查是否获取锁成功
    if (acquired >= numInstances / 2 + 1 && elapsed < ttl) {
        return ttl - elapsed;  // 返回有效时间
    }
    
    // 4. 获取锁失败，释放所有锁
    for (int i = 0; i < numInstances; i++) {
        releaseLock(instances[i], resource);
    }
    
    return 0;
}
```

打个比方：

> Redlock 就像"多国签证"：
> - 需要向多个国家（Redis 节点）申请签证（锁）
> - 多数国家同意，签证才有效
> - 如果时间不够，签证无效

## 2 缓存一致性

### 2.1 为什么需要一致性？

```
// 缓存和数据库的数据可能不一致

// 场景 1：先更新数据库，再删除缓存
// 如果删除缓存失败，缓存中还是旧数据

// 场景 2：先删除缓存，再更新数据库
// 如果更新数据库失败，缓存被删除，数据库还是旧数据
```

### 2.2 常见策略

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| Cache Aside | 先更新数据库，再删除缓存 | 简单 | 可能不一致 |
| Read/Write Through | 读写都通过缓存 | 一致性好 | 复杂 |
| Write Behind | 异步写入数据库 | 性能好 | 可能丢失数据 |

### 2.3 Cache Aside 模式

```
// Cache Aside 模式

// 读操作
1. 先读缓存
   ↓
2. 缓存命中，返回数据
   ↓
3. 缓存未命中，读数据库
   ↓
4. 将数据写入缓存
   ↓
5. 返回数据

// 写操作
1. 更新数据库
   ↓
2. 删除缓存
```

### 2.4 延迟双删

```
// 延迟双删策略
// 解决"先删除缓存，再更新数据库"的一致性问题

// 步骤
1. 删除缓存
   ↓
2. 更新数据库
   ↓
3. 延迟一段时间（如 500ms）
   ↓
4. 再次删除缓存

// 原理
// 延迟期间，如果有读操作，会将旧数据写入缓存
// 第二次删除可以清除这些旧数据
```

### 2.5 消息队列

```
// 使用消息队列保证一致性

// 步骤
1. 更新数据库
   ↓
2. 发送删除缓存的消息到消息队列
   ↓
3. 消费者从消息队列获取消息
   ↓
4. 删除缓存

// 优势
// 异步处理，不影响主流程
// 消息队列保证消息不丢失
```

## 3 缓存穿透

### 3.1 什么是缓存穿透？

```
// 缓存穿透：查询一个不存在的数据
// 缓存中没有，数据库也没有
// 每次请求都会打到数据库

// 示例
// 黑客攻击：查询不存在的用户 ID
// 每次请求都穿透缓存，打到数据库
```

### 3.2 解决方案

```
// 方案 1：缓存空值
// 查询数据库为空时，缓存一个空值

if (cache.get(key) == null) {
    value = db.get(key);
    if (value == null) {
        // 缓存空值，设置较短的过期时间
        cache.set(key, "", 60);
    } else {
        cache.set(key, value);
    }
}

// 方案 2：布隆过滤器
// 在缓存前加一层布隆过滤器
// 判断数据是否存在

if (!bloomFilter.mightContain(key)) {
    return null;  // 数据肯定不存在
}
```

### 3.3 布隆过滤器

```c
// 布隆过滤器的原理
// 一个位数组 + 多个哈希函数

// 添加元素
void add(String key) {
    for (int i = 0; i < hashFunctions.length; i++) {
        int index = hashFunctions[i](key) % bitArray.length;
        bitArray[index] = 1;
    }
}

// 查询元素
boolean mightContain(String key) {
    for (int i = 0; i < hashFunctions.length; i++) {
        int index = hashFunctions[i](key) % bitArray.length;
        if (bitArray[index] == 0) {
            return false;  // 肯定不存在
        }
    }
    return true;  // 可能存在
}
```

打个比方：

> 布隆过滤器就像"门禁系统"：
> - 住户信息存储在位数组中
> - 来访者先检查门禁（布隆过滤器）
> - 门禁说"不认识"，肯定不是住户
> - 门禁说"认识"，可能是住户（有误判）

## 4 缓存击穿

### 4.1 什么是缓存击穿？

```
// 缓存击穿：一个热点 KEY 过期
// 大量并发请求同时打到数据库

// 示例
// 热门商品详情页缓存过期
// 瞬间大量请求穿透到数据库
```

### 4.2 解决方案

```
// 方案 1：互斥锁
// 只允许一个线程查询数据库，其他线程等待

if (cache.get(key) == null) {
    if (tryLock(key)) {
        // 获取锁成功，查询数据库
        value = db.get(key);
        cache.set(key, value);
        unlock(key);
    } else {
        // 获取锁失败，等待重试
        sleep(100);
        return get(key);
    }
}

// 方案 2：逻辑过期
// 不设置实际过期时间，而是记录逻辑过期时间

// 缓存结构
{
    "value": "data",
    "expireTime": 1609459200000
}

// 查询时检查逻辑过期
if (cache.get(key).expireTime < currentTime) {
    // 逻辑过期，异步更新缓存
    asyncUpdateCache(key);
}
return cache.get(key).value;
```

```
// 缓存雪崩：大量 KEY 同时过期
// 或者 Redis 节点宕机
// 导致大量请求打到数据库

// 到点后大量 KEY 同时过期

### 5.2 解决方案

```
// 方案 1：随机过期时间
// 在基础过期时间上加随机值

// 方案 2：多级缓存

## 7 新手常见误区

### 误区 1："分布式锁只需要 SETNX 就够了"

**不完全对。** SETNX 实现的分布式锁有很多问题，如锁超时、客户端崩溃等。生产环境建议使用 Redlock 或 Redisson。

### 误区 2："缓存一致性可以保证 100% 一致"

**错！** 分布式环境下，缓存和数据库的一致性很难保证 100%。通常采用最终一致性策略，允许短暂的不一致。

### 误区 3："缓存穿透和缓存击穿是一回事"

**错！** 缓存穿透是查询不存在的数据，缓存击穿是热点 KEY 过期。两者的解决方案不同。
