# 第十章：标签管理

## 本章导读

在学这一章之前，你可能会有这些疑问：

- 项目发布了一个版本（比如 v1.0.0），怎么标记这个提交，方便以后快速找到？
- 标签和分支有什么区别？为什么不能用分支来标记版本？
- 标签创建之后怎么推送到远程仓库？别人怎么拉取我的标签？
- 标签打错了怎么办？能删除或者修改吗？

这一章就是为了解答这些问题。我们会先搞清楚标签的本质，再学会如何创建、查看、推送和删除标签。

---

## 1 为什么需要标签？

### 痛点分析

想象一下这些场景：

1. 你的项目发布 v1.0.0 版本，你在提交信息里写了"Release v1.0.0"。三个月后，你想找到这个版本的代码，翻提交历史翻到眼瞎
2. 你想对比 v1.0.0 和 v2.0.0 之间的差异，但找不到这两个版本对应的提交
3. 你同事问你"v1.5.0 是哪个提交"，你支支吾吾说不清楚
4. 你想基于 v1.0.0 版本修复一个紧急 bug，但不知道从哪个提交开始改

如果没有标签机制，你只能靠提交信息或者提交哈希来定位——这既不方便，也不直观。

### 生活化类比

把标签想象成"书签"：

- 你在看一本厚厚的小说（项目历史），看到第 100 页时觉得这里很重要
- 你在这里夹了一个书签，上面写着"关键剧情"（git tag v1.0.0）
- 下次想回来看，直接翻到书签的位置，不用一页页数
- 你还可以夹多个书签："主角出场"、"高潮部分"、"结局"（v1.0.0、v2.0.0、v3.0.0）

标签就是 Git 提交历史中的"书签"，帮你快速定位重要的里程碑。

> **一句话总结**：标签是给重要提交起的"别名"，让你能快速找到版本发布点。

---

## 2 核心原理

### 标签是什么？

标签是一个**指向特定提交的引用**，它和分支很像，但有一个关键区别：

- **分支**：可以移动，随着新提交不断向前推进
- **标签**：不能移动，一旦创建就固定在某个提交上

打个比方：分支像是一条河流，水流不断向前；标签像是河边的一个标记桩，永远固定在那个位置。

### 标签的类型

Git 有两种标签：

1. **轻量标签**：只是一个指针，指向某个提交，没有额外信息
2. **附注标签**：包含标签名、注释、创建者信息、创建时间等，存储在 Git 数据库中

推荐使用**附注标签**，因为它包含更多信息，方便以后查看。

### 标签的存储位置

标签创建后存储在本地 `.git/refs/tags/` 目录下。标签不会自动随 `git push` 推送到远程，需要你显式推送。

## 3 基础用法

### 查看标签

```bash
# 列出所有标签
git tag

# 按模式搜索标签
git tag -l "v1.*"       # 搜索所有 v1.x.x 的标签
git tag -l "*beta*"     # 搜索包含 beta 的标签
```

### 创建轻量标签

轻量标签只是一个指针，没有额外信息。

```bash
# 给最近一次提交创建轻量标签
git tag v1.0.0

# 给历史提交创建轻量标签
git tag v0.9.0 a1b2c3d
```

### 创建附注标签（推荐）

附注标签包含完整的元数据，推荐使用。

```bash
# 给最近一次提交创建附注标签
git tag -a v1.0.0 -m "Release version 1.0.0"

# 给历史提交创建附注标签
git tag -a v0.9.0 -m "Beta release" a1b2c3d
```

### 查看标签详情

```bash
# 查看附注标签的详细信息
git show v1.0.0

# 输出示例：
# tag v1.0.0
# Tagger: Your Name <your@email.com>
# Date:   Mon Jan 1 12:00:00 2024 +0800
#
# Release version 1.0.0
#
# commit a1b2c3d...
# Author: ...
# Date: ...
#
#     提交信息
```

### 轻量标签 vs 附注标签

| 特性 | 轻量标签 | 附注标签 |
| --- | --- | --- |
| 创建命令 | `git tag v1.0.0` | `git tag -a v1.0.0 -m "..."` |
| 包含信息 | 只有提交引用 | 标签名、注释、创建者、时间 |
| 存储方式 | 简单的指针 | 完整的 Git 对象 |
| 推荐程度 | 不推荐 | 推荐 |
| 使用场景 | 临时标记 | 正式版本发布 |

## 4 推送标签

标签不会自动随 `git push` 推送，需要显式推送。

```bash
# 推送单个标签
git push origin v1.0.0

# 推送所有本地标签
git push origin --tags
```

### 推送策略

| 场景 | 命令 | 说明 |
| --- | --- | --- |
| 推送单个标签 | `git push origin v1.0.0` | 只推送指定的标签 |
| 推送所有标签 | `git push origin --tags` | 一次性推送所有本地标签 |
| 推送分支和标签 | `git push && git push --tags` | 先推送分支，再推送标签 |

::: tip
推荐使用 `git push origin --tags` 一次性推送所有标签，避免漏掉某个标签。
:::

---

## 5 删除标签

### 删除本地标签

```bash
# 删除本地标签
git tag -d v1.0.0
```

### 删除远程标签

```bash
# 方法 1：推送一个空标签到远程（推荐）
git push origin --delete v1.0.0

# 方法 2：使用 refs/tags 语法
git push origin :refs/tags/v1.0.0
```

### 删除标签的完整流程

```bash
# 1. 删除本地标签
git tag -d v1.0.0

# 2. 删除远程标签
git push origin --delete v1.0.0

# 3. 其他协作者需要拉取最新的标签
git fetch --tags
```

## 6 检出标签

标签指向特定的提交，你可以检出标签查看当时的代码。

```bash
# 检出标签（进入 detached HEAD 状态）
git checkout v1.0.0

# 或者使用新命令
git switch v1.0.0
```

::: warning
检出标签后会进入 "detached HEAD" 状态，此时的提交不会关联到任何分支。如果你需要修改代码，应该基于标签创建新分支。
:::

### 基于标签创建新分支

```bash
# 基于标签创建新分支并切换
git checkout -b hotfix v1.0.0

# 或者使用新命令
git switch -c hotfix v1.0.0

# 现在你可以在 hotfix 分支上修改代码
# 修改完成后提交
git commit -m "fix: 修复 v1.0.0 的问题"

# 推送新分支
git push -u origin hotfix
```

## 7 标签命名规范

推荐使用**语义化版本号**（Semantic Versioning）：

```
v1.0.0        # 主版本.次版本.补丁版本
v1.2.3        # 1 主版本，2 次版本，3 补丁版本
```

### 版本号规则

| 版本变化 | 含义 | 示例 |
| --- | --- | --- |
| 补丁版本 +1 | 修复 bug，向后兼容 | v1.0.0 → v1.0.1 |
| 次版本 +1 | 新增功能，向后兼容 | v1.0.0 → v1.1.0 |
| 主版本 +1 | 重大更新，不兼容旧版 | v1.0.0 → v2.0.0 |

### 预发布版本

```
v1.0.0-alpha      # 内部测试版
v1.0.0-beta       # 公开测试版
v1.0.0-rc.1       # 候选发布版（Release Candidate）
v1.0.0-rc.2       # 第二个候选版本
```

### 命名建议

- 始终以 `v` 开头，方便识别
- 使用数字，避免使用字母（除了预发布标识）
- 遵循语义化版本规范
- 标签名要简洁，不要包含空格或特殊字符

## 8 标签与分支的对比

| 特性 | 标签 | 分支 |
| --- | --- | --- |
| 是否可移动 | 不可移动 | 可移动（随提交前进） |
| 用途 | 标记版本发布点 | 开发功能、修复 bug |
| 创建方式 | `git tag` | `git branch` |
| 是否推送 | 需要显式推送 | 默认推送 |
| 命名规范 | 语义化版本号 | 功能名、bug 编号等 |
| 生命周期 | 永久保留 | 可删除 |
| 检出后状态 | detached HEAD | 正常分支状态 |

## 10 新手常见误区

### 误区 1："标签可以像分支一样移动"

**不对。** 标签一旦创建就固定在某个提交上，不能移动。如果你想在另一个提交上打同样的标签，只能删除旧标签，再重新创建。

正确做法：标签是"永久标记"，创建前要确认提交是正确的。如果打错了，删除后重新创建。

### 误区 2："git push 会自动推送所有标签"

**不会。** `git push` 只会推送分支，不会自动推送标签。你需要显式使用 `git push origin --tags` 或者 `git push origin v1.0.0`。

正确做法：每次创建标签后，记得手动推送，或者在推送分支时加上 `--tags` 参数。

### 误区 3："检出标签后可以继续提交"

**可以提交，但不推荐。** 检出标签后会进入 "detached HEAD" 状态，此时的提交不会关联到任何分支，容易丢失。如果你需要修改，应该基于标签创建新分支。

正确做法：`git checkout -b hotfix v1.0.0` 创建新分支后再修改。

### 误区 4："轻量标签和附注标签没区别"

**有区别。** 轻量标签只是一个指针，没有额外信息；附注标签包含标签名、注释、创建者、时间等完整信息。在团队协作中，附注标签更容易追溯。

正确做法：正式版本发布时，始终使用附注标签（`-a` 和 `-m`）。

### 误区 5："标签命名随便写就行"

**不规范。** 标签命名应该遵循语义化版本规范（v1.0.0），这样别人一看就知道是什么版本。如果你用 `release-1.0`、`version_1_0_0` 等不规范的命名，会增加理解成本。

正确做法：统一使用 `vX.Y.Z` 格式，预发布版本加上 `-alpha`、`-beta`、`-rc` 等标识。

## 11 动手练习

### 练习 1：基础练习 — 创建和查看标签

1. 在你的仓库中，给最近一次提交创建一个附注标签 `v1.0.0`
2. 用 `git tag` 查看所有标签，确认标签已创建
3. 用 `git show v1.0.0` 查看标签详情
4. 给历史提交（比如前 3 个提交）创建一个标签 `v0.9.0`

<details>
<summary>点击查看答案</summary>

```bash
# 1. 给最近一次提交创建附注标签
git tag -a v1.0.0 -m "Release version 1.0.0"

# 2. 查看所有标签
git tag
# 输出应该包含：v1.0.0

# 3. 查看标签详情
git show v1.0.0
# 输出应该显示：标签名、创建者、时间、注释、提交信息

# 4. 给历史提交创建标签
git tag -a v0.9.0 -m "Beta release" HEAD~3

# 5. 再次查看所有标签
git tag
# 输出应该包含：v0.9.0, v1.0.0

# 6. 按模式搜索标签
git tag -l "v1.*"
# 输出：v1.0.0
```

</details>

### 练习 2：进阶练习 — 推送和删除标签

完成以下任务：

1. 创建一个标签 `v1.1.0`
2. 推送这个标签到远程仓库
3. 删除本地标签 `v1.1.0`
4. 删除远程标签 `v1.1.0`
5. 重新创建标签 `v1.1.0`，并一次性推送所有标签

<details>
<summary>点击查看答案</summary>

```bash
# 1. 创建标签
git tag -a v1.1.0 -m "Add new feature"

# 2. 推送单个标签
git push origin v1.1.0
# 输出：Counting objects: ...
# To remote-repo
#  * [new tag]         v1.1.0 -> v1.1.0

# 3. 删除本地标签
git tag -d v1.1.0
# 输出：Deleted tag 'v1.1.0'

# 4. 删除远程标签
git push origin --delete v1.1.0
# 输出：To remote-repo
#  - [deleted]         v1.1.0

# 5. 重新创建标签
git tag -a v1.1.0 -m "Add new feature (recreated)"

# 6. 推送所有标签
git push origin --tags
# 输出：Counting objects: ...
# To remote-repo
#  * [new tag]         v1.1.0 -> v1.1.0
#  * [new tag]         v1.0.0 -> v1.0.0
#  * [new tag]         v0.9.0 -> v0.9.0
```

</details>

### 练习 3（挑战）：综合练习 — 基于标签修复版本

模拟以下场景：

1. 你的项目已经发布 v1.0.0 版本
2. 用户反馈 v1.0.0 有一个严重 bug，需要紧急修复
3. 基于 v1.0.0 标签创建一个 `hotfix-v1.0.0` 分支
4. 在 hotfix 分支上修复 bug（模拟修改）
5. 提交修复，创建标签 `v1.0.1`
6. 推送 hotfix 分支和标签到远程

<details>
<summary>点击查看答案</summary>

```bash
# 1. 假设已经发布了 v1.0.0
# 如果没有，先创建
git tag -a v1.0.0 -m "Release version 1.0.0"
git push origin v1.0.0

# 2. 基于 v1.0.0 标签创建 hotfix 分支
git checkout -b hotfix-v1.0.0 v1.0.0
# 输出：Switched to a new branch 'hotfix-v1.0.0'

# 3. 修复 bug（模拟修改）
echo "// Fix critical bug" >> app.js

# 4. 提交修复
git add app.js
git commit -m "fix: 修复 v1.0.0 的严重 bug"

# 5. 创建补丁版本标签
git tag -a v1.0.1 -m "Fix critical bug in v1.0.0"

# 6. 推送 hotfix 分支
git push -u origin hotfix-v1.0.0

# 7. 推送标签
git push origin v1.0.1

# 8. 切回 main 分支（可选）
git checkout main

# 9. 如果需要，可以将 hotfix 合并到 main
git merge hotfix-v1.0.0

# 10. 删除 hotfix 分支（可选）
git branch -d hotfix-v1.0.0
```

</details>

## 12 本章小结

- 标签用于标记版本发布点，是"不可移动"的引用
- 推荐使用附注标签（`-a` 和 `-m`），包含完整信息
- 标签需要显式推送：`git push origin --tags`
- 删除标签需要同时删除本地和远程
- 检出标签后进入 detached HEAD，建议创建新分支
- 遵循语义化版本规范：v1.0.0、v1.2.3-beta
