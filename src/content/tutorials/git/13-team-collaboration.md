# 第十三章：团队协作实践

## 本章导读

在前面的章节中，你已经学会了 Git 的分支、合并、变基等操作。但当你进入团队开发，情况就完全不一样了。在学这一章之前，你可能会有这些疑问：

- 团队里这么多人，代码怎么合并到一起才不乱？
- 我写的代码，别人怎么知道写得好不好？谁来检查？
- main 分支这么重要，万一有人乱推代码怎么办？
- 合并代码的时候，应该选哪种方式？有什么区别？

这一章就是为了解答这些问题。我们会从 Pull Request 开始，一步步搞懂团队协作的完整流程，让你从"单打独斗"过渡到"团队作战"。

---

## 13.1 为什么需要团队协作规范？

### 痛点分析

想象一下这个场景：一个 5 人团队，没有协作规范，所有人都直接往 main 分支推代码。

```
小张：推了一版代码，main 分支挂了
小李：赶紧修复，结果和小王的代码冲突了
小王：我昨天写的代码怎么没了？谁覆盖的？
小陈：别吵了，我推的代码把数据库配置覆盖了，线上出 bug 了
```

这就像一间没有红绿灯的十字路口，所有人都往前冲，结果就是堵死。

打个比方：

> 团队协作规范就像交通规则。红绿灯告诉你什么时候能走（分支保护），驾照考试确保你会开车（代码审查），行车记录仪记录一切（提交历史）。没有这些规则，马路就变成了碰碰车现场。

### 解决方案

Git 提供了一套完整的团队协作机制：

1. **Pull Request**：提议合并代码，让大家先看看
2. **代码审查**：同事帮你检查代码质量
3. **分支保护**：给重要分支加"锁"，不能随便推
4. **合并策略**：选择最合适的方式把代码合到一起

> **一句话总结**：团队协作规范让每个人都能安全、高效地贡献代码，同时保证项目质量。

## 13.2 Pull Request（PR）

### 概念解释

Pull Request 简称 PR，翻译过来就是"拉取请求"。它的核心思想是：

> 不要直接往主分支推代码，而是先推到自己的分支，然后"请求"主分支把你的代码"拉"进来。

打个比方：

> 你（功能分支）想加入一个俱乐部（main 分支），不能直接闯进去，得先提交一份申请（PR），俱乐部的管理员（审查者）审核通过后，你才能正式加入（合并）。

### 创建 PR 的流程

```bash
# 第一步：从 main 分支创建功能分支
git checkout -b feature/user-auth main

# 第二步：开发功能，提交代码
git add .
git commit -m "feat: 添加用户认证"

# 第三步：推送功能分支到远程仓库
git push -u origin feature/user-auth

# 第四步：在 GitHub/GitLab 上创建 Pull Request
# （这一步在网页上操作，点击 "New Pull Request"）
```

### PR 标题规范

PR 的标题要让人一眼看出你做了什么，推荐使用 Conventional Commits 格式：

```
# 好的标题，一眼就知道做了什么
feat: 添加用户登录功能
fix: 修复购物车计算错误
docs: 更新 API 文档

# 不好的标题，看了等于没看
修改了一些东西
更新代码
fix bug
```

### PR 描述模板

一个好的 PR 描述，能帮审查者快速理解你的改动：

```markdown
## 变更内容
- 添加用户登录表单
- 实现 JWT 认证
- 添加登录状态管理

## 测试情况
- [x] 单元测试通过
- [x] 手动测试登录流程
- [x] 边界情况处理

## 截图
（如果是 UI 变更，贴上前后对比截图）

## 相关问题
Closes #123
```

### PR 大小的最佳实践

| PR 大小 | 建议 |
| --- | --- |
| 小于 100 行 | 最佳，审查者最喜欢 |
| 100-400 行 | 可以接受，尽量控制在这个范围 |
| 400-1000 行 | 太大了，建议拆分 |
| 超过 1000 行 | 必须拆分，没人愿意审这么大的 PR |

打个比方：

> PR 就像快递包裹，小而专注的包裹容易验收，一个装满东西的大箱子只会让人头疼。

## 13.3 代码审查（Code Review）

### 概念解释

代码审查就是让同事帮你"挑毛病"。这不是找茬，而是团队保证代码质量的重要手段。

打个比方：

> 代码审查就像考试后的互批试卷。批改的人能发现你没注意到的错误，你也能从别人的代码中学到新写法。最终大家都进步了。

### 审查者职责

1. **理解上下文**：先阅读 PR 描述和相关 issue，搞清楚要解决什么问题
2. **检查代码质量**：
   - 代码是否清晰易读
   - 是否有明显的 bug
   - 是否遵循项目规范
   - 是否有安全隐患
3. **提供建设性反馈**：
   - 指出问题的同时给出建议
   - 区分"必须修改"和"建议优化"
   - 认可优秀的实现

### 审查评论示例

```
# 好的评论，指出问题并给出建议
建议：这里可以使用 map 方法简化代码，减少循环嵌套

# 好的评论，明确标记严重程度
[必须修改] 这个变量名不够清晰，建议改为 userData，
不然其他开发者看到 temp 不知道是什么

# 好的评论，给予正面反馈
优秀：这个错误处理很完善，考虑了网络超时和服务器错误两种情况
```

### 使用 GitHub CLI 审查

```bash
# 查看某个 PR 的详情
gh pr view 123

# 在本地检出 PR 的代码进行审查
gh pr checkout 123

# 批准这个 PR
gh pr approve 123

# 请求修改（附带说明原因）
gh pr request-changes 123 -m "需要添加单元测试"
```

## 13.4 分支保护

### 概念解释

分支保护就是给重要分支加一把"锁"，防止有人不小心或恶意地破坏代码。

打个比方：

> main 分支就像公司的保险柜，不能谁都能打开。你需要钥匙（PR 审批），还得通过身份验证（CI 测试通过），才能打开保险柜。

### GitHub 分支保护规则

在 GitHub 的 Settings > Branches 中配置：

```yaml
# 分支保护规则配置
Branch protection rules:
  # 保护 main 分支
  - Branch name pattern: main
  
  # 要求通过 Pull Request 才能合并
  Require pull requests before merging:
    - Required approvals: 2          # 至少需要 2 个人批准
    - Dismiss stale reviews: true    # 有新提交时，之前的批准自动失效
    - Require review from Code Owners: true  # 需要代码所有者审查
  
  # 要求状态检查通过
  Require status checks to pass:
    - CI/CD 测试必须通过
    - 代码质量检查通过
  
  # 其他保护措施
  - Require branches to be up to date: true  # 合并前必须和 main 保持同步
  - Include administrators: true             # 管理员也受限制
  - Allow force pushes: false                # 禁止强制推送
  - Allow deletions: false                   # 禁止删除分支
```

### 保护效果

| 操作 | 无保护 | 有保护 |
| --- | --- | --- |
| 直接 push 到 main | 可以 | 不可以 |
| 绕过 PR 合并 | 可以 | 不可以 |
| 强制推送 | 可以 | 不可以 |
| 删除分支 | 可以 | 不可以 |
| 未经审查合并 | 可以 | 不可以 |

## 13.5 合并策略

合并代码时，你有三种策略可选。选对了事半功倍，选错了历史一团糟。

### Squash and Merge（压缩合并）

把 PR 里的所有提交压缩成一个提交：

```
PR 中的提交：A ── B ── C
合并后：        D (squash，三个变成一个)
```

**优点**：
- 主分支历史非常干净，每个功能只有一个提交
- 看主分支历史的时候，一目了然

**缺点**：
- 丢失了开发过程中的细节

**适用场景**：功能分支、小改动、提交历史比较乱的情况

### Rebase and Merge（变基合并）

把 PR 的提交"重新播放"到目标分支上：

```
合并前：
main:    X ── Y
              \
feature:       A ── B ── C

合并后：
main:    X ── Y ── A' ── B' ── C'
```

**优点**：
- 保持线性历史，没有分叉
- 保留了每个提交

**缺点**：
- 如果提交太多，主分支历史会很长

**适用场景**：提交历史清晰、每个提交都有意义的情况

### Merge Commit（合并提交）

创建一个专门的合并提交，保留完整的分支结构：

```
合并前：
main:    X ── Y
              \
feature:       A ── B ── C

合并后：
main:    X ── Y ──────── M
              \          /
feature:       A ── B ── C
```

**优点**：
- 保留完整的开发历史
- 可以清楚看到哪些提交属于同一个功能

**缺点**：
- 历史图中会有很多分叉和合并节点

**适用场景**：大型功能、需要保留完整开发历史的场景

### 三种策略对比

| 特性 | Squash | Rebase | Merge Commit |
| --- | --- | --- | --- |
| 主分支历史 | 干净，一个功能一个提交 | 线性，保留每个提交 | 保留分支结构 |
| 提交数量 | 最少 | 不变 | 多一个合并提交 |
| 开发细节 | 丢失 | 保留 | 完整保留 |
| 适合场景 | 小功能、快速迭代 | 提交清晰的功能 | 大功能、需要追溯 |
| 团队推荐 | 大多数团队首选 | 注重历史质量的团队 | 需要完整记录的项目 |

## 13.6 团队协作规范

### 提交信息规范

使用 Conventional Commits 规范，让提交信息标准化：

```
<type>(<scope>): <subject>

<body>

<footer>
```

**类型说明**：

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| feat | 新功能 | feat(auth): 添加用户登录 |
| fix | 修复 bug | fix(cart): 修复价格计算错误 |
| docs | 文档变更 | docs: 更新 README |
| style | 代码格式（不影响逻辑） | style: 调整缩进 |
| refactor | 重构（不是新功能也不是修复） | refactor: 提取公共函数 |
| test | 测试相关 | test: 添加登录单元测试 |
| chore | 构建或工具变更 | chore: 升级依赖版本 |

**完整示例**：

```
feat(auth): 添加用户登录功能

- 实现用户名密码登录
- 添加 JWT token 验证
- 集成登录状态管理

Closes #123
```

### 代码所有权

使用 `CODEOWNERS` 文件定义代码所有者，PR 涉及这些文件时，会自动请求对应团队审查。

```
# .github/CODEOWNERS 文件

# 全局默认所有者（所有改动都需要这个团队审查）
* @team-leads

# 前端代码归前端团队
/src/components/ @frontend-team
/src/styles/ @frontend-team

# 后端 API 归后端团队
/api/ @backend-team

# 数据库变更需要 DBA 和团队负责人共同审查
/migrations/ @db-team @team-leads
```

打个比方：

> CODEOWNERS 就像公司的部门分工。前端页面的改动找前端组，数据库的改动找 DBA，谁的地盘谁负责。这样就不会出现"外行指导内行"的情况。

## 13.7 核心知识点总结

| 知识点 | 说明 |
| --- | --- |
| Pull Request | 提议合并代码的请求，是团队协作的核心 |
| 代码审查 | 同事检查你的代码质量，提供建设性反馈 |
| 分支保护 | 给重要分支加锁，防止不当修改 |
| Squash Merge | 把多个提交压缩成一个，保持主分支干净 |
| Rebase Merge | 变基后合并，保持线性历史 |
| Merge Commit | 创建合并提交，保留完整分支结构 |
| Conventional Commits | 提交信息规范，格式为 type(scope): subject |
| CODEOWNERS | 定义代码所有者，自动分配审查者 |

## 13.8 新手常见误区

### 误区 1："PR 描述随便写几个字就行了"

**错！** PR 描述是审查者理解你代码的第一扇窗。如果你写"改了一些东西"，审查者只能一个个文件去猜你做了什么。

正确做法：用模板写清楚改了什么、为什么改、怎么测试的。好的 PR 描述能节省一半的沟通时间。

### 误区 2："代码审查就是找茬，通过就行了"

不是的。代码审查的目的不是"通过"或"不通过"，而是：
1. 发现潜在问题
2. 分享知识（让团队成员了解彼此的代码）
3. 提升代码质量

即使是资深工程师的代码，也需要审查。

### 误区 3："PR 越大越好，一次把所有功能都放进去"

恰恰相反。大 PR 审查起来非常痛苦，而且容易漏掉问题。

正确做法：一个 PR 只做一件事，控制在 400 行以内。如果功能太大，拆成多个 PR 分步合并。

### 误区 4："main 分支不用保护，我们团队人少"

人少也需要保护。误操作不分人数，一个 `git push --force` 就能让所有人的代码消失。分支保护的成本很低，但能避免灾难性的后果。

### 误区 5："合并策略无所谓，选哪个都一样"

不同的合并策略会影响项目历史的清晰度。如果团队没有统一约定，有人用 Squash，有人用 Merge Commit，主分支的历史就会乱七八糟。

正确做法：团队统一选择一种合并策略，并写进开发规范中。
