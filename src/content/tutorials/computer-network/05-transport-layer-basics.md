# 第5章：传输层基础

## 本章导读

在学这一章之前，你可能会有这些疑问：

- TCP 和 UDP 有什么区别？为什么有两种协议？
- 端口号是什么？为什么需要端口号？
- TCP 三次握手是怎么工作的？为什么需要三次？
- 为什么视频通话用 UDP，而网页浏览用 TCP？

这一章就是为了解答这些问题。我们会先搞清楚**传输层的核心功能**，再对比**TCP 和 UDP 的特性**，最后理解**TCP 连接建立的过程**。

---

## 5.1 为什么需要传输层？

### 痛点分析

如果没有传输层：

- 网络层只提供主机到主机的通信，无法区分具体的应用程序
- 就像**邮局能把信送到你家，但不知道是给家里哪个人**
- 无法保证数据的可靠传输
- 无法控制数据传输的速率

### 解决方案

传输层负责**提供端到端的可靠或不可靠传输服务**。

打个比方：

> 传输层就像**快递公司的客服系统**，TCP 是顺丰（保证送达、有 tracking），UDP 是平邮（不保证、速度快）。

### 传输层的核心功能

| 功能 | 说明 | 生活例子 |
|------|------|----------|
| 进程寻址 | 使用端口号标识应用程序 | 门牌号 |
| 可靠传输 | 保证数据按序、无差错到达 | 快递签收 |
| 流量控制 | 控制发送速率，避免接收方过载 | 水龙头调节 |
| 拥塞控制 | 避免网络过载 | 交通管制 |
| 多路复用 | 多个应用共享网络 | 多车道公路 |

## 5.2 端口号

### 什么是端口号？

**定义**：传输层用来标识应用程序的编号

**长度**：16 位，范围 0-65535

**作用**：区分同一台主机上的不同应用程序

### 端口号分类

| 范围 | 类型 | 说明 | 例子 |
|------|------|------|------|
| 0-1023 | 熟知端口 | 分配给常用服务 | 80（HTTP）、443（HTTPS）、22（SSH） |
| 1024-49151 | 注册端口 | 分配给应用程序 | 3306（MySQL）、8080（HTTP 替代） |
| 49152-65535 | 动态端口 | 临时分配给客户端 | 客户端随机使用 |

### 常见端口号

| 端口 | 协议 | 服务 |
|------|------|------|
| 20/21 | TCP | FTP |
| 22 | TCP | SSH |
| 23 | TCP | Telnet |
| 25 | TCP | SMTP |
| 53 | TCP/UDP | DNS |
| 80 | TCP | HTTP |
| 110 | TCP | POP3 |
| 143 | TCP | IMAP |
| 443 | TCP | HTTPS |
| 3306 | TCP | MySQL |
| 3389 | TCP | 远程桌面 |

**生活类比**：

> 端口号就像**公寓的门牌号**，IP 地址是公寓地址，端口号是具体房间号。快递员（数据包）送到公寓后，根据门牌号找到正确的房间（应用程序）。

### Socket 地址

**定义**：IP 地址 + 端口号，唯一标识一个网络通信端点

**例子**：`192.168.1.100:8080`

## 5.3 UDP 协议

### UDP 的特点

| 特性 | 说明 |
|------|------|
| 无连接 | 发送前不需要建立连接 |
| 不可靠 | 不保证数据到达、不保证顺序 |
| 无拥塞控制 | 想发就发，不管网络状况 |
| 速度快 | 头部开销小（8 字节） |
| 支持一对一、一对多 | 可以广播、组播 |

### UDP 报文格式

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 源端口(16位) │ 目的端口(16位)│ UDP长度(16位)│ UDP校验和    │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

**头部简单**：只有 8 字节，开销小

### UDP 的应用场景

- 实时应用：视频通话、在线游戏、直播
- DNS 查询
- DHCP
- SNMP

**生活类比**：像**发微信语音**，发出去就不管了，丢了就丢了，不会重发。

---

## 5.4 TCP 协议

### TCP 的特点

| 特性 | 说明 |
|------|------|
| 面向连接 | 发送前必须建立连接（三次握手） |
| 可靠传输 | 保证数据按序、无差错、不丢失 |
| 全双工 | 双方可以同时发送和接收 |
| 点对点 | 只能一对一通信 |
| 流量控制 | 滑动窗口机制 |
| 拥塞控制 | 慢开始、拥塞避免、快重传、快恢复 |

### TCP 报文格式

```
┌──────────────┬──────────────┬──────────────────────────────┐
│ 源端口(16位) │ 目的端口(16位)│ TCP序号(32位)                │
├──────────────┴──────────────┼──────────────────────────────┤
│ TCP确认号(32位)             │ 数据偏移│保留│控制位(6位)    │
├─────────────────────────────┼──────────────────────────────┤
│ 窗口大小(16位)              │ 校验和(16位)                 │
├─────────────────────────────┼──────────────────────────────┤
│ 紧急指针(16位)              │ 选项（可选）                 │
├─────────────────────────────┴──────────────────────────────┤
│ 数据                                                        │
└────────────────────────────────────────────────────────────┘
```

**关键字段说明**：

| 字段 | 说明 |
|------|------|
| 序号 | 数据流的字节编号，用于排序 |
| 确认号 | 期望收到对方的下一个字节序号 |
| 控制位 | URG、ACK、PSH、RST、SYN、FIN |
| 窗口大小 | 接收方还能接收多少数据 |

### TCP vs UDP 对比

| 对比项 | TCP | UDP |
|--------|-----|-----|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠 | 不可靠 |
| 顺序 | 保证顺序 | 不保证 |
| 速度 | 较慢 | 快 |
| 头部开销 | 20 字节 | 8 字节 |
| 流量控制 | 有 | 无 |
| 拥塞控制 | 有 | 无 |
| 传输方式 | 字节流 | 数据报 |
| 应用场景 | 文件传输、网页、邮件 | 视频、游戏、DNS |

## 5.5 TCP 连接管理

### 三次握手（建立连接）

**过程**：

```
客户端                    服务器
  │                         │
  │  1. SYN (seq=x)         │
  │ ──────────────────────> │
  │                         │
  │  2. SYN+ACK (seq=y,     │
  │     ack=x+1)            │
  │ <────────────────────── │
  │                         │
  │  3. ACK (ack=y+1)       │
  │ ──────────────────────> │
  │                         │
  │     连接建立成功         │
```

**步骤详解**：

1. **第一次握手**：客户端发送 SYN 报文，seq=x，进入 SYN_SENT 状态
2. **第二次握手**：服务器收到 SYN，回复 SYN+ACK，seq=y，ack=x+1，进入 SYN_RCVD 状态
3. **第三次握手**：客户端收到 SYN+ACK，回复 ACK，ack=y+1，进入 ESTABLISHED 状态

**为什么需要三次握手？**

- **防止历史连接**：避免旧的 SYN 报文建立错误连接
- **同步序号**：双方确认对方的初始序号
- **资源分配**：服务器在第二次握手时分配资源，第三次确认

**生活类比**：像**打电话**：
- "喂，你能听到我吗？"（SYN）
- "能听到，你能听到我吗？"（SYN+ACK）
- "能听到！"（ACK）

### 四次挥手（断开连接）

**过程**：

```
客户端                    服务器
  │                         │
  │  1. FIN (seq=u)         │
  │ ──────────────────────> │
  │                         │
  │  2. ACK (ack=u+1)       │
  │ <────────────────────── │
  │                         │
  │  3. FIN (seq=w)         │
  │ <────────────────────── │
  │                         │
  │  4. ACK (ack=w+1)       │
  │ ──────────────────────> │
  │                         │
  │     连接断开             │
```

**步骤详解**：

1. **第一次挥手**：客户端发送 FIN，请求断开连接，进入 FIN_WAIT_1
2. **第二次挥手**：服务器收到 FIN，回复 ACK，进入 CLOSE_WAIT
3. **第三次挥手**：服务器发送 FIN，进入 LAST_ACK
4. **第四次挥手**：客户端收到 FIN，回复 ACK，进入 TIME_WAIT，等待 2MSL 后关闭

**为什么需要四次挥手？**

- TCP 是全双工，每个方向必须单独关闭
- 服务器收到 FIN 时可能还有数据要发送
- 确保双方都能正常关闭

**为什么需要 TIME_WAIT？**

- 确保最后一个 ACK 能到达服务器
- 等待网络中该连接的残留报文消失
- 时间：2MSL（Maximum Segment Lifetime，通常 2 分钟）

## 5.6 TCP 可靠传输机制

### 序号与确认

**序号**：每个字节都有一个序号，用于排序

**确认号**：期望收到的下一个字节序号，表示之前的字节都已收到

### 超时重传

**原理**：发送数据后启动定时器，如果超时未收到确认，则重传

**超时时间**：RTT（往返时间）的动态估计

### 滑动窗口

**原理**：
- 发送方可以连续发送多个数据段，不需要等待确认
- 窗口大小由接收方决定（流量控制）
- 收到确认后，窗口向前滑动

**生活类比**：像**发微信**，你可以连续发多条消息，不用等对方回复每一条。

## 5.7 核心知识点总结

| 知识点 | 说明 |
|--------|------|
| 端口号 | 16 位，标识应用程序 |
| UDP | 无连接、不可靠、速度快 |
| TCP | 面向连接、可靠、全双工 |
| 三次握手 | 建立连接，同步序号 |
| 四次挥手 | 断开连接，全双工关闭 |
| TIME_WAIT | 等待 2MSL，确保可靠断开 |
| 滑动窗口 | 流量控制，提高利用率 |

## 5.8 新手常见误区

### 误区 1："TCP 三次握手可以简化为两次"

**错！** 两次握手无法防止历史连接，也无法同步双方的初始序号。第三次握手是确认服务器的 SYN 被正确接收。

### 误区 2："UDP 完全不可靠，所以没用"

不对。UDP 虽然不保证可靠性，但速度快、开销小，适合实时应用。视频通话、在线游戏等场景更需要低延迟，而不是绝对可靠。

### 误区 3："端口号可以随意使用"

不准确。0-1023 是熟知端口，需要管理员权限才能使用；1024-49151 是注册端口，建议按标准使用；49152-65535 是动态端口，客户端可以随意使用。

### 误区 4："TCP 连接建立后，立即开始传输数据"

不对。三次握手只是建立连接，还需要等待应用层准备好数据。实际传输数据是在连接建立之后。
