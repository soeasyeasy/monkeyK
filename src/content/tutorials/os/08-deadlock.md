# 第八章：死锁处理

## 本章导读

在学这一章之前，你可能会有这些疑问：

- 什么是死锁？为什么程序会"卡住"不动？
- 死锁是怎么产生的？需要满足什么条件？
- 操作系统是怎么防止死锁的？银行家算法是什么？
- 如果死锁真的发生了，系统能怎么办？

这一章就是为了解答这些问题。我们会先搞清楚 **死锁的概念和必要条件**，然后学习四种处理策略：忽略、预防、避免（银行家算法）、检测与恢复。学完这章，你就能理解操作系统是如何应对这个经典难题的。

---

## 1 为什么需要处理死锁？

### 痛点分析

想象一下这些场景：

- 你在电脑上同时打开两个文档，文档 A 锁住了打印机等扫描仪，文档 B 锁住了扫描仪等打印机。结果两个文档都卡住了，什么都打不了。
- 数据库里，事务 A 锁住了表 X 等表 Y，事务 B 锁住了表 Y 等表 X。两个事务互相等待，永远完成不了。
- 四辆车同时到达十字路口，每辆车都在等右边的车先走，结果谁也走不了。

这些场景的共同点是：**多个执行流互相等待对方持有的资源，所有人都卡住了**。这就是死锁。

### 解决方案

操作系统有四种应对死锁的策略：

1. **忽略**：假装死锁不存在（大多数操作系统的做法）
2. **预防**：破坏死锁的必要条件，让死锁不可能发生
3. **避免**：动态检查资源分配，确保系统不会进入危险状态
4. **检测与恢复**：允许死锁发生，检测到后想办法解除

> **一句话总结**：死锁是并发编程中的"顽疾"，操作系统用不同策略来应对它。

---

## 2 死锁的概念

**死锁（Deadlock）** 是指两个或多个进程因竞争资源而相互等待，导致所有进程都无法继续执行的状态。

打个比方：

> 就像两个人在窄路上相遇，谁也不肯退让，结果两个人都走不了。

### 死锁示例

```
进程 A 持有打印机，等待磁盘
进程 B 持有磁盘，等待打印机
→ 两个进程都在等待，无法继续
```

```
┌──────────┐  等待磁盘   ┌──────────┐
│  进程 A   │ ─────────> │  进程 B   │
│ 持有打印机 │            │  持有磁盘  │
└──────────┘ <───────── └──────────┘
             等待打印机
```

### 生活中的死锁

| 场景 | 描述 | 类比 |
| --- | --- | --- |
| 交通堵塞 | 四辆车在十字路口互相等待 | 谁也不肯先走 |
| 两个人过桥 | 两人从两端上桥，在中间相遇，都不退让 | 窄桥只能过一人 |
| 数据库事务 | 事务 A 锁表 X 等表 Y，事务 B 锁表 Y 等表 X | 互相持有对方需要的 |

---

## 3 死锁的必要条件

死锁的发生必须同时满足以下四个条件（Coffman 条件），缺一不可：

| 条件 | 说明 | 生活类比 |
| --- | --- | --- |
| 互斥（Mutual Exclusion） | 资源一次只能被一个进程使用 | 打印机一次只能一个人用 |
| 持有并等待（Hold and Wait） | 进程持有至少一个资源，同时等待获取其他资源 | 拿着碗还想要筷子 |
| 不可抢占（No Preemption） | 资源只能由持有者主动释放，不能被强制剥夺 | 不能从别人手里抢东西 |
| 循环等待（Circular Wait） | 存在一个进程的循环等待链 | A 等 B，B 等 C，C 等 A |

::: info
这四个条件是死锁的**必要条件**，即死锁发生时这些条件一定成立。但不是**充分条件**——即使四个条件都满足，也不一定发生死锁。就像具备了起火的所有条件，但如果没有火星，也不会着火。
:::

---

## 4 死锁处理策略概览

操作系统有四种处理死锁的策略：

| 策略 | 思路 | 特点 | 生活类比 |
| --- | --- | --- | --- |
| 忽略 | 假装死锁不存在 | 大多数 OS 的做法（如 Linux、Windows） | 鸵鸟策略，把头埋进沙子 |
| 预防 | 破坏四个必要条件之一 | 保守，资源利用率低 | 严格安检，不让危险品上车 |
| 避免 | 动态检查资源分配状态 | 需要预知资源需求 | 银行放贷前检查余额 |
| 检测与恢复 | 允许死锁发生，检测后恢复 | 运行时开销 | 定期体检，发现病就治 |

## 5 死锁预防

通过破坏四个必要条件之一来预防死锁。

### 破坏互斥条件

- 将独占资源改为可共享资源
- 例如：使用 spooling 技术让多个进程共享打印机
- 局限性：很多资源本质上不可共享（如文件锁）

打个比方：

> 把独木桥改建成多车道大桥，大家就能同时通过了。但有些资源（如打印机）本质上就是独占的，很难共享。

### 破坏持有并等待条件

- 进程在开始执行前一次性申请所有资源
- 或者进程在申请新资源前必须先释放所有已持有的资源

```c
// 方式一：一次性申请所有资源
request(R1, R2, R3);  // 同时申请三个资源
// 只有全部可用时才分配，否则一个都不给

// 方式二：逐步申请
release_all();          // 先释放所有已持有的资源
request(R1, R3);        // 重新申请需要的资源
```

::: tip
破坏持有并等待的缺点是**资源利用率低**和**可能饥饿**——进程可能长时间得不到所有需要的资源。就像你必须同时拿到碗、筷子和勺子才能开始吃饭，如果勺子被别人拿着，你就只能干等着。
:::

### 破坏不可抢占条件

- 如果进程不能立即获得所需资源，则释放已持有的所有资源
- 或者在等待其他资源时，已持有的资源可以被抢占

```c
// 进程持有 R1 和 R2，申请 R3
// 如果 R3 不可用：
release(R1);    // 释放已持有的 R1
release(R2);    // 释放已持有的 R2
wait(R1, R2, R3);  // 重新申请所有三个资源
```

打个比方：

> 你拿着碗和盘子，还想要筷子。如果筷子没有了，你必须把碗和盘子放回去，然后重新排队等所有餐具。

### 破坏循环等待条件

- 对所有资源类型进行线性排序
- 进程只能按递增顺序申请资源

```
资源排序：R1 < R2 < R3

合法：先申请 R1，再申请 R2
非法：先申请 R2，再申请 R1
```

打个比方：

> 规定所有人必须按编号从小到大借用工具。如果你已经借了 2 号工具，就只能借 3 号或更大的，不能回头借 1 号。这样就打破了循环等待的可能。

::: info
破坏循环等待条件是实践中较常用的方法。Java 中的 `synchronized` 嵌套锁就建议按固定顺序获取，以避免死锁。
:::

## 6 死锁避免

死锁避免允许四个必要条件存在，但在运行时动态检查资源分配状态，确保系统不会进入不安全状态。

打个比方：

> 就像银行放贷款：银行不会把所有钱都贷出去，而是留一部分准备金。每次有人来贷款，银行都会检查：贷完这笔钱后，剩下的钱够不够让至少一个客户还清贷款？如果够，就贷；如果不够，就拒绝。

### 安全状态

- **安全状态**：存在至少一个资源分配序列，使得所有进程都能完成
- **不安全状态**：不存在这样的序列（但不一定已经死锁）

```
安全状态 → 可以保证所有进程完成（像银行有足够的准备金）
不安全状态 → 可能死锁，但不一定（像银行资金紧张但还没破产）
死锁状态 → 一定死锁（像银行已经破产了）
```

### 银行家算法（Banker's Algorithm）

银行家算法由 Dijkstra 提出，是最著名的死锁避免算法。

#### 数据结构

```c
// 假设系统有 n 个进程，m 种资源类型

int Available[m];           // 每种资源的可用数量（银行还剩多少钱）
int Max[n][m];              // 每个进程对每种资源的最大需求（每个客户最多要贷多少）
int Allocation[n][m];       // 每个进程当前已分配的资源数量（已经贷给每个客户多少）
int Need[n][m];             // 每个进程还需要的资源数量（每个客户还差多少）
                            // 计算公式：Need[i][j] = Max[i][j] - Allocation[i][j]
```

#### 安全性检查算法

```c
// 检查系统是否处于安全状态
boolean isSafe() {
    int Work[m] = Available;        // 工作向量：当前可用的资源数量
    boolean Finish[n] = {false};    // 完成标记：每个进程是否已完成

    // 反复寻找可以完成的进程
    boolean found = true;
    while (found) {
        found = false;
        for (int i = 0; i < n; i++) {
            // 如果进程 i 还没完成，且它的需求小于等于当前可用资源
            if (!Finish[i] && Need[i] <= Work) {
                // 进程 i 可以完成
                Work += Allocation[i];  // 假设进程 i 完成后释放所有资源
                Finish[i] = true;       // 标记进程 i 已完成
                found = true;           // 继续寻找下一个
            }
        }
    }

    // 如果所有进程都能完成，则系统处于安全状态
    return all(Finish == true);
}
```

#### 资源请求算法

```c
// 进程 i 请求资源
boolean request(int i, int Request[m]) {
    // 第一步：检查请求是否合法（不能超过最大需求）
    if (Request > Need[i]) {
        error("进程超过了最大需求");
        return false;
    }

    // 第二步：检查是否有足够资源（不能超出可用量）
    if (Request > Available) {
        // 资源不够，进程需要等待
        return false;
    }

    // 第三步：试探性分配（先假装同意，看看会不会出问题）
    Available -= Request;           // 可用资源减少
    Allocation[i] += Request;       // 分配给进程 i
    Need[i] -= Request;             // 进程 i 的需求减少

    // 第四步：检查安全性（分配后系统还安全吗？）
    if (isSafe()) {
        return true;    // 安全，正式分配
    } else {
        // 不安全，回滚（撤销刚才的分配）
        Available += Request;
        Allocation[i] -= Request;
        Need[i] += Request;
        // 进程需要等待
        return false;
    }
}
```

### 银行家算法示例

假设系统有 5 个进程（P0-P4），3 种资源（A、B、C），总数分别为 10、5、7。

初始状态：

| 进程 | Max (A,B,C) | Allocation (A,B,C) | Need (A,B,C) |
| --- | --- | --- | --- |
| P0 | 7,5,3 | 0,1,0 | 7,4,3 |
| P1 | 3,2,2 | 2,0,0 | 1,2,2 |
| P2 | 9,0,2 | 3,0,2 | 6,0,0 |
| P3 | 2,2,2 | 2,1,1 | 0,1,1 |
| P4 | 4,3,3 | 0,0,2 | 4,3,1 |

Available = (10-7, 5-2, 7-5) = **(3, 3, 2)**

安全性检查：

```
Work = (3, 3, 2)    // 初始可用资源

第 1 轮：
  P3: Need(0,1,1) <= Work(3,3,2) 满足 → Work = (3,3,2) + (2,1,1) = (5,4,3)
  P4: Need(4,3,1) <= Work(5,4,3) 满足 → Work = (5,4,3) + (0,0,2) = (5,4,5)
  P1: Need(1,2,2) <= Work(5,4,5) 满足 → Work = (5,4,5) + (2,0,0) = (7,4,5)
  P0: Need(7,4,3) <= Work(7,4,5) 满足 → Work = (7,4,5) + (0,1,0) = (7,5,5)
  P2: Need(6,0,0) <= Work(7,5,5) 满足 → Work = (7,5,5) + (3,0,2) = (10,5,7)

安全序列：<P3, P4, P1, P0, P2> → 系统处于安全状态
```

::: tip
银行家算法需要预先知道每个进程的最大资源需求，且进程数量固定，这在现实中很难满足。因此它主要用于理论教学和特定场景（如数据库锁管理）。
:::

## 7 死锁检测与恢复

### 死锁检测

#### 每种资源一个实例

使用**资源分配图（Resource Allocation Graph, RAG）** 来检测死锁。

```
进程 ──申请边──> 资源     （进程在等资源）
资源 ──分配边──> 进程     （资源被进程持有）

如果图中存在环，则发生死锁
```

打个比方：

> 就像画一张关系图：谁拿着什么、谁在等什么。如果画出来发现形成了一个圈（A 等 B，B 等 C，C 等 A），那就是死锁了。

#### 每种资源多个实例

使用类似银行家算法的检测算法：

```c
// 检测死锁的算法
boolean detectDeadlock() {
    int Work[m] = Available;          // 当前可用资源
    boolean Finish[n];                // 每个进程的完成标记

    // 初始化 Finish：已分配资源为 0 的进程标记为已完成
    for (int i = 0; i < n; i++) {
        Finish[i] = (Allocation[i] == 0);  // 没持有资源的视为已完成
    }

    // 反复寻找可以完成的进程
    boolean found = true;
    while (found) {
        found = false;
        for (int i = 0; i < n; i++) {
            // 如果进程 i 还没完成，且它的请求小于等于当前可用资源
            if (!Finish[i] && Request[i] <= Work) {
                Work += Allocation[i];     // 假设进程 i 完成后释放资源
                Finish[i] = true;          // 标记为已完成
                found = true;
            }
        }
    }

    // 所有 Finish[i] == false 的进程都处于死锁状态
    return any(Finish == false);  // 如果有进程无法完成，说明存在死锁
}
```

### 死锁恢复

检测到死锁后，可以采取以下恢复措施：

| 方法 | 说明 | 代价 | 生活类比 |
| --- | --- | --- | --- |
| 终止所有死锁进程 | 简单粗暴，全部杀掉重来 | 高 | 把所有人都赶下桥 |
| 逐个终止进程 | 每终止一个就检测是否解除死锁 | 中 | 一次让一个人退回去 |
| 资源抢占 | 从死锁进程中抢占资源给其他进程 | 可能引起回滚 | 强制从某人手里拿东西 |
| 进程回滚 | 将进程回滚到之前的安全状态 | 需要保存检查点 | 让所有人退回起点重新来 |

#### 终止进程的选择标准

选择终止哪个进程时，需要考虑以下因素：

| 因素 | 说明 |
| --- | --- |
| 优先级 | 低优先级进程先终止 |
| 已执行时间 | 已执行时间短的进程先终止（沉没成本低） |
| 已分配资源 | 占用资源少的进程先终止（释放的资源少但影响小） |
| 交互性 | 非交互式进程先终止（用户感知不到） |
| 完成难度 | 预计剩余工作量大的进程先终止 |

::: info
大多数操作系统（如 Linux、Windows）采用**鸵鸟策略**——忽略死锁问题。因为死锁发生的概率较低，且检测和恢复的开销较大。但在数据库系统中，死锁检测是标配功能。
:::

## 8 死锁处理策略对比

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 忽略 | 假装死锁不存在 | 零开销 | 死锁时系统卡死 | 通用操作系统 |
| 预防 | 破坏必要条件 | 死锁不可能发生 | 资源利用率低 | 嵌入式系统 |
| 避免 | 银行家算法 | 安全且高效 | 需要预知资源需求 | 数据库系统 |
| 检测恢复 | 允许死锁，事后处理 | 不影响正常运行 | 检测有开销 | 数据库事务 |

## 9 新手常见误区

### 误区 1："死锁的四个必要条件都满足，就一定会死锁"

**错！** 四个条件是必要条件，不是充分条件：

1. 必要条件意味着：死锁发生时，这些条件一定成立
2. 但即使四个条件都成立，也不一定发生死锁
3. 就像具备了起火的条件（可燃物、氧气、温度），但没有火星也不会着火

正确做法：理解必要条件和充分条件的区别，四个条件同时满足只是"可能"死锁。

### 误区 2："死锁预防比死锁避免更好"

**不是的！** 两者各有优缺点：

1. 死锁预防：通过破坏条件来防止死锁，但资源利用率低，限制多
2. 死锁避免：允许条件存在，但动态检查确保安全，更灵活
3. 预防像"一刀切"，避免更"智能"

正确做法：根据系统需求选择，实时系统可能用预防，通用系统可能用避免。

### 误区 3："银行家算法在实际系统中广泛使用"

**不是的！** 银行家算法主要用于教学：

1. 它要求预先知道每个进程的最大资源需求，现实中很难做到
2. 它要求进程数量固定，但实际系统中进程是动态创建和销毁的
3. 它的开销较大，不适合高性能系统

正确做法：理解银行家算法的思想（安全状态检查），但知道它的实际应用有限。

### 误区 4："死锁检测的开销可以忽略不计"

**不是的！** 死锁检测有显著开销：

1. 每次资源分配都需要运行检测算法，时间复杂度为 O(n*n)
2. 检测频率越高，开销越大；频率越低，死锁持续时间越长
3. 需要在检测开销和死锁影响之间权衡

正确做法：根据系统特点设置合理的检测频率，不是越频繁越好。

### 误区 5："终止进程是恢复死锁的最佳方式"

**不一定！** 终止进程虽然简单，但代价可能很高：

1. 进程可能已经执行了很长时间，终止意味着所有工作白费
2. 可能丢失重要数据
3. 用户体验差

正确做法：根据情况选择恢复策略，优先考虑回滚到检查点，终止进程是最后手段。

## 10 动手练习

### 练习 1：基础练习 - 死锁条件判断

判断以下场景是否构成死锁，并说明满足了哪些必要条件：

```
进程 A 持有打印机，等待扫描仪
进程 B 持有扫描仪，等待打印机
```

<details>
<summary>点击查看答案</summary>

**是的，这是一个死锁场景。**

满足的四个必要条件：

1. **互斥**：打印机和扫描仪一次只能被一个进程使用
2. **持有并等待**：进程 A 持有打印机并等待扫描仪，进程 B 持有扫描仪并等待打印机
3. **不可抢占**：打印机和扫描仪不能被强制从进程中夺走
4. **循环等待**：A 等待 B 持有的资源，B 等待 A 持有的资源，形成循环

四个条件同时满足，因此发生死锁。

</details>

### 练习 2：进阶练习 - 银行家算法安全性检查

假设系统有 3 个进程（P0、P1、P2），2 种资源（A、B），总数分别为 10、5。

当前状态：

| 进程 | Max (A,B) | Allocation (A,B) | Need (A,B) |
| --- | --- | --- | --- |
| P0 | 5,3 | 2,1 | 3,2 |
| P1 | 4,2 | 1,0 | 3,2 |
| P2 | 3,2 | 1,1 | 2,1 |

Available = (10-4, 5-2) = **(6, 3)**

请判断系统是否处于安全状态，如果是，给出安全序列。

<details>
<summary>点击查看答案</summary>

**安全性检查过程：**

```
Work = (6, 3)    // 初始可用资源

第 1 轮：
  P0: Need(3,2) <= Work(6,3) 满足 → Work = (6,3) + (2,1) = (8,4)
  P1: Need(3,2) <= Work(8,4) 满足 → Work = (8,4) + (1,0) = (9,4)
  P2: Need(2,1) <= Work(9,4) 满足 → Work = (9,4) + (1,1) = (10,5)

安全序列：<P0, P1, P2> → 系统处于安全状态
```

**验证：**
- P0 完成后释放 (2,1)，Work 变为 (8,4)
- P1 完成后释放 (1,0)，Work 变为 (9,4)
- P2 完成后释放 (1,1)，Work 变为 (10,5)，等于总资源数

所有进程都能完成，系统处于安全状态。

</details>

### 练习 3（挑战）：综合练习 - 死锁预防策略分析

假设系统有 4 种资源（R1 < R2 < R3 < R4），3 个进程：

- P1 已持有 R2，申请 R4
- P2 已持有 R3，申请 R1
- P3 已持有 R1，申请 R3

请分析：
1. 当前是否可能发生死锁？
2. 如果使用"资源有序分配"策略（只能按递增顺序申请），哪些申请是合法的？
3. 如何修改申请顺序来避免死锁？

<details>
<summary>点击查看答案</summary>

**1. 当前是否可能发生死锁？**

分析循环等待：
- P1 持有 R2，等待 R4
- P2 持有 R3，等待 R1
- P3 持有 R1，等待 R3

P2 和 P3 形成了循环等待：P2 等待 P3 持有的 R1，P3 等待 P2 持有的 R3。
**是的，可能发生死锁。**

**2. 使用资源有序分配策略（只能按递增顺序申请）：**

资源排序：R1 < R2 < R3 < R4

- P1：已持有 R2，申请 R4 → R2 < R4，**合法**
- P2：已持有 R3，申请 R1 → R3 > R1，**非法**（不能回头申请更小的）
- P3：已持有 R1，申请 R3 → R1 < R3，**合法**

**3. 如何修改申请顺序来避免死锁？**

P2 需要修改申请顺序：
- 原来：先申请 R3，再申请 R1（非法）
- 修改：先申请 R1，再申请 R3（合法）

修改后：
- P1：先申请 R2，再申请 R4（合法）
- P2：先申请 R1，再申请 R3（合法）
- P3：先申请 R1，再申请 R3（合法）

由于所有进程都按递增顺序申请资源，不可能形成循环等待链，因此死锁被预防。

</details>
