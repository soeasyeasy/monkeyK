# 第八章：死锁处理

## 死锁的概念

**死锁（Deadlock）** 是指两个或多个进程因竞争资源而相互等待，导致所有进程都无法继续执行的状态。

### 死锁示例

```
进程 A 持有打印机，等待磁盘
进程 B 持有磁盘，等待打印机
→ 两个进程都在等待，无法继续
```

```
┌──────────┐  等待磁盘   ┌──────────┐
│  进程 A   │ ─────────> │  进程 B   │
│ 持有打印机 │            │  持有磁盘  │
└──────────┘ <───────── └──────────┘
             等待打印机
```

### 生活中的死锁

| 场景 | 描述 |
| --- | --- |
| 交通堵塞 | 四辆车在十字路口互相等待 |
| 两个人过桥 | 两人从两端上桥，在中间相遇，都不退让 |
| 数据库事务 | 事务 A 锁表 X 等表 Y，事务 B 锁表 Y 等表 X |

## 死锁的必要条件

死锁的发生必须同时满足以下四个条件（Coffman 条件）：

| 条件 | 说明 |
| --- | --- |
| 互斥（Mutual Exclusion） | 资源一次只能被一个进程使用 |
| 持有并等待（Hold and Wait） | 进程持有至少一个资源，同时等待获取其他资源 |
| 不可抢占（No Preemption） | 资源只能由持有者主动释放，不能被强制剥夺 |
| 循环等待（Circular Wait） | 存在一个进程的循环等待链 |

::: info
这四个条件是死锁的**必要条件**，即死锁发生时这些条件一定成立。但不是**充分条件**——即使四个条件都满足，也不一定发生死锁。
:::

## 死锁处理策略

操作系统有四种处理死锁的策略：

| 策略 | 思路 | 特点 |
| --- | --- | --- |
| 忽略 | 假装死锁不存在 | 大多数 OS 的做法（如 Linux、Windows） |
| 预防 | 破坏四个必要条件之一 | 保守，资源利用率低 |
| 避免 | 动态检查资源分配状态 | 需要预知资源需求 |
| 检测与恢复 | 允许死锁发生，检测后恢复 | 运行时开销 |

## 死锁预防

通过破坏四个必要条件之一来预防死锁。

### 破坏互斥条件

- 将独占资源改为可共享资源
- 例如：使用 spooling 技术让多个进程共享打印机
- 局限性：很多资源本质上不可共享（如文件锁）

### 破坏持有并等待条件

- 进程在开始执行前一次性申请所有资源
- 或者进程在申请新资源前必须先释放所有已持有的资源

```c
// 方式一：一次性申请所有资源
request(R1, R2, R3);  // 同时申请三个资源
// 只有全部可用时才分配

// 方式二：逐步申请
release_all();          // 先释放所有资源
request(R1, R3);        // 重新申请
```

::: tip
破坏持有并等待的缺点是**资源利用率低**和**可能饥饿**——进程可能长时间得不到所有需要的资源。
:::

### 破坏不可抢占条件

- 如果进程不能立即获得所需资源，则释放已持有的所有资源
- 或者在等待其他资源时，已持有的资源可以被抢占

```c
// 进程持有 R1 和 R2，申请 R3
// 如果 R3 不可用：
release(R1);
release(R2);
wait(R1, R2, R3);  // 重新申请所有资源
```

### 破坏循环等待条件

- 对所有资源类型进行线性排序
- 进程只能按递增顺序申请资源

```
资源排序：R1 < R2 < R3

合法：先申请 R1，再申请 R2
非法：先申请 R2，再申请 R1
```

::: info
破坏循环等待条件是实践中较常用的方法。Java 中的 `synchronized` 嵌套锁就建议按固定顺序获取，以避免死锁。
:::

## 死锁避免

死锁避免允许四个必要条件存在，但在运行时动态检查资源分配状态，确保系统不会进入不安全状态。

### 安全状态

- **安全状态**：存在至少一个资源分配序列，使得所有进程都能完成
- **不安全状态**：不存在这样的序列（但不一定已经死锁）

```
安全状态 → 可以保证所有进程完成
不安全状态 → 可能死锁，但不一定
死锁状态 → 一定死锁
```

### 银行家算法（Banker's Algorithm）

银行家算法由 Dijkstra 提出，是最著名的死锁避免算法。

#### 数据结构

```c
// 假设系统有 n 个进程，m 种资源类型

int Available[m];           // 每种资源的可用数量
int Max[n][m];              // 每个进程对每种资源的最大需求
int Allocation[n][m];       // 每个进程当前已分配的资源数量
int Need[n][m];             // 每个进程还需要的资源数量
                            // Need[i][j] = Max[i][j] - Allocation[i][j]
```

#### 安全性检查算法

```c
boolean isSafe() {
    int Work[m] = Available;        // 工作向量
    boolean Finish[n] = {false};    // 完成标记

    // 找到一个可以完成的进程
    boolean found = true;
    while (found) {
        found = false;
        for (int i = 0; i < n; i++) {
            if (!Finish[i] && Need[i] <= Work) {
                // 进程 i 可以完成
                Work += Allocation[i];  // 释放进程 i 的资源
                Finish[i] = true;
                found = true;
            }
        }
    }

    // 如果所有进程都能完成，则安全
    return all(Finish == true);
}
```

#### 资源请求算法

```c
boolean request(int i, int Request[m]) {
    // 1. 检查请求是否合法
    if (Request > Need[i]) {
        error("进程超过了最大需求");
        return false;
    }

    // 2. 检查是否有足够资源
    if (Request > Available) {
        // 等待
        return false;
    }

    // 3. 试探性分配
    Available -= Request;
    Allocation[i] += Request;
    Need[i] -= Request;

    // 4. 检查安全性
    if (isSafe()) {
        return true;    // 安全，正式分配
    } else {
        // 回滚
        Available += Request;
        Allocation[i] -= Request;
        Need[i] += Request;
        // 等待
        return false;
    }
}
```

### 银行家算法示例

假设系统有 5 个进程（P0-P4），3 种资源（A、B、C），总数分别为 10、5、7。

初始状态：

| 进程 | Max (A,B,C) | Allocation (A,B,C) | Need (A,B,C) |
| --- | --- | --- | --- |
| P0 | 7,5,3 | 0,1,0 | 7,4,3 |
| P1 | 3,2,2 | 2,0,0 | 1,2,2 |
| P2 | 9,0,2 | 3,0,2 | 6,0,0 |
| P3 | 2,2,2 | 2,1,1 | 0,1,1 |
| P4 | 4,3,3 | 0,0,2 | 4,3,1 |

Available = (10-7, 5-2, 7-5) = **(3, 3, 2)**

安全性检查：

```
Work = (3, 3, 2)

第 1 轮：
  P3: Need(0,1,1) <= Work(3,3,2) ✅ → Work = (3,3,2) + (2,1,1) = (5,4,3)
  P4: Need(4,3,1) <= Work(5,4,3) ✅ → Work = (5,4,3) + (0,0,2) = (5,4,5)
  P1: Need(1,2,2) <= Work(5,4,5) ✅ → Work = (5,4,5) + (2,0,0) = (7,4,5)
  P0: Need(7,4,3) <= Work(7,4,5) ✅ → Work = (7,4,5) + (0,1,0) = (7,5,5)
  P2: Need(6,0,0) <= Work(7,5,5) ✅ → Work = (7,5,5) + (3,0,2) = (10,5,7)

安全序列：<P3, P4, P1, P0, P2> → 系统处于安全状态
```

::: tip
银行家算法需要预先知道每个进程的最大资源需求，且进程数量固定，这在现实中很难满足。因此它主要用于理论教学和特定场景（如数据库锁管理）。
:::

## 死锁检测与恢复

### 死锁检测

#### 每种资源一个实例

使用**资源分配图（Resource Allocation Graph, RAG）** 来检测死锁。

```
进程 ──申请边──> 资源
资源 ──分配边──> 进程

如果图中存在环，则发生死锁
```

#### 每种资源多个实例

使用类似银行家算法的检测算法：

```c
boolean detectDeadlock() {
    int Work[m] = Available;
    boolean Finish[n];

    // 初始化 Finish
    for (int i = 0; i < n; i++) {
        Finish[i] = (Allocation[i] == 0);
    }

    boolean found = true;
    while (found) {
        found = false;
        for (int i = 0; i < n; i++) {
            if (!Finish[i] && Request[i] <= Work) {
                Work += Allocation[i];
                Finish[i] = true;
                found = true;
            }
        }
    }

    // 所有 Finish[i] == false 的进程都处于死锁状态
    return any(Finish == false);
}
```

### 死锁恢复

检测到死锁后，可以采取以下恢复措施：

| 方法 | 说明 | 代价 |
| --- | --- | --- |
| 终止所有死锁进程 | 简单粗暴 | 高 |
| 逐个终止进程 | 每终止一个就检测是否解除死锁 | 中 |
| 资源抢占 | 从死锁进程中抢占资源给其他进程 | 可能引起回滚 |
| 进程回滚 | 将进程回滚到之前的安全状态 | 需要保存检查点 |

#### 终止进程的选择标准

| 因素 | 说明 |
| --- | --- |
| 优先级 | 低优先级进程先终止 |
| 已执行时间 | 已执行时间短的进程先终止 |
| 已分配资源 | 占用资源少的进程先终止 |
| 交互性 | 非交互式进程先终止 |
| 完成难度 | 预计剩余工作量大的进程先终止 |

::: info
大多数操作系统（如 Linux、Windows）采用**鸵鸟策略**——忽略死锁问题。因为死锁发生的概率较低，且检测和恢复的开销较大。但在数据库系统中，死锁检测是标配功能。
:::

## 本章小结

- 死锁是多个进程互相等待资源的状态
- 死锁的四个必要条件：互斥、持有并等待、不可抢占、循环等待
- **死锁预防**通过破坏四个必要条件之一来防止死锁
- **死锁避免**通过银行家算法动态检查资源分配，确保系统处于安全状态
- **死锁检测与恢复**允许死锁发生，检测到后通过终止进程或抢占资源来恢复
- 大多数通用操作系统选择忽略死锁，而数据库等关键系统会实现死锁检测
