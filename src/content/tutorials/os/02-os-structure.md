# 第二章：操作系统结构

## 本章导读

在学这一章之前，你可能会有这些疑问：

- 为什么我的程序不能直接操作硬件？非要通过操作系统？
- 系统调用是什么？它和普通函数有什么区别？
- 中断是什么？为什么键盘按一下电脑就能响应？
- 内核态和用户态到底有什么区别？切换的时候发生了什么？

这一章就是为了解答这些问题。我们会先搞清楚为什么需要内核态和用户态，再学习系统调用和中断机制，最后看看操作系统的几种结构。学完之后，你会理解操作系统是怎么保护系统资源、怎么响应外部事件的。

---

## 2.1 为什么需要内核态和用户态？

### 痛点分析

想象一下，如果所有程序都能直接操作硬件，会发生什么？

1. 一个有 Bug 的程序可能直接覆盖操作系统的代码，导致系统崩溃
2. 一个恶意程序可以直接读取其他程序的内存，窃取密码
3. 两个程序同时写硬盘，数据就乱了
4. 一个程序死循环了，整个电脑就卡死了

这就好比一栋大楼没有门禁，任何人都能进配电室、机房、财务室。一个熊孩子乱按按钮，整栋楼就停电了。

### 解决方案

操作系统引入了"双模式"机制：内核态和用户态。

打个比方：

> 内核态就像大楼的配电室，只有物业（操作系统）能进。用户态就像大楼的各个房间，租户（用户程序）可以在里面自由活动，但不能进配电室乱搞。租户需要用电，得找物业（通过系统调用）来操作。

```
没有双模式：所有程序都能直接操作硬件
  程序A → 直接操作内存 → 可能覆盖程序B的数据
  程序B → 直接操作硬盘 → 可能和程序C冲突

有了双模式：程序只能在自己的空间里玩
  程序A（用户态） → 请求操作系统（内核态） → 操作系统安全地操作硬件
  程序B（用户态） → 请求操作系统（内核态） → 操作系统安全地操作硬件
```

> 一句话总结：内核态和用户态是操作系统的安全机制，防止用户程序乱搞。

## 2.2 内核态与用户态

现代操作系统通过双模式（Dual Mode）运行来保护系统资源。CPU 提供了两种不同的执行模式：

| 模式 | 别名 | 权限 | 运行内容 | 生活化类比 |
| --- | --- | --- | --- | --- |
| 内核态（Kernel Mode） | 特权模式、管态 | 可执行所有指令，访问所有资源 | 操作系统内核代码 | 像物业，能进配电室、机房 |
| 用户态（User Mode） | 非特权模式、目态 | 只能执行非特权指令 | 用户程序 | 像租户，只能在自己的房间里 |

### 模式切换

从用户态切换到内核态只有三种途径：

1. 系统调用（主动请求）
2. 中断（外部事件）
3. 异常（程序出错）

```
用户程序执行（用户态）
    |
    |-- 系统调用 --> 陷入内核 --> 内核态执行
    |                                |
    |                                |-- 执行完毕 --> 返回用户态
    |
    |-- 中断发生 --> 保存现场 --> 内核态执行中断处理
    |                                |
    |                                |-- 处理完毕 --> 恢复现场 --> 返回用户态
    |
    |-- 执行特权指令 --> 触发异常 --> 操作系统终止程序
```

打个比方：

> 你（用户程序）在家里（用户态）想用电，有两种方式：
> 1. 主动找物业（系统调用）："帮我开一下灯"
> 2. 突然停电了（中断），物业自动来处理
> 3. 你试图自己进配电室（执行特权指令），被保安拦住（触发异常）

```c
// 示例：用户程序不能直接操作硬件
#include <stdio.h>

int main() {
    // 错误做法：试图直接操作硬件端口
    // outb(0x3f8, 'A');  // 这会触发异常，程序被终止
    
    // 正确做法：通过系统调用
    // write() 会触发系统调用，切换到内核态，由操作系统操作硬件
    write(1, "A", 1);  // 输出字符 'A'
    
    return 0;
}
```

## 2.3 系统调用

系统调用（System Call）是用户程序请求操作系统服务的接口。它是用户态与内核态之间的桥梁。

打个比方：

> 系统调用就像餐厅的点餐窗口。你（用户程序）不能直接进厨房（内核）做菜，只能通过点餐窗口（系统调用）告诉服务员（操作系统）你要什么菜。

### 常见的系统调用分类

| 类别 | 示例 | 说明 | 生活化类比 |
| --- | --- | --- | --- |
| 进程控制 | `fork()`, `exit()`, `wait()` | 创建、终止、等待进程 | 像开新店、关店、等顾客 |
| 文件管理 | `open()`, `read()`, `write()`, `close()` | 文件的打开、读写、关闭 | 像借书、看书、还书 |
| 设备管理 | `ioctl()`, `read()`, `write()` | 设备请求和控制 | 像申请使用打印机 |
| 信息维护 | `getpid()`, `alarm()`, `sleep()` | 获取/设置系统信息 | 像查自己的身份证、设闹钟 |
| 通信 | `pipe()`, `shmget()`, `socket()` | 进程间通信 | 像打电话、发短信 |
| 保护 | `chmod()`, `chown()` | 访问控制 | 像改密码、改权限 |

### 系统调用的执行过程

以 Linux 下 `write()` 系统调用为例：

```c
#include <unistd.h>  // 包含 POSIX 标准函数声明
#include <stdio.h>   // 包含标准输入输出函数

int main() {
    char msg[] = "Hello, OS!\n";  // 定义一个字符串，包含要输出的内容
    // write 是一个系统调用
    // 参数1：文件描述符，STDOUT_FILENO 表示标准输出（屏幕）
    // 参数2：缓冲区，指向要输出的数据
    // 参数3：字节数，要输出的字符数量
    write(STDOUT_FILENO, msg, sizeof(msg) - 1);  // -1 是因为不输出字符串末尾的 '\0'
    return 0;  // 程序正常退出
}
```

执行流程：

```
1. 用户程序调用 write()（用户态 C 库函数）
   你在餐厅说："我要一份炒饭"
   
2. C 库将系统调用号存入寄存器（如 eax = 4）
   服务员记下："炒饭，编号 4"
   
3. 执行 trap 指令（如 int 0x80 或 syscall）
   服务员通过对讲机呼叫厨房
   
4. CPU 切换到内核态，跳转到系统调用处理入口
   厨房接到订单，开始准备
   
5. 内核根据调用号查表，找到对应的处理函数 sys_write()
   厨师根据订单号找到对应的菜谱
   
6. 执行实际的 I/O 操作
   厨师开始炒菜
   
7. 将结果存入寄存器，切换回用户态
   菜做好了，服务员端给你
   
8. 用户程序继续执行
   你继续吃饭
```

### POSIX 与 Win32 API

不同的操作系统提供不同的系统调用接口：

| 标准 | 适用系统 | 示例 | 特点 |
| --- | --- | --- | --- |
| POSIX | UNIX/Linux/macOS | `fork()`, `pthread_create()`, `open()` | 跨平台，开源系统都用 |
| Win32 API | Windows | `CreateProcess()`, `CreateFile()`, `CreateThread()` | Windows 专用 |

```c
// POSIX 创建进程（Linux/macOS）
#include <unistd.h>  // 包含 fork() 函数声明

int main() {
    pid_t pid = fork();  // 创建子进程，返回子进程的 PID
    
    if (pid == 0) {
        // 子进程执行的代码
        printf("我是子进程\n");
    } else {
        // 父进程执行的代码
        printf("我是父进程\n");
    }
    
    return 0;
}
```

```c
// Win32 创建进程（Windows）
#include <windows.h>  // 包含 Windows API 函数声明

int main() {
    STARTUPINFO si = { sizeof(si) };  // 启动信息结构体
    PROCESS_INFORMATION pi;           // 进程信息结构体
    
    BOOL result = CreateProcess(
        NULL,           // 应用名称，NULL 表示从命令行获取
        "notepad.exe",  // 命令行，要启动的程序
        NULL, NULL,     // 安全属性，NULL 表示默认
        FALSE,          // 不继承句柄
        0,              // 创建标志，0 表示默认
        NULL, NULL,     // 环境/目录，NULL 表示继承父进程
        &si, &pi        // 启动信息/进程信息，用于接收返回结果
    );
    
    if (result) {
        printf("进程创建成功\n");
        CloseHandle(pi.hProcess);  // 关闭进程句柄
        CloseHandle(pi.hThread);   // 关闭线程句柄
    }
    
    return 0;
}
```

## 2.4 中断机制

中断是操作系统响应外部事件的核心机制。没有中断，操作系统就无法及时响应 I/O 完成、硬件错误等事件。

打个比方：

> 中断就像你在家写作业，突然门铃响了（中断信号）。你放下笔（保存现场），去开门（执行中断处理），看到是快递（处理事件），签收了快递（完成处理），然后回到书桌继续写作业（恢复现场）。

### 中断的分类

| 类型 | 说明 | 示例 | 生活化类比 |
| --- | --- | --- | --- |
| 外中断（硬件中断） | 由 CPU 外部的硬件设备发出 | 键盘输入、定时器中断、I/O 完成 | 像门铃响、电话响 |
| 内中断（异常） | 由 CPU 执行指令时内部产生 | 除零错误、缺页异常、非法指令 | 像你写作业时发现算错了 |
| 陷入（Trap） | 由程序主动执行 trap 指令产生 | 系统调用 | 像你主动按门铃叫外卖 |

```
中断来源分类：

+-----------------------------------------+
|                 中断                     |
+--------------+--------------------------+
|   外中断      |        内中断            |
|  (异步)      |       (同步)             |
+--------------+------------+-------------+
|  可屏蔽中断   |  不可屏蔽  |   陷入      |
|  (键盘/定时器) |  (硬件故障) |  (系统调用)  |
+--------------+------------+-------------+
```

### 中断处理过程

```
1. 设备发出中断信号
   快递小哥按门铃
   
2. CPU 完成当前指令后检查中断请求
   你写完当前这道题，听到门铃
   
3. CPU 保存当前程序计数器（PC）和寄存器状态
   你记下写到哪一页、哪一题
   
4. CPU 根据中断向量表找到对应的处理程序入口
   你看门铃旁边的说明："快递去门口签收"
   
5. 执行中断服务程序（ISR）
   你去门口签收快递
   
6. 恢复被中断程序的现场
   你回到书桌，翻到刚才那一页
   
7. 继续执行被中断的程序
   你继续写作业
```

### 中断向量表

中断向量表（Interrupt Vector Table, IVT）存储了每个中断对应的处理程序入口地址。就像一本电话簿，每个中断号对应一个处理函数的地址。

| 中断号 | 类型 | 说明 | 生活化类比 |
| --- | --- | --- | --- |
| 0 | 异常 | 除零错误 | 像"数学错误"处理流程 |
| 6 | 异常 | 非法指令 | 像"无效操作"处理流程 |
| 13 | 异常 | 通用保护异常 | 像"权限错误"处理流程 |
| 14 | 异常 | 缺页异常 | 像"内存不足"处理流程 |
| 32 | 外中断 | 定时器中断 | 像"闹钟响了"处理流程 |
| 33 | 外中断 | 键盘中断 | 像"有人按键"处理流程 |
| 128 (0x80) | 陷入 | Linux 系统调用（x86） | 像"点餐窗口"处理流程 |

```c
// 中断处理示例（伪代码）
#include <stdio.h>

// 中断服务程序（ISR）
void keyboard_isr() {
    // 读取键盘缓冲区
    char key = read_keyboard_buffer();
    // 处理按键
    printf("按下了: %c\n", key);
}

// 中断向量表（简化版）
void* interrupt_vector_table[256] = {
    [0] = divide_by_zero_handler,      // 中断 0：除零错误
    [6] = invalid_opcode_handler,      // 中断 6：非法指令
    [13] = general_protection_fault,   // 中断 13：通用保护异常
    [14] = page_fault_handler,         // 中断 14：缺页异常
    [32] = timer_interrupt_handler,    // 中断 32：定时器中断
    [33] = keyboard_isr,               // 中断 33：键盘中断
    [128] = syscall_handler,           // 中断 128：系统调用
};

int main() {
    // 当键盘中断发生时，CPU 会自动调用 keyboard_isr()
    return 0;
}
```

## 2.5 操作系统结构

### 简单结构

早期操作系统（如 MS-DOS）没有明确的模块划分，代码高度耦合。

打个比方：

> 就像一个杂货铺，老板一个人既收银、又理货、又打扫卫生，所有事情混在一起。

```
+------------------+
|   应用程序        |
+------------------+
|   BIOS / DOS     |  <-- 没有清晰的模块边界
+------------------+
|   硬件           |
+------------------+
```

### 分层结构

将操作系统划分为多个层次，每层只使用下一层提供的服务。

打个比方：

> 就像一栋大楼，每层只能使用下一层的服务。1 楼用 0 楼的服务，2 楼用 1 楼的服务，不能跨层使用。

```
+------------------+
|  第 N 层：用户界面 |  <-- 你在这里，看到图形界面
+------------------+
|  第 N-1 层：...   |
+------------------+
|    ...            |
+------------------+
|  第 1 层：硬件抽象 |  <-- 把硬件操作封装成简单接口
+------------------+
|  第 0 层：硬件    |  <-- 最底层的硬件
+------------------+
```

| 优点 | 缺点 |
| --- | --- |
| 模块化和易于调试 | 层次间调用可能带来性能开销 |
| 每层只关心自己的功能 | 层次划分有时不够灵活 |
| 修改一层不影响其他层 | 跨层调用需要层层传递 |

### 微内核结构

只将最基本的功能放入内核，其余功能以用户态进程（服务）的形式运行。

打个比方：

> 就像一个公司，只保留核心管理层（微内核），其他业务部门（文件系统、网络栈、驱动程序）都是独立的子公司，通过内部通信（IPC）协作。

| 微内核提供的功能 | 用户态服务 |
| --- | --- |
| 进程间通信（IPC） | 文件系统服务 |
| 基本调度 | 内存管理服务 |
| 基本地址空间 | 设备驱动服务 |

| 优点 | 缺点 |
| --- | --- |
| 可靠性高（一个服务崩溃不影响系统） | IPC 开销大，性能可能低于宏内核 |
| 安全性好 | 实现复杂 |
| 易于扩展 | 调试困难 |

```
+----------------------------------+
|           用户空间                |
|  +--------+--------+--------+    |
|  | 文件系统| 网络栈 | 驱动程序|    |  <-- 这些服务独立运行
|  +--------+--------+--------+    |
+----------------------------------+
|           内核空间                |
|  +----------------------------+  |
|  |      微内核（核心功能）     |  |
|  |  - 进程管理                |  |
|  |  - 内存管理                |  |
|  |  - IPC（进程间通信）       |  |
|  +----------------------------+  |
+----------------------------------+
```

## 2.6 对比表格

| 对比项 | 简单结构 | 分层结构 | 微内核结构 |
| --- | --- | --- | --- |
| 模块化程度 | 低（代码耦合） | 中（按层划分） | 高（按功能划分） |

## 2.7 新手常见误区

### 误区 1："系统调用就是普通的函数调用"

不对。系统调用和普通函数调用有本质区别：

- 普通函数调用：在用户态执行，不切换模式，速度快
- 系统调用：需要从用户态切换到内核态，执行完再切换回来，速度慢

打个比方：普通函数调用就像你在自己房间里拿东西，系统调用就像你要去物业那里办事。

```c
// 普通函数调用：不切换模式
int add(int a, int b) {
    return a + b;  // 直接在用户态执行
}

// 系统调用：需要切换到内核态
write(1, "Hello", 5);  // 从用户态切换到内核态，由操作系统操作硬件
```

### 误区 2："中断就是系统调用"

不对。中断和系统调用虽然都会切换到内核态，但触发方式不同：

- 系统调用：程序主动发起的（陷入）
- 中断：外部设备触发的（异步的）

打个比方：系统调用就像你主动按门铃叫外卖，中断就像门铃突然响了（快递来了）。

### 误区 3："用户态程序可以主动切换到内核态"

不对。用户态程序不能主动切换到内核态后继续执行自己的代码。切换只能通过中断、异常或系统调用，而且切换后执行的是操作系统代码，不是用户代码。

打个比方：你不能自己打开配电室的门进去操作，只能叫物业来帮你操作。

### 误区 4："中断处理越慢越好"

不对。中断处理应该尽可能快，否则会阻塞其他中断和程序执行。如果中断处理很耗时，应该把耗时的工作放到"下半部"（bottom half）延迟执行。

打个比方：快递小哥按门铃，你应该快速签收，而不是在门口聊半小时。

### 误区 5："微内核比宏内核先进，所以微内核更好"

不能简单地说谁更好。微内核可靠性好但性能差，宏内核性能好但可靠性差。不同的场景适合不同的架构。Linux 选择宏内核是因为服务器场景需要高性能，QNX 选择微内核是因为嵌入式场景需要高可靠性。

| `printf("Hello")` | 普通函数调用 | C 标准库函数，在用户态执行 |
| `write(1, "Hello", 5)` | 系统调用 | 需要切换到内核态，操作硬件 |
| `fork()` | 系统调用 | 创建新进程，需要内核参与 |
| `malloc(100)` | 普通函数调用 | C 标准库函数，分配内存（但底层可能调用系统调用） |
| `open("file.txt", O_RDONLY)` | 系统调用 | 打开文件，需要内核操作文件系统 |

注意：`printf` 和 `malloc` 虽然是普通函数，但它们底层可能会调用系统调用（如 `write` 和 `mmap`）。

</details>

### 练习 2：进阶练习

用生活化的语言解释以下概念：

1. 内核态和用户态
2. 系统调用
3. 中断
4. 中断向量表

<details>
<summary>点击查看答案</summary>

参考答案：

1. 内核态和用户态：
   - 内核态就像大楼的配电室，只有物业（操作系统）能进，可以操作所有设备
   - 用户态就像大楼的各个房间，租户（用户程序）可以在里面自由活动，但不能进配电室

2. 系统调用：
   - 就像餐厅的点餐窗口，你（用户程序）不能直接进厨房（内核）做菜，只能通过点餐窗口告诉服务员你要什么

3. 中断：
   - 就像你在家写作业，突然门铃响了。你放下笔（保存现场），去开门（执行中断处理），看到是快递（处理事件），签收了快递（完成处理），然后回到书桌继续写作业（恢复现场）

4. 中断向量表：
   - 就像一本电话簿，每个中断号对应一个处理函数的地址。门铃响（中断 33），你查电话簿知道要去门口签收（调用 keyboard_isr）

### 练习 3（挑战）：综合练习

假设你要设计一个操作系统，请回答以下问题：

1. 你会选择哪种结构（简单结构/分层结构/微内核）？为什么？
2. 哪些功能应该放在内核态？哪些可以放在用户态？
3. 如何设计中断处理机制？

<details>
<summary>点击查看答案</summary>

参考答案：

1. 结构选择：分层结构。因为分层结构模块化和易调试的优点适合教学操作系统，而且性能比微内核好。如果是生产环境，可能会选择微内核（如嵌入式场景）或宏内核（如服务器场景）。

2. 功能划分：
   - 内核态：进程管理、内存管理、中断处理、系统调用接口
   - 用户态：文件系统、网络栈、设备驱动程序
   
   理由：核心功能必须放在内核态保证安全和效率，非核心功能放在用户态提高可靠性。

3. 中断处理机制设计：
   - 使用中断向量表，每个中断号对应一个处理函数
   - 中断处理程序要尽可能快，耗时的工作放到下半部
   - 区分可屏蔽中断和不可屏蔽中断
   - 中断处理时要保存和恢复现场

</details>
