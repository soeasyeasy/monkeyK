# 第六章：进程同步

## 本章导读

在学这一章之前，你可能会有这些疑问：

- 多个程序同时运行时，为什么会出现数据错乱？
- 什么是"竞争条件"？为什么它这么危险？
- 操作系统是怎么保证多个进程"有序"访问共享资源的？
- 信号量和管程到底是什么？它们有什么区别？

这一章就是为了解答这些问题。我们会先搞清楚 **竞争条件和临界区问题**，然后学习 Peterson 算法、硬件同步指令、信号量和管程等同步机制，让你能够理解并发编程中的核心难题和解决方案。

---

## 1 为什么需要进程同步？

### 痛点分析

想象一下，你和室友共用一个银行账户：

- 你查看余额：1000 元
- 室友同时查看余额：1000 元
- 你取出 200 元，余额变成 800 元
- 室友取出 300 元，余额变成 700 元（他以为余额是 1000）
- 实际应该剩下 500 元，但系统显示 700 元

这就是没有同步机制时的灾难——数据不一致，结果不可预测。

### 解决方案

进程同步就像是给银行账户加了一把锁：

- 你取钱时，先锁住账户
- 室友必须等你取完、解锁后才能操作
- 这样就能保证数据的一致性

> **一句话总结**：进程同步让多个进程能够"有序、安全"地访问共享资源，避免数据错乱。

## 2 同步的基本概念

### 竞争条件（Race Condition）

当多个进程并发访问和操作共享数据，且最终结果取决于执行顺序时，就发生了竞争条件。

打个比方：

> 就像两个人同时编辑同一个文档，一个人刚写完一句话，另一个人就把它删了，最后文档乱七八糟。

```c
// 共享变量
int counter = 0;  // 这是一个共享的计数器

// 两个进程同时执行这个函数
void increment() {
    counter++;  // 看起来是一行代码，但实际上包含三步：
                // 1. 读取 counter 的值到 CPU 寄存器
                // 2. 在寄存器中把值加 1
                // 3. 把新值写回 counter
}

// 进程 A 和进程 B 同时调用 increment()
// 期望结果：counter = 2（加了两次 1）
// 实际可能：counter = 1（交错执行导致丢失了一次加法）
```

交错执行的详细过程：

```
时间  进程 A              进程 B              内存中的 counter
─────────────────────────────────────────────────────────────
t1   读取 counter (=0)                        counter = 0
t2                        读取 counter (=0)    counter = 0
t3   counter + 1 (=1)                         counter = 0
t4                        counter + 1 (=1)     counter = 0
t5   写回 counter (=1)                        counter = 1
t6                        写回 counter (=1)    counter = 1
→ 结果：counter = 1（错误！应该是 2）
```

::: info
要避免竞争条件，必须确保多个进程在访问共享数据时是**互斥**的——即同一时刻只有一个进程在操作共享数据。就像卫生间，一次只能进一个人，其他人必须排队等待。
:::

## 3 临界区问题

### 临界区模型

每个进程的代码可以分为四个部分：

```
┌─────────────────────────────┐
│         进入区（Entry Section）  │  ← 请求进入临界区，申请锁
├─────────────────────────────┤
│         临界区（Critical Section）│  ← 访问共享资源的代码
├─────────────────────────────┤
│         退出区（Exit Section）   │  ← 释放临界区，释放锁
├─────────────────────────────┤
│         剩余区（Remainder Section）│ ← 其他不访问共享资源的代码
└─────────────────────────────┘
```

打个比方：

> 临界区就像卫生间的洗手台，进入区是敲门问"有人吗？"，临界区是洗手，退出区是开门出来，剩余区是其他活动。

### 临界区问题的三个要求

要正确解决临界区问题，必须满足以下三个条件：

| 要求 | 说明 | 生活类比 |
| --- | --- | --- |
| 互斥（Mutual Exclusion） | 同一时刻最多只有一个进程在临界区内 | 卫生间一次只能进一个人 |
| 前进（Progress） | 如果没有进程在临界区内，且有进程想进入，则应该让它们中的一个进入，不能无限期推迟 | 卫生间没人时，排队的人应该能进去 |
| 有界等待（Bounded Waiting） | 进程请求进入临界区后，必须在有限步内获得许可进入 | 排队的人不能无限等待，必须有上限 |

## 4 Peterson 算法

**Peterson 算法**是 1981 年由 Gary Peterson 提出的软件解决方案，用于解决两个进程的临界区问题。

打个比方：

> 就像两个人共用一个房间，他们约定：先举手表示想用房间，然后把"使用权"让给对方。如果对方也想用，就让对方先进；如果对方不用，自己就进去。

### 算法实现

```c
// 共享变量
int turn;           // 表示谁应该进入临界区（0 或 1）
boolean flag[2];    // 表示进程是否想进入临界区

// 进程 i 的代码（j = 1 - i，即另一个进程）
do {
    // 进入区代码
    flag[i] = true;         // 表示"我想进入临界区"
    turn = j;               // 礼貌地说"该你了"（让给对方）

    // 等待条件：对方也想进入 且 轮到对方
    while (flag[j] && turn == j);  // 自旋等待，直到对方不想进或轮到自己

    // 临界区代码
    // ... 访问共享资源 ...

    // 退出区代码
    flag[i] = false;        // 表示"我离开临界区了"

    // 剩余区代码
    // ... 其他操作 ...
} while (true);
```

### 正确性分析

| 要求 | 是否满足 | 说明 |
| --- | --- | --- |
| 互斥 | 满足 | 两个进程不能同时在临界区，因为 turn 只能指向一个进程 |
| 前进 | 满足 | 如果只有一个进程想进入，它可以立即进入 |
| 有界等待 | 满足 | 每个进程最多等待一次，对方就会让出 |

::: tip
Peterson 算法仅适用于两个进程。对于多进程场景，需要使用更通用的方法（如信号量、硬件指令等）。这个算法的意义在于证明了纯软件也能解决同步问题。
:::

## 5 硬件同步指令

现代计算机体系结构提供了特殊的硬件指令来支持同步操作，这些指令都是**原子操作**——在执行过程中不会被中断。

### 测试并设置（Test-and-Set）

原子地读取并修改一个内存位置，就像检查门锁并立即锁门，一气呵成。

```c
// 硬件指令：测试并设置
boolean TestAndSet(boolean *target) {
    boolean old = *target;    // 保存原来的值
    *target = true;           // 设置为 true（上锁）
    return old;               // 返回原来的值（如果是 false，说明之前没锁）
}

// 使用 Test-and-Set 实现互斥
boolean lock = false;  // 共享锁，初始为 false（未锁定）

do {
    // 进入区
    while (TestAndSet(&lock));  // 如果 lock 是 true，就一直重试（自旋等待）

    // 临界区
    // ... 访问共享资源 ...

    // 退出区
    lock = false;  // 释放锁

    // 剩余区
} while (true);
```

### 交换（Swap）

原子地交换两个内存位置的值，就像两个人交换座位。

```c
// 硬件指令：交换
void Swap(boolean *a, boolean *b) {
    boolean temp = *a;    // 临时保存 a 的值
    *a = *b;              // 把 b 的值给 a
    *b = temp;            // 把 a 原来的值给 b
}

// 使用 Swap 实现互斥
boolean lock = false;  // 共享锁

do {
    boolean key = true;         // 准备一个"钥匙"
    while (key) {
        Swap(&lock, &key);      // 原子交换：lock 和 key 互换
        // 如果 lock 原来是 false，key 就变成 false，循环结束
        // 如果 lock 原来是 true，key 还是 true，继续等待
    }

    // 临界区
    // ... 访问共享资源 ...

    // 退出区
    lock = false;  // 释放锁

    // 剩余区
} while (true);
```

### 比较并交换（Compare-and-Swap, CAS）

更高级的原子操作，只有当前值等于期望值时才更新。

```c
// 硬件指令：比较并交换
int CompareAndSwap(int *value, int expected, int new_value) {
    int temp = *value;              // 保存当前值
    if (*value == expected) {       // 如果当前值等于期望值
        *value = new_value;         // 更新为新值
    }
    return temp;                    // 返回原来的值
}

// 使用示例
// 如果 value 当前是 0，就改成 1；否则不变
CompareAndSwap(&value, 0, 1);
```

::: info
这些硬件指令都是**原子操作**——在执行过程中不会被中断。它们是实现同步原语的基础，但使用不当会导致**忙等待（Busy Waiting）**，浪费 CPU 资源。就像你在卫生间门口一直敲门问"好了没？好了没？"，而不是坐下来等。
:::

### 硬件指令方案的问题

| 问题 | 说明 | 生活类比 |
| --- | --- | --- |
| 忙等待 | 进程在等待锁时持续消耗 CPU | 一直敲门问，浪费精力 |
| 饥饿 | 等待的进程可能无限期等待 | 排队的人可能永远进不去 |
| 死锁 | 多个进程互相等待 | 两个人互相等对方先走 |

## 6 信号量（Semaphore）

**信号量**是 Dijkstra 提出的一种更高级的同步工具，解决了硬件方案中忙等待的问题。

打个比方：

> 信号量就像停车场的计数器：显示还有多少空位。车进来时减 1，车出去时加 1。当计数器为 0 时，新车就只能在外面等，不会一直在门口转圈。

### 信号量的定义

```c
// 信号量是一个整数变量，只能通过两个原子操作访问

// wait 操作（也叫 P 操作、down 操作）
void wait(semaphore *S) {
    S->value--;              // 计数器减 1
    if (S->value < 0) {      // 如果计数器变成负数
        // 阻塞当前进程（让它睡觉，不消耗 CPU）
        block();
    }
    // 如果计数器 >= 0，进程继续执行
}

// signal 操作（也叫 V 操作、up 操作）
void signal(semaphore *S) {
    S->value++;              // 计数器加 1
    if (S->value <= 0) {     // 如果计数器 <= 0，说明有进程在等待
        // 唤醒一个等待的进程
        wakeup();
    }
    // 如果没有进程等待，只是简单地增加计数器
}
```

### 信号量类型

| 类型 | 值域 | 用途 | 生活类比 |
| --- | --- | --- | --- |
| 计数信号量 | 任意非负整数 | 控制对多个资源的访问 | 停车场有 100 个车位 |
| 二值信号量（互斥锁） | 0 或 1 | 实现互斥访问 | 卫生间只有一个坑位 |

### 使用信号量实现互斥

```c
semaphore mutex = 1;  // 初始值为 1，表示资源可用

// 进程 Pi
do {
    wait(mutex);      // 进入区：申请锁（如果 mutex=1，变成 0，进入临界区）
    // 临界区
    // ... 访问共享资源 ...
    signal(mutex);    // 退出区：释放锁（mutex 从 0 变成 1）
    // 剩余区
} while (true);
```

### 使用信号量实现同步

```c
// 场景：进程 P1 执行完 S1 后，P2 才能执行 S2
semaphore sync = 0;  // 初始值为 0，表示 P2 必须等待

// 进程 P1
S1;              // 执行 S1
signal(sync);    // 通知 P2："我完成了，你可以开始了"

// 进程 P2
wait(sync);      // 等待 P1 完成（如果 sync=0，P2 被阻塞）
S2;              // P1 完成后，P2 才能执行 S2
```

::: tip
信号量的关键优势是**没有忙等待**。当进程无法获得信号量时，它会被阻塞并放入等待队列，不消耗 CPU 资源。就像在餐厅排队，你可以坐下来等，而不是站在门口一直问。
:::

## 7 管程（Monitor）

**管程**是一种高级同步构造，将共享数据和操作封装在一起，确保同一时刻只有一个进程在管程内活动。

打个比方：

> 管程就像自动售货机：你把钱放进去（输入），选择商品（操作），机器自动处理（封装的逻辑），吐出商品（输出）。你不需要知道机器内部怎么工作，也不需要担心别人同时操作。

```
// 管程的基本结构
monitor MonitorName {
    // 共享变量（只有管程内部能访问）
    int count;

    // 条件变量（用于进程间同步）
    condition full, empty;

    // 操作（封装了对共享数据的操作）
    void produce() {
        // 生产逻辑
        // ...
    }

    void consume() {
        // 消费逻辑
        // ...
    }

    // 初始化
    init() {
        count = 0;
    }
}
```

### 管程的特点

| 特点 | 说明 | 优势 |
| --- | --- | --- |
| 模块化 | 将共享资源及其操作封装在一起 | 代码更清晰，易于维护 |
| 互斥 | 自动保证同一时刻只有一个进程在管程内 | 编译器保证，不会出错 |
| 条件变量 | 通过 wait/signal 实现进程间的同步 | 更灵活，支持复杂同步 |

::: info
管程的优点是安全性高（编译器保证互斥），但灵活性不如信号量。Java 中的 `synchronized` 关键字和 `ReentrantLock` 就是管程思想的实现。你可以把 `synchronized` 方法看作是一个管程，同一时刻只有一个线程能执行。
:::

## 8 同步机制对比

| 机制 | 实现方式 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| Peterson 算法 | 纯软件 | 简单，无需硬件支持 | 仅适用于两个进程 | 教学示例 |
| 硬件指令 | 原子指令 | 简单，通用 | 忙等待，浪费 CPU | 底层实现 |
| 信号量 | 操作系统支持 | 无忙等待，灵活 | 使用不当易出错 | 通用同步 |
| 管程 | 语言/编译器支持 | 安全，模块化 | 灵活性较低 | 高级语言 |

## 9 新手常见误区

### 误区 1："信号量的 wait 和 signal 可以随便调换顺序"

**错！** wait 和 signal 的顺序非常重要：

1. 在生产者-消费者问题中，如果先 `wait(mutex)` 再 `wait(empty)`，当缓冲区满时会导致死锁
2. 正确顺序：先 `wait(empty)` 再 `wait(mutex)`，先检查资源，再加锁

正确做法：理解每个信号量的作用，按照逻辑顺序调用。

### 误区 2："二值信号量和互斥锁是一样的"

**不完全对！** 虽然它们都能实现互斥，但有区别：

1. 二值信号量：值为 0 或 1，可以用于同步和互斥
2. 互斥锁（mutex）：有所有权概念，只有加锁的线程才能解锁
3. 互斥锁支持优先级继承，可以避免优先级反转问题

正确做法：实现互斥时优先使用 mutex，同步时使用信号量。

### 误区 3："管程比信号量高级，所以总是更好"

**不是的！** 管程和信号量各有优缺点：

1. 管程：安全性高（编译器保证），但灵活性低，某些复杂同步难以实现
2. 信号量：灵活性高，可以实现各种同步逻辑，但使用不当容易出错

正确做法：根据场景选择，简单互斥用管程，复杂同步用信号量。

### 误区 4："硬件指令方案效率最高"

**不一定！** 硬件指令方案会导致忙等待：

1. 忙等待会持续消耗 CPU 资源
2. 在单 CPU 系统中，忙等待甚至可能导致死锁
3. 信号量通过阻塞进程，避免了忙等待，整体效率更高

正确做法：硬件指令主要用于实现更高级的同步原语（如信号量），不直接用于应用层。

### 练习 1：基础练习 - 竞争条件分析

分析以下代码，说明为什么会出现竞争条件，并给出可能的执行结果。

```c
int x = 10, y = 20;

// 进程 A
void processA() {
    x = x + 5;    // 步骤 1：读取 x
                  // 步骤 2：x + 5
                  // 步骤 3：写回 x
}

// 进程 B
void processB() {
    y = y + x;    // 步骤 1：读取 y
                  // 步骤 2：读取 x
                  // 步骤 3：y + x
                  // 步骤 4：写回 y
}
```

假设两个进程同时执行，x 和 y 的最终值可能是多少？

<details>
<summary>点击查看答案</summary>

**可能的执行序列和结果：**

**情况 1：A 先执行完，B 再执行**
- A 执行：x = 15
- B 执行：y = 20 + 15 = 35
- 最终：x = 15, y = 35

**情况 2：B 先执行完，A 再执行**
- B 执行：y = 20 + 10 = 30
- A 执行：x = 15
- 最终：x = 15, y = 30

**情况 3：交错执行（B 读取 x 时 A 还没写回）**

- B 读取 x = 10
- A 执行：x = 15
- B 计算：y = 20 + 10 = 30

- A 执行：x = 15
- B 读取 y = 20
- B 读取 x = 15
- B 计算：y = 20 + 15 = 35
- 最终：x = 15, y = 35

**结论：** 由于竞争条件，y 的值可能是 30 或 35，取决于执行顺序。

<details>
<summary>点击查看答案</summary>

**信号量定义：**
```c
semaphore empty = 3;    // 空位数量，初始为 3
semaphore full = 0;     // 满位数量，初始为 0
semaphore mutex = 1;    // 互斥信号量，保护缓冲区访问
```

**进程 A（生产者）：**
```c
void producer() {
    while (true) {
        item = produce();       // 生产一个数据
        wait(empty);            // 等待空位（如果 empty=0，阻塞）
        wait(mutex);            // 进入临界区，加锁
        insert(item);           // 放入缓冲区
        signal(mutex);          // 离开临界区，解锁
        signal(full);           // 满位数量加 1，通知消费者
    }
}
```

**进程 B（消费者）：**
```c
void consumer() {
    while (true) {
        wait(full);             // 等待数据（如果 full=0，阻塞）
        wait(mutex);            // 进入临界区，加锁
        item = remove();        // 从缓冲区取出
        signal(mutex);          // 离开临界区，解锁
        signal(empty);          // 空位数量加 1，通知生产者
        consume(item);          // 消费数据
    }
}
```

**信号量作用说明：**
- `empty`：控制生产者，缓冲区满时阻塞
- `full`：控制消费者，缓冲区空时阻塞
- `mutex`：保证对缓冲区的互斥访问

**执行流程示例：**
1. 初始：empty=3, full=0, mutex=1
2. 生产者生产：wait(empty)→empty=2, wait(mutex)→mutex=0, insert, signal(mutex)→mutex=1, signal(full)→full=1
3. 消费者消费：wait(full)→full=0, wait(mutex)→mutex=0, remove, signal(mutex)→mutex=1, signal(empty)→empty=3
